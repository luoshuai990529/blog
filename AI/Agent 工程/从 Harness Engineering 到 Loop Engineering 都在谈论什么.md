# 从 Harness Engineering 到 Loop Engineering 都在谈论什么？

## 一、问题背景

AI Coding 进入工程深水区之后，真正的瓶颈已经不再只是“模型会不会写代码”。

在早期 Demo 阶段，一个好的 Prompt 往往就能带来明显收益：让模型解释代码、生成函数、补测试、改样式。但当 Agent 被放进真实项目里，问题会迅速变复杂：需求描述不完整、业务规则藏在老代码和老同学脑子里、文档过期、测试不可信、工具权限不清楚、执行过程不可追踪、失败经验无法沉淀。

这也是为什么近几年 AI 工程领域连续出现了几个新词：Prompt Engineering、Context Engineering、Harness Engineering、Loop Engineering。它们不是单纯的概念营销，而是在回答同一个问题的不同层面：

> 如何把大模型从一次性问答工具，推进到可验证、可恢复、可持续运行的工程系统？

## 二、核心结论

> [!summary] 核心判断
> Prompt、Context、Harness、Loop 不是互相替代的概念，而是层层嵌套的工程能力：Prompt 负责把任务说清楚，Context 负责给模型正确背景，Harness 负责给 Agent 搭建可靠执行环境，Loop 负责让 Agent 围绕目标持续迭代。

如果只优化 Prompt，Agent 仍然会缺少业务上下文；如果只堆上下文，Agent 仍然可能在错误工具、错误权限和错误验证里失控；如果只有 Harness，Agent 仍然主要是被动执行；而 Loop Engineering 的价值，是在前面这些基础足够稳之后，让 Agent 能跨回合、跨任务、跨时间地自主推进目标。

一句话说：

```text
Prompt Engineering 解决“怎么说清楚”
Context Engineering 解决“该让模型知道什么”
Harness Engineering 解决“模型如何被约束、验证和执行”
Loop Engineering 解决“Agent 如何持续、自主地推进目标”
```

## 三、概念时间线：这些新词分别在解决什么

### 1. 2022 左右：Prompt Engineering

Prompt Engineering 关注的是如何写好指令：角色设定、任务拆解、输出格式、约束条件、Few-shot 示例、思考步骤等。

它解决的是“任务表达”问题。对于一次性生成、问答、改写、代码片段生成，Prompt 的质量仍然非常重要。但它的边界也很明显：再好的 Prompt，也无法自动补齐企业内部知识、历史决策、工具状态和真实验证结果。

### 2. 2025 左右：Context Engineering

Context Engineering 关注的是如何给模型提供正确背景。它不仅包括 RAG，也包括文件检索、MCP 工具、历史消息压缩、知识库、规则文档、仓库结构、API 文档、测试日志等上下文治理。

它解决的是“模型该看到什么”问题。很多 Agent 失败不是因为模型不会推理，而是因为它看到的信息不完整、不新、不准，或者上下文太长导致关键信号被噪声淹没。

### 3. 2026 年初：Harness Engineering

Harness Engineering 关注的是模型外部的工程环境。它不直接追求“让模型更聪明”，而是给 Agent 配置工具、约束、检查、执行管线、状态管理、权限边界、日志、评分器和知识沉淀机制。

它解决的是“Agent 如何真实执行并被验证”问题。企业项目里，AI 生成代码只是中间步骤，真正重要的是代码能否通过测试、是否符合业务约束、是否可回滚、是否能被审计、失败经验能否进入下一次执行。

### 4. 2026 年中：Loop Engineering

Loop Engineering 关注的是自主循环。它不再把 Agent 看作“你问一次，它答一次”的工具，而是让 Agent 围绕目标反复执行“计划、行动、检查、修正”，直到满足停止条件，或者明确证明目标不可达。

它解决的是“Agent 如何持续推进复杂目标”问题。典型形态包括目标导向循环、时间驱动循环、主动式循环、多 Agent 并行循环，以及跨 session 的长期任务恢复。

## 四、它在 Agent 工程链路中的位置

从 Agent 系统链路看，这四层可以这样放置：

```text
用户目标
  → Prompt Engineering：定义任务、约束、输出格式
  → Context Engineering：注入项目知识、业务背景、工具信息、历史状态
  → Harness Engineering：提供工具、权限、验证、观测、知识沉淀
  → Loop Engineering：基于目标、触发器、停止条件持续迭代
  → 可验证交付物：代码、文档、PR、测试结果、运行状态、知识库更新
```

这也是为什么四层是嵌套关系，而不是替代关系。Loop Engineering 依赖 Harness 提供可靠验证，Harness 依赖 Context 提供正确背景，Context 又依赖 Prompt 把任务目标和边界讲清楚。

## 五、Harness Engineering：给 Agent 搭一个可靠工作环境

Harness 的直译有“安全带、马具、测试夹具”的含义，放在 Agent 工程里，可以理解为包在模型外面的执行系统。

它的核心不是写一个更长的系统提示词，而是把 Agent 做事所需的环境结构化：

- **Guides**：规则、流程、最佳实践、代码规范、业务协议。
- **Tools**：代码编辑、命令执行、浏览器、MCP、数据库、CI、监控系统。
- **Sensors**：测试结果、日志、截图、告警、评分器、用户反馈。
- **Guards**：权限边界、人工确认、受保护文件、危险操作拦截。
- **Memory**：项目知识、变更记录、失败样本、决策历史。
- **Observability**：执行轨迹、token 消耗、工具调用、产物状态。

企业级 Harness 的目标，是让 Agent 的行为变得可控、可测、可回溯。它不保证模型永远不犯错，但它要保证错误能被发现、能被限制、能被复盘，并能转化成下一次执行时的知识。

大多企业级的 Harness 实践可以概括成三块：

1. **研发端到端交付轨道**：把需求、设计、实现、测试、部署、归档拆成标准阶段，让 Agent 在固定协议里推进。
2. **线上运营闭环轨道**：把告警、巡检、证据采集、根因分析、修复、回归和归档纳入 AI 辅助流程。
3. **长期知识库**：把业务规则、接口契约、变更历史、踩坑经验沉淀为 Agent 可检索和可复用的长期记忆。

这类实践的关键不是“让 AI 一步完成所有事”，而是先把真实研发流程拆成可执行、可检查、可沉淀的工程单元。

### 1. Harness 的模块边界与接口契约

Harness 不能只是一组散落在主循环里的回调。模型、工具、状态、策略和验证会持续变化，如果没有清晰模块边界，后续接入新模型、新工具或新审批规则时，很容易把运行时改成不可测试的大状态机。

一个可演进的 Harness 至少应把下面几类能力抽象成独立模块：

| 模块 | 核心职责 | 最小接口关注点 |
| --- | --- | --- |
| `ToolRegistry` | 注册、描述和发现可调用能力 | 输入 Schema、输出 Schema、副作用等级、超时、是否可取消 |
| `StateStore` | 保存会话、任务、待办和工具执行状态 | 检查点、幂等键、恢复、版本和生命周期 |
| `PolicyEngine` | 在执行前作出确定性授权决策 | allow / ask / deny、作用域、风险等级、审计原因 |
| `Verifier` | 判断步骤或任务是否真的完成 | 测试、断言、评分器、人工审批、失败证据 |
| `MemoryProvider` | 管理长期知识与会话记忆 | 写入策略、检索、过期、冲突和来源 |
| `TraceExporter` | 输出一次执行的过程证据 | run、model、tool、approval、verification 的关联标识 |

模型只负责提出下一步意图；Harness 负责把意图转换成带契约、权限和反馈的执行。尤其不能让模型直接决定工具副作用、状态提交和完成判定，这些必须由可测试的确定性模块兜底。

推荐的调用顺序是：

```text
模型输出 tool call
  → ToolRegistry 校验输入与副作用
  → PolicyEngine 决定放行、审批或拒绝
  → Executor 执行并写入 StateStore
  → Verifier 验证环境结果
  → TraceExporter 记录证据
  → 将受预算控制的结果返回模型
```

### 2. Trace 与 OpenTelemetry：让一次 Agent 执行可观测、可审计

普通应用只记录接口日志，往往无法解释“为什么 Agent 选了这个工具、工具执行后状态是否改变、答案为什么被判定完成”。Harness 的 Trace 应以一次任务运行（`agent.run`）为根，而不是以某条自然语言消息为根。

建议将一次执行统一关联为：

```text
agent.run
  ├─ context.load
  ├─ model.call
  ├─ tool.call
  │   └─ approval / retry / cancellation
  ├─ verifier.check
  └─ final.answer / task.complete
```

每个 span 至少关联 `trace_id`、`run_id`、`session_id`、`task_id` 和 `tool_call_id`；模型调用还应记录模型版本、输入/输出 token、缓存命中、延迟和成本，工具调用则应记录权限决策、副作用等级、目标资源、重试次数和最终状态。敏感 Prompt、凭证和业务数据不能直接写入 Trace，应只记录脱敏摘要、哈希或受权限保护的引用。

OpenTelemetry 的价值不在于“多接一个 SDK”，而在于让模型调用、工具执行、审批、CI 和线上指标沿用同一条 Trace 关联链。这样一次失败才能从用户任务定位到模型决策、工具参数、验证报告和实际系统状态，并支持成本分析、线上抽样评测与安全审计。

### 3. Agent CI/PR 交付流水线：把“完成”变成可合并的证据

Coding Agent 的终点不应是“生成了代码”，而应是一个可审查、可验证、可回滚的变更。Harness 应将 Agent 的产物纳入既有工程交付链，而不是绕过分支、CI 与评审直接写入主干。

一条可执行的最小流水线可以是：

```text
任务与验收标准
  → 独立 worktree / 分支
  → Agent 计划与实现
  → 本地 lint、类型检查、单测和必要的 UI/接口验证
  → 独立 Review Agent 审查 diff 与验收证据
  → 创建 PR
  → CI、人工审批或策略检查
  → 合并、发布与线上回归
  → 将结果、失败原因和决策归档
```

其中的关键不是让每一步都由 Agent 自动完成，而是为每一步定义输入、产物、验证器和回退方式。实现 Agent 不能同时充当唯一验证者；高风险变更应由独立上下文的 Review Agent、CI 或人工审批打断“自证正确”的偏差。发布、生产数据修改和权限调整仍应保留明确的人工闸门。

### 4. 仓库知识治理与熵治理：让 Agent 长期看得懂系统

对 Agent 而言，无法在运行时发现、读取和验证的知识，等价于不存在。架构决策、领域规则、接口契约、执行计划、已知风险和验证方式，应尽量作为仓库内、版本化、可链接的工件保存，而不应长期停留在聊天记录、即时消息或个人记忆中。

但“把文档都存下来”不是治理。随着需求和代码演进，规则、Skill、工具描述、测试与文档都会产生熵：过期内容、重复约束、相互冲突的方案和无效工具会让 Agent 得到错误上下文，且降低选择正确动作的概率。

建议建立轻量的治理机制：

1. **知识分层**：项目入口规则保持短且稳定；领域说明、运行手册、执行计划和历史决策按需加载。
2. **变更同步**：代码、接口或部署方式发生变更时，CI 检查关联文档、Schema、示例与验证命令是否同步更新。
3. **可执行验证**：优先将不变量写入类型、测试、Linter、Hooks 和 CI；文档说明不能替代机器可执行的约束。
4. **定期清理**：用定时任务或 Agent 扫描失效链接、陈旧规则、未引用 Skill、重复工具和长期失败样本，生成小粒度修复 PR。
5. **决策可追溯**：关键计划、架构取舍、验证报告和已知债务需要带来源、更新时间与适用范围，避免旧结论被当作当前事实。

仓库知识治理的目标不是让 Agent 读取更多文档，而是持续提高“正确上下文在需要时可发现、可验证、可更新”的概率。熵治理也不是一次性重构，而是用小步、可验证的清理避免技术债和错误知识不断复利。

## 六、Loop Engineering：让 Agent 从响应工具变成持续执行系统

Loop Engineering 的核心，是把人从每一步操作里抽离出来，让人只负责目标设定、监督和最终判断。

传统 AI Coding 是：

```text
人输入 Prompt → Agent 执行一次 → 人检查 → 人继续输入 Prompt
```

Loop Engineering 希望变成：

```text
人定义目标和停止条件
  → Agent 自主计划
  → Agent 执行
  → 系统验证
  → 不满足则继续迭代
  → 满足条件或达到上限后退出
```

常见 Loop 可以分成四类：

1. **回合制循环**：每次 Prompt 都触发一次 Agent 循环，适合探索性、小规模、非固定流程任务。
2. **目标导向循环**：通过 `/goal` 定义完成标准，让 Agent 多轮尝试直到达标或达到尝试上限。
3. **时间驱动循环**：通过 `/loop`、`/schedule` 等机制定时检查外部状态，比如 PR 评论、CI、告警、日报。
4. **主动式循环**：把 schedule、goal、skills、subagents、workflows、auto mode 组合起来，处理持续涌入的工单、反馈、依赖升级或数据迁移。

Loop Engineering 和 ReAct 的区别在于层级不同。ReAct 更像一次任务内部的“思考、行动、观察”模式；Loop Engineering 更关注任务外层的触发器、停止条件、状态恢复、验证策略、成本控制和长期自治。

Loop 的风险也更大。没有明确目标，Agent 会高效跑偏；没有验证机制，Agent 会把“看起来完成”当成真正完成；没有状态外置，长任务中断后无法恢复；没有成本预算，循环会吞掉大量 token 和工具调用。

因此，Loop 不是越自动越好，而是要在 Harness 可靠之后逐步释放自主度。

## 七、Claude Code 与 CodeBuddy 的能力映射

### 1. Claude Code

Claude Code 的 loop 能力可以按四层理解：

- **Prompt 层**：普通自然语言任务、明确输出格式、约束条件。
- **Context 层**：项目文件、技能文档、官方文档、历史对话、工具结果。
- **Harness 层**：Skills、tools、MCP、subagents、code review、usage 统计、验证脚本。
- **Loop 层**：`/goal`、`/loop`、`/schedule`、dynamic workflows、auto mode。

典型实践是：先用 Skills 固化验证方式，再用 `/goal` 定义客观完成条件。例如“将首页 Lighthouse 分数提升到 90 分以上，最多尝试 5 次”。这类任务适合 Loop，因为成功条件明确，验证方式客观，失败后 Agent 可以继续迭代。

### 2. CodeBuddy

CodeBuddy 的能力映射也类似：

- **Prompt / Rules**：定义项目规则、执行边界和输出约束。
- **Context / Memory**：保存项目知识、历史状态、业务背景。
- **Harness / MCP / Skills / Team**：连接外部工具，固化工作方法，使用多 Agent 进行探索、实现、审查。
- **Loop / Goal / Automations**：用 `/goal` 做目标导向循环，用 `/loop` 做本地周期循环，用 Automations 做跨 session 或云端周期任务。

实践上，可以把 CodeBuddy 用成一个“研发操作系统”：人提出目标，Agent 拆解任务，Team 模式并行探索，MCP 连接 GitHub、CI、监控和文档系统，Rules 和 Memory 保证项目约束延续，Automations 负责持续检查和推进。

但不建议一开始就追求全自动。更稳妥的方式，是先从高频、低风险、可验证的任务开始：比如处理 lint、补测试、修复 CI、同步文档、归档变更、巡检 PR 评论。

## 八、企业级项目中的落地问题

### 1. 老项目最大的障碍不是代码，而是隐性知识

历史项目里有大量“代码里看不见的规矩”：特殊客户逻辑、废弃但不能删的接口、文档与线上行为不一致、只有老同学知道的业务约束。

Agent 如果直接进入这类项目，很容易在语法层面做对，在业务层面做错。落地时要先建设项目知识库，把隐性规则变成可检索、可审计、可更新的显性上下文。

### 2. 测试通过不等于业务正确

AI 生成测试常见问题是覆盖不足、断言偏弱、只验证“能跑通”，没有验证“业务真的正确”。UI 自动化还会受环境、数据、截图差异和业务复杂度影响。

企业需要补的不只是测试数量，而是测试质量评估、反例生成、覆盖率与业务风险映射，以及对测试本身的二次审查机制。

### 3. 评分机制必须连接下游真实结果

很多团队会给 Agent 阶段产物打分，但分数如果只看当前阶段产物，就会出现“设计阶段 90 分，实现阶段翻车”的问题。

更好的做法是让评分机制接入下游反馈：实现失败、测试失败、线上告警、人工驳回、回滚记录，都应该反哺前面阶段的评分和规则。

### 4. 知识库需要治理，不只是归档

把所有变更都写进知识库并不等于长期记忆。知识会过期，规则会冲突，历史结论会被新架构推翻。

企业需要设计知识的生命周期：新增、引用、验证、老化、合并、淘汰。否则 Agent 会从知识库里检索到过期结论，并把它当成最新事实执行。

### 5. 自动化要有权限边界和人工刹车

Loop 的价值是减少人工持续参与，不是取消人工判断。涉及生产变更、数据修改、权限调整、成本增长、用户可见行为时，必须设置人工确认、回滚机制和审计记录。

## 九、推荐最佳实践流程

企业落地不建议从“全自动 Agent”开始，而应该按下面顺序推进：

1. **选定高频任务**：优先选择重复、低风险、产出可验证的任务，如 CI 修复、PR 评论处理、文档同步、测试补齐。
2. **定义完成标准**：把“做好了”改写成可检查条件，如测试通过、覆盖率达到阈值、告警清零、性能分数达标。
3. **整理上下文**：准备项目规则、接口文档、业务约束、历史坑点、代码结构说明，避免 Agent 盲目探索。
4. **接入工具链**：让 Agent 能访问代码、测试、CI、Issue、监控、文档和运行日志。
5. **建立验证闭环**：用测试、lint、类型检查、截图、日志、评分器、人工 review 共同确认结果。
6. **沉淀 Skills 和 Rules**：把成功经验、失败样本和检查清单写成可复用工作方法。
7. **引入目标导向 Loop**：对成功标准明确的任务使用 `/goal`，并设置最大尝试次数。
8. **引入时间驱动 Loop**：对外部状态变化任务使用 `/loop` 或 schedule，如定时检查 CI、PR、告警。
9. **逐步引入多 Agent**：只有当任务可以拆分、隔离和独立验证时，再使用 subagents 或 Team 模式。
10. **持续治理成本和质量**：定期查看 token、工具调用、失败率、人工驳回率和线上反馈。

可以概括成一条工程路径：

```text
高频任务
  → 明确目标
  → 准备上下文
  → 接入工具
  → 建立验证
  → 沉淀规则和技能
  → 小范围 Loop
  → 多 Agent / 自动化
  → 质量与成本治理
```

## 十、总结

Harness Engineering 和 Loop Engineering 的出现，说明 AI Coding 已经从“如何让模型生成更好答案”，进入“如何让 Agent 在真实工程系统里稳定工作”的阶段。

Harness 解决的是环境问题：工具、规则、验证、状态、观测、知识沉淀。Loop 解决的是自治问题：触发器、目标、停止条件、反馈迭代、长期运行。

二者的关系不是二选一，而是先后依赖：

```text
没有 Harness 的 Loop 是失控自动化
没有 Loop 的 Harness 是增强型工具箱
可靠的企业 Agent 需要二者叠加
```

一句话概括：

> Agent 工程的核心不是让模型更自由，而是把目标、上下文、能力、状态、验证和风险变成系统可管理的结构，然后在这些结构之内逐步释放自主度。
