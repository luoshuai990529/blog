# Agent 系统架构与工程化实践

> 原文：[Tw93：你不知道的 Agent：原理、架构与工程实践](https://x.com/HiTw93/status/2034627967926825175)

## 一、问题背景

Agent 的核心循环并不复杂。抽象到最小实现，它就是不断执行“读取上下文 → 让模型决策 → 调用工具 → 写回结果”的循环，直到模型不再调用工具、返回最终文本。

真正复杂的部分不在循环本身，而在循环之外：

- Agent 应该看到哪些上下文。
- 它可以调用哪些工具。
- 工具描述是否足够清楚。
- 中间状态如何保存和恢复。
- 多个 Agent 如何隔离与协作。
- 结果如何验证。
- 过程如何追踪。
- 危险动作如何被阻断。

因此，做 Agent 工程不能只盯着“换更强模型”或“写更长 Prompt”。在真实项目里，很多失败不是模型能力不足，而是 Harness、上下文、工具、记忆、评测和安全边界没有设计好。

## 二、核心结论

> [!summary] 核心判断
> Agent 的本质是一个稳定循环，但能否稳定交付，取决于循环之外的工程系统：Harness 提供验证和约束，上下文工程提供高信噪比信息，工具设计决定可行动作，记忆和状态外化支持长任务，多 Agent 依赖隔离协议，评测、追踪和安全边界决定能否进入生产。

一句话说：

```text
Agent Loop 决定系统能不能动起来
Harness 决定系统能不能跑稳
Context 决定模型能不能判断对
Tools 决定模型能不能做成事
Memory / Trace / Eval / Safety 决定系统能不能长期使用
```

## 三、Agent 在技术链路中的位置

Agent 属于 LLM 应用从“生成回答”走向“执行任务”的控制层。它把模型、上下文、工具和反馈机制连接起来，让系统可以在不确定环境中动态选择下一步动作。

可以把 Agent 系统拆成以下链路：

```text
用户目标
  → 任务定义：目标、约束、停止条件
  → 上下文装配：项目知识、历史状态、工具说明、运行环境
  → Agent Loop：感知、决策、行动、反馈
  → 工具执行：文件、Shell、浏览器、API、MCP、CI、监控
  → 验证反馈：测试、日志、评分器、人工 Review、线上信号
  → 状态沉淀：会话历史、任务进度、知识库、提交记录
  → 下一轮迭代或交付
```

这条链路里，LLM 负责推理和决策，外部系统负责状态、边界、验证和恢复。稳定的 Agent 架构不应该把所有逻辑塞进主循环，而应该把能力拆到循环外部的可治理模块中。

## 四、Agent Loop：核心循环要保持简单

Agent Loop 的基本结构是：

```text
messages = [用户输入 + 系统上下文]

while true:
  response = model(messages, tools)
  if response 是最终回答:
    return response
  tool_result = call_tool(response.tool_call)
  messages.append(response)
  messages.append(tool_result)
```

对应到行为层，就是：

```text
感知 → 决策 → 行动 → 反馈 → 再决策
```

这个循环本身不需要复杂。很多开源 Agent、官方 SDK 和 AI Coding 工具的主循环都类似，真正的差异通常来自三类外部扩展：

1. **扩展工具集和 handler**：让 Agent 能访问文件、命令、浏览器、数据库、CI、监控等能力。
2. **调整系统提示和上下文结构**：决定模型每轮看到什么规则、知识和状态。
3. **把状态外化到文件或数据库**：让长任务可恢复、可审计、可跨 session 延续。

主循环如果膨胀成一个巨大的状态机，后续会很难调试。更好的分工是：模型负责运行时推理，框架负责状态管理，工具负责确定性动作，验证系统负责判断结果。

## 五、Workflow 与 Agent 的边界

不是所有 AI 系统都应该做成 Agent。

**Workflow** 是由代码预先写死执行路径的系统，适合输入边界清楚、流程稳定、每一步都可预定义的任务。

**Agent** 是由 LLM 在运行时决定下一步动作的系统，适合路径不固定、需要动态选择工具、需要自我修正的任务。

判断方式可以很简单：

| 任务特征 | 更适合 Workflow | 更适合 Agent |
| --- | --- | --- |
| 执行路径 | 固定 | 动态 |
| 输入类型 | 可枚举 | 开放 |
| 工具选择 | 代码决定 | 模型决定 |
| 失败处理 | 预设分支 | 运行时推理 |
| 验证方式 | 明确规则 | 规则 + 反馈循环 |

很多系统打着 Agent 的名字，本质仍然是 Workflow。这不是问题。真正重要的是为任务选择合适的控制权分配方式：稳定流程交给代码，不确定决策交给模型。

## 六、五种常见控制模式

大多数 Agent 系统不是单一模式，而是几种控制模式的组合。

### 1. Prompt Chaining：提示链

把任务拆成线性步骤，每一步 LLM 处理上一步输出，中间可以插入代码检查点。

适合：先写大纲再写正文、先抽取再总结、先生成再翻译。

### 2. Routing：路由

先对输入分类，再分发到不同模型、工具或流程。

适合：客服分流、技术问题分类、简单任务走小模型、复杂任务走强模型。

### 3. Parallelization：并行

并行有两种常见形式：

- 分段法：把任务拆成多个独立子任务并发执行。
- 投票法：同一任务运行多次，通过共识或评审提高可靠性。

适合：高风险决策、多视角代码审查、大文档分块处理。

### 4. Orchestrator-Workers：编排器-工作者

中央 Agent 动态拆解任务，委派给多个子 Agent，最后汇总结果。

适合：复杂研发任务、多方案探索、代码迁移、跨模块分析。

### 5. Evaluator-Optimizer：评估器-优化器

生成器产出结果，评估器给反馈，系统循环优化直到达标。

适合：翻译、创意写作、代码质量优化、测试修复、性能优化。

这些模式可以组合使用。工程上不必执着于“完整自主 Agent”，能用简单 Workflow 解决的任务，就不应该引入不必要的自主性。

## 七、Harness：让 Agent 跑稳的外围系统

Harness 是围绕 Agent 构建的测试、验证与约束基础设施。它至少包括四类能力：

- **验收基线**：什么算完成，什么算失败。
- **执行边界**：哪些文件、命令、环境、权限可以使用。
- **反馈信号**：测试、日志、监控、截图、评分器、人工反馈。
- **回退手段**：撤销、回滚、重试、隔离分支、人工接管。

模型当然重要，但在高可验证任务里，Harness 对成功率的影响往往更大。因为 Agent 真正需要的不是“自由发挥”，而是在清晰目标和自动反馈下不断修正。

最适合 Agent 的任务通常同时满足两个条件：

```text
目标明确 + 结果可自动验证
```

如果目标明确但必须靠人验收，吞吐量会卡在人工 Review 上；如果有自动反馈但目标模糊，系统会高效地往错误方向跑；如果两者都没有，Agent 基本无法稳定发挥。

Harness 的目标就是把任务推向“目标明确、可自动验证”的区域。

## 八、上下文工程：稳定性来自高信噪比

Agent 失败经常不是因为上下文不够长，而是因为上下文太吵。

无关内容占据大量窗口后，关键信号会被稀释，模型决策质量下降。这类问题可以理解为 Context Rot：系统给了模型更多信息，但真正有用的信息更难被注意到。

### 1. 上下文要分层

推荐按稳定性和使用频率分层：

| 层级 | 内容 | 原则 |
| --- | --- | --- |
| 常驻层 | 身份、硬约束、项目契约、禁止事项 | 短、硬、稳定、每轮都需要 |
| 按需加载层 | Skills、领域知识、专项文档 | 描述符常驻，正文触发时加载 |
| 运行时注入层 | 当前时间、用户偏好、环境状态 | 每轮按需拼入，不污染长期上下文 |
| 记忆层 | 跨会话经验、历史决策 | 存文件或数据库，需要时检索 |
| 系统层 | Hooks、Linter、CI、权限控制 | 确定性逻辑不进上下文 |

凡是可以通过代码、Hooks、CI、权限系统表达的确定性约束，都不应该反复写进 Prompt 里让模型“记住”。

### 2. 压缩要保留决策

上下文压缩不是越短越好。最容易丢的往往不是废话，而是早期决策的理由、失败路径和关键约束。

压缩时应优先保留：

1. 架构决策和原因。
2. 已修改文件和关键变更。
3. 验证状态：哪些通过，哪些失败。
4. 未完成任务、风险、回滚笔记。
5. 必须原样保留的标识符：URL、文件名、hash、PR 编号、端口、UUID。

工具输出可以摘要，但验证结论和决策依据不能丢。

### 3. 文件系统适合作为上下文接口

大量工具结果不适合直接塞进模型上下文。更好的方式是先落盘，再让 Agent 通过搜索、脚本或读取片段按需使用。

```text
工具写入文件
  → Agent 只读取必要片段
  → 历史结果可追踪
  → 开发者可直接查看
  → 压缩后仍可回溯原始材料
```

文件系统让上下文从“一次性输入”变成“可检索状态”，尤其适合长任务、大日志、大 JSON、大型代码搜索结果。

### 4. Prompt Caching 会反向影响架构

Prompt Caching 依赖精确前缀匹配。稳定的系统提示、工具定义和高频规则放在前面，有利于缓存命中；动态内容、工具结果、用户输入放在后面，避免破坏前缀。

这也是为什么常驻层要短而稳定，Skills 要按需加载，工具定义不要频繁变动。

## 九、Skills：把知识做成按需加载的方法

Skill 本质上不是文档合集，而是 Agent 的路由条件和操作方法。

一个好 Skill 至少要说明：

- 什么时候应该使用。
- 什么时候不应该使用。
- 输入是什么。
- 输出是什么。
- 验证标准是什么。
- 有哪些反例或边界。

Skill 描述太长，会增加常驻上下文成本；描述太泛，会导致误触发。真正有效的描述不是“我能做什么”，而是“什么情况下该用我”。

常见反模式：

1. 一个 Skill 覆盖 review、deploy、debug、incident 等多个不同任务。
2. 把几百行手册塞进 Skill 正文，而不是拆成 supporting files。
3. 有副作用的 Skill 没有限制调用时机和速率。
4. Skill 描述像功能介绍，不像路由条件。

Skills 应该和上下文分层配合：高频方法保留短描述，完整材料按需读取，低频知识直接放文档，不必强行做成 Skill。

## 十、工具设计：按 Agent 目标设计，而不是照搬 API

上下文决定模型能看到什么，工具决定模型能做什么。

很多工具调用失败，不是模型不会选，而是工具本身的设计视角错了：它是给工程师看的 API，不是给 Agent 用的操作界面。

### 1. 工具设计的三个阶段

**第一代：API 封装**

每个 API endpoint 对应一个工具，粒度过细，Agent 需要自己协调多个底层接口，容易选错和漏步骤。

**第二代：ACI，Agent-Computer Interface**

工具面向 Agent 的目标，而不是底层 API 操作。例如不要暴露 `create_file`、`write_content`、`set_permission` 三个工具，而是提供一个 `create_script(path, content, executable)`。

**第三代：Advanced Tool Use**

进一步优化工具发现和调用方式：

- Tool Search：按需发现工具，不把全部工具定义塞进上下文。
- Programmatic Tool Calling：用代码编排多个工具调用，中间结果不进 LLM 上下文。
- Tool Use Examples：给工具附带真实调用示例，提高调用准确率。

### 2. ACI 工具设计原则

一个适合 Agent 的工具应该满足：

- 名称表达任务目标，而不是底层接口名。
- 参数有语义，能减少误填。
- 描述包含使用边界和反例。
- 返回值只保留下一步需要的信息。
- 错误信息结构化，并给出修正建议。
- 工具定义和实现保持一致，避免文档漂移。

调试 Agent 选错工具时，应先检查工具描述、参数边界、返回值和错误提示，而不是第一时间怀疑模型能力。

### 3. 工具消息要隔离

框架内部事件不应该全部暴露给 LLM。例如压缩发生、通知推送、工具调用被跳过，这些事件需要保存在会话历史里，但不一定要进入模型上下文。

更合理的做法是区分：

- **框架消息**：保存完整内部状态，供系统恢复和审计。
- **LLM 消息**：只保留模型理解任务所需的 user、assistant、tool_result。

这样可以减少 token 噪声，也避免模型被内部实现细节干扰。

## 十一、记忆系统：让 Agent 跨会话保持连续性

Agent 没有天然时间连续性。一次会话结束后，上下文会清空；下一次启动时，如果没有外部记忆，它并不知道之前发生了什么。

记忆应按解决的问题分类：

| 记忆类型 | 位置 | 作用 |
| --- | --- | --- |
| 工作记忆 | 当前上下文窗口 | 保存当前任务最小必要信息 |
| 程序性记忆 | Skills | 保存“如何做某件事” |
| 情景记忆 | JSONL 会话历史、日志 | 保存发生过什么 |
| 语义记忆 | MEMORY.md、知识库 | 保存跨会话需要复用的事实和偏好 |

记忆系统的关键不是“什么都存”，而是能被检索、能被验证、能被淘汰。

长期记忆尤其要避免污染：过期规则、错误结论、临时偏好如果被永久注入系统提示，会让 Agent 在未来任务里持续犯错。

## 十二、状态外化与长任务恢复

提高 Agent 自主度的前提是状态外化。

长任务不应该依赖模型“记住自己做到哪里”。任务进度、待办列表、验证状态、失败记录、提交记录、分支状态，都应该写入文件、数据库或 Git。

推荐长任务流程：

```text
Initializer Agent
  → 建立任务状态文件
  → 拆分可验证子任务
  → 标记验收标准

Coding Agent 每轮执行
  → 读取当前状态
  → 完成一个子任务
  → 运行验证
  → 更新状态
  → 提交或记录变更
  → 安全退出
```

这样即使 session 中断、上下文压缩或模型切换，后续 Agent 也能恢复现场。

慢速 I/O 也不应阻塞主循环。后台任务、长时间测试、外部服务调用可以通过通知队列或状态文件把结果注入下一轮，而不是把 Agent Loop 改成复杂的异步状态机。

## 十三、多 Agent：核心是隔离和协议，不是并行数量

多 Agent 的价值不是“同时多开几个模型”，而是通过隔离上下文、角色和工作区，降低单个上下文膨胀和思路固化的问题。

多 Agent 系统至少需要设计：

- **任务图**：谁负责什么，依赖关系是什么。
- **角色边界**：研究、实现、评审、测试、总结分别由谁做。
- **权限边界**：哪些 Agent 只能读，哪些可以写，哪些可以执行命令。
- **工作区隔离**：并行方案最好在独立分支或 worktree 中完成。
- **回传协议**：子 Agent 回传结构化摘要，不把全部上下文塞回主 Agent。
- **独立验证**：评审 Agent 不能沿用实现 Agent 的上下文偏见。

多 Agent 会放大错误共识。一个错误假设如果被多个 Agent 反复引用，系统会显得更自信，但不一定更正确。因此必须引入测试、编译器、独立评审或人工检查打断错误传播。

## 十四、评测与验证：同时看过程和结果

Agent 评测不能只看最终答案，也不能只看执行轨迹。

需要同时看两类信号：

- **Transcript**：Agent 如何思考、选工具、调用工具、处理错误。
- **Outcome**：环境最终状态是否正确，比如代码是否通过测试、文件是否生成、线上指标是否恢复。

常见指标：

- **Pass@k**：多次尝试里至少成功一次，衡量能力上限。
- **Pass^k**：连续多次都成功，衡量稳定性。
- **人工驳回率**：最终结果被人工退回的比例。
- **工具失败率**：工具调用报错、参数错误、权限错误比例。
- **恢复成功率**：任务中断后能否继续。
- **成本指标**：token、工具调用次数、运行时间。

看到分数下降时，不要只改 Agent。评测环境、评分器、资源限制、测试数据、聚合方式都可能有问题。评测系统本身如果不可信，基于它优化 Agent 只会越改越偏。

## 十五、Trace 与可观测性

Trace 是排查 Agent 的前提。

生产级 Agent 至少应该记录：

- 每轮模型输入和输出摘要。
- 工具开始、工具结束、工具错误。
- 工具参数和关键返回值。
- 上下文压缩事件。
- 任务状态变化。
- 验证命令和验证结果。
- 人工确认和拒绝。
- token 与运行耗时。

Trace 不应该只服务调试，也应该服务在线评测、人工审查、成本分析和安全审计。

在线评测可以按风险采样：

- 用户负反馈。
- 高 token 消耗。
- 工具连续失败。
- 权限敏感操作。
- 模型、Prompt、工具定义变更后的流量。
- 固定时间窗口内的随机样本。

## 十六、安全：目标不是识别所有攻击，而是阻断危险动作

Agent 安全设计不能只依赖模型识别风险。更可靠的目标是：即使模型被误导，危险动作也无法直接发生。

关键做法：

1. **不可信边界标记**：网页、用户输入、Issue 评论、邮件、日志都应默认不可信。
2. **最小权限**：Agent 只获得完成任务所需的最小文件、命令、API 权限。
3. **敏感操作确认**：删除、支付、生产变更、权限修改、外发数据需要人工确认。
4. **工具级防护**：危险参数、路径、命令在工具层拦截，而不是只靠 Prompt 禁止。
5. **独立复核**：高风险路径引入另一个模型或规则系统复核。
6. **可回滚**：变更必须能撤销，失败必须能恢复。

安全边界应尽量写进系统和工具，而不是写成“请不要做危险事”。

## 十七、OpenClaw 带来的架构启示

OpenClaw 的价值不在于发明了一个更复杂的 Agent Loop，而在于把大量工程细节落到了可运行系统里。

可以沉淀出几个启示：

1. **消息要解耦**：框架内部消息和 LLM 可见消息分开。
2. **状态要外化**：长任务状态不能只放在上下文窗口里。
3. **提示要分层**：常驻规则短而稳定，知识按需加载。
4. **记忆要可恢复**：压缩和归档不能让历史完全不可追溯。
5. **工具要面向 Agent 目标设计**：不要机械封装底层 API。
6. **评测和 Trace 要先行**：没有观测，就没有可靠调试。
7. **安全边界要系统化**：靠权限、工具和流程阻断危险动作。

这些都是 Agent 从 Demo 走向生产时必须补齐的工程能力。

## 十八、推荐落地路径

落地 Agent 系统可以按下面顺序推进：

1. **先区分 Workflow 和 Agent**：固定流程先用 Workflow，不要为了概念强行 Agent 化。
2. **定义任务成功标准**：把“做好了”变成测试、指标、检查项或人工验收表。
3. **建设 Harness**：补齐执行边界、验证信号、回退机制和权限控制。
4. **治理上下文**：分层加载、减少噪声、把大结果落盘、明确压缩保留优先级。
5. **重构工具设计**：从 API 封装转向 ACI，减少工具数量，提升描述和错误反馈质量。
6. **引入 Skills**：把可复用方法做成按需加载的工作流，而不是长文档常驻。
7. **外化状态和记忆**：让长任务可恢复，让历史经验可检索、可更新、可淘汰。
8. **再引入多 Agent**：先有隔离、协议和验证，再并行探索。
9. **建设评测与 Trace**：同时看过程和结果，用真实失败样本反哺系统。
10. **最后扩大自主度**：只有当目标、工具、验证和安全边界稳定后，才适合引入更长周期的自动化和主动触发。

一条简化路线是：

```text
Workflow / Agent 边界判断
  → 成功标准
  → Harness
  → 上下文分层
  → ACI 工具
  → Skills
  → 状态外化
  → 多 Agent
  → Eval / Trace / Safety
  → 生产级自主循环
```

## 十九、工程落地中的坑

### 1. 把 Agent Loop 写复杂

主循环越复杂，越难判断问题来自模型、工具、状态还是框架。新增能力优先放在工具、上下文、状态和验证层，不要不断改主循环。

### 2. 用长 Prompt 代替工程约束

模型会忘、会误解、会被上下文噪声干扰。关键约束应该进入 Linter、CI、Hooks、权限系统和工具参数校验。

### 3. 工具越接越多

工具定义会消耗上下文，也会稀释注意力。工具应该少而准，面向 Agent 目标设计，能用 Shell、脚本或 Skill 解决的，不一定要包装成 MCP 工具。

### 4. 压缩丢掉关键决策

摘要如果只保留“做了什么”，不保留“为什么这么做”和“哪些验证失败过”，后续 Agent 会重复踩坑。

### 5. 多 Agent 没有隔离

多个 Agent 共享同一上下文、同一工作区、同一错误假设时，只会放大混乱。多 Agent 的前提是协议和隔离。

### 6. 评测系统不可信

如果评分器、测试环境或数据集有问题，Agent 优化会被错误信号牵引。看到分数波动，先验证评测系统本身。

### 7. 安全只靠提示词

Prompt 注入、恶意网页、Issue 评论和日志内容都可能诱导 Agent。安全要靠权限、工具拦截、人工确认和审计。

## 二十一、最终沉淀

Agent 工程的重点不是把模型放得更自由，而是先把目标、上下文、工具、状态、反馈和风险都变成系统可管理的结构。

Agent Loop 只是发动机。要让系统进入生产，需要 Harness 提供护栏和验证，上下文工程提供高质量信息，工具设计提供可靠动作，记忆和状态外化提供连续性，多 Agent 协议提供协作边界，Eval、Trace 和 Safety 提供长期治理能力。

一句话总结：

> 可用的 Agent 靠模型能力启动，可靠的 Agent 靠工程系统收敛。
