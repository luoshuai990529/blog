# 从 Claude Code 源码学习 Agent 安全治理：权限策略、命令解析与沙箱边界

## 一、问题背景：给 Agent 工具，不等于给它无限执行权

AI Coding Agent 的危险不来自模型会不会输出某条命令，而来自命令会在真实机器、真实仓库和真实凭证环境中执行。一个看似普通的 `git`、`npm` 或 `curl` 调用，可能组合重定向、环境变量、管道、子进程和目录切换，最终写入不该写的路径或泄露敏感数据。

因此，安全治理不能只在提示词里写“请谨慎”。Claude Code 在 `src/utils/permissions/permissions.ts`、`src/tools/BashTool/bashPermissions.ts`、`readOnlyValidation.ts`、`shouldUseSandbox.ts` 和交互式权限处理器中，将安全判断做成了执行前的多层决策链。

## 二、核心结论

> [!summary] 核心判断
> Agent 安全的关键不是把工具一律禁掉，而是让每次高风险动作都经过“规则匹配 → 语义分析 → 隔离执行或人工审批 → 结果审计”的最小权限链路；自然语言约束只负责引导，确定性机制才负责兜底。

## 三、它在 Agent 技术链路中的位置

```text
模型生成工具调用
  → 输入校验
  → 静态拒绝规则与允许规则
  → 命令解析、只读判定与风险识别
  → 沙箱判定 / 人工审批 / 自动放行
  → 受限执行
  → 审计、持久化授权与错误反馈
```

安全模块位于工具运行时之前，并贯穿执行全程。它既是模型行为的边界，也是用户能理解、修改和撤销的授权系统。

## 四、Claude Code 的安全治理拆分

### 1. 权限策略：拒绝优先，按作用域匹配

权限系统把规则分为允许（allow）、询问（ask）和拒绝（deny）等行为，并可按工具名、命令前缀或具体输入内容匹配。工具注册阶段还会预先过滤被整体拒绝的工具，避免模型看到一个理论上永远不能使用的能力。

一个稳妥的判定顺序应是：

```text
显式拒绝
  → 显式允许
  → 是否可证明为低风险只读操作
  → 是否可在沙箱中执行
  → 请求用户批准
  → 默认拒绝或返回可解释的限制
```

规则的目标不是让模型绕过确认，而是把用户已明确同意的安全重复操作变成低摩擦流程。

### 2. 命令解析：不能只靠字符串黑名单

`BashTool` 中专门处理复合命令、管道、环境变量、包装器、目录切换、重定向和 Git 相关路径。这说明“包含 rm 就拒绝、包含 git status 就允许”的字符串匹配是不可靠的。

例如，同一个 `git` 命令在不同工作目录、不同仓库形态下的风险不同；`cd` 与后续命令组成的复合语句也会改变校验基准。源码对无法解析的情况采取保守策略：不能证明安全，就转入更严格的权限检查。

工程上应尽量把 Shell 语句解析为命令片段和参数，而不是依赖正则。对无法完整解析的 shell 语法，宁可要求批准，也不要自动放行。

### 3. 只读验证：只放行可证明无副作用的操作

`readOnlyValidation.ts` 使用严格允许列表识别可自动执行的只读命令，并额外防范 Git 内部目录、路径跳转和复合命令造成的逃逸。这里的思想是：

> “看上去像读取”不够；只有能证明不会写入、不会联网产生副作用、不会越过允许路径的调用，才是只读。

只读判断既能减少无意义的确认，也能成为工具并发的安全前提。它不能取代通用权限系统，因为很多安全命令仍需根据项目策略判断。

### 4. 沙箱：限制爆炸半径，而不是宣布绝对安全

`shouldUseSandbox.ts` 负责判断命令是否适合进入沙箱。沙箱应限制文件写入范围、网络访问、进程能力和凭证可见性，使未知或中等风险动作的损害范围可控。

但沙箱不是授权的替代品：有些命令无法在沙箱运行，有些副作用在沙箱外部仍然存在，配置错误本身也可能造成逃逸。因此需要“策略决定是否允许，沙箱决定允许后能影响多大范围”的双层模型。

### 5. 人工审批与多通道决策

交互式权限处理器把本地终端、远程界面和其他连接通道的批准结果汇入一个只决议一次的上下文。用户拒绝后，拒绝原因会作为工具结果回到模型，而不是让模型以为调用凭空消失。

成熟的审批界面至少应说明：动作、参数、影响范围、风险原因、可选的单次或持久化授权，以及拒绝后的替代建议。复杂风险可以借助模型生成解释，但最终允许/拒绝必须由确定性策略和用户授权决定。

## 五、分阶段实践

### 1. 第一阶段：先定义能力边界

按读取、写入、本地进程、网络、凭证、部署和删除等能力划分工具；默认最小权限，不要从“全部可执行”再补黑名单。

### 2. 第二阶段：建立规则与审批链

实现允许（allow）/询问（ask）/拒绝（deny）规则，支持项目级和用户级作用域。对每次请求记录匹配到的规则和最终决策，保证出现误放行时可追溯。

### 3. 第三阶段：强化 Shell 语义分析

对命令做分段解析，识别 `&&`、`||`、管道、重定向、子命令、环境变量和当前工作目录（cwd）改变。无法理解时走审批，而非尝试“智能猜测”。

### 4. 第四阶段：引入沙箱和纵深防御

为沙箱定义可写目录、网络策略、可执行文件和资源上限；再用文件路径校验、凭证隔离、审计日志和紧急停用开关叠加防护。

## 六、工程落地中的坑

1. **只用提示词约束危险操作。** 模型会遗忘、误解或被上下文干扰；安全边界必须在执行层实现。
2. **只靠命令关键词黑名单。** Shell 的组合能力使这种方案很容易被绕过，且会误伤正常操作。
3. **把沙箱当成万能开关。** 沙箱配置、网络、挂载目录和外部服务都可能扩大风险；仍应保留审批和最小权限。
4. **允许规则过宽。** 将整类解释器、包管理器或 Shell 前缀永久放行，通常等价于放弃后续参数约束。
5. **没有拒绝后的反馈。** 模型不知道为何被拒绝就容易重复尝试；应返回具体边界和安全替代路径。

## 七、推荐落地路径

1. 先列出工具能力矩阵和默认拒绝策略。
2. 实现显式允许（allow）/询问（ask）/拒绝（deny）与审计日志。
3. 为文件路径和命令前缀增加严格解析与匹配。
4. 仅对可证明安全的读取操作做自动放行与并发。
5. 将未知或中风险命令放入受限沙箱。
6. 最后补齐远程审批、策略同步、紧急停用和安全回归用例。

## 九、最终沉淀

Agent 安全不是限制模型“能不能思考”，而是限制它“能以什么权限影响真实世界”。当规则、解析、沙箱、审批和审计形成闭环后，Agent 才能在获得足够行动能力的同时保持可控。

一句话总结：

> 安全的 Agent 不是拥有最少工具的 Agent，而是每次工具执行都能证明其权限、范围和后果的 Agent。
