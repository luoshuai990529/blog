# 从 Claude Code 源码学习 Multi-Agent 工程：子 Agent、Teammate、Coordinator 与任务协议

## 一、问题背景：多 Agent 的难点不在“多开几个模型”

单 Agent 面对大型工程任务时，探索、设计、修改和验证会争夺同一个上下文窗口。将任务交给多个 Agent 可以隔离上下文、缩短独立调研的等待时间，但也会立即带来共享状态、权限继承、文件冲突、结果回收和取消传播等系统问题。

Claude Code 的源码并未把多 Agent 当成一条简单的“调用模型”路径，而是拆为 Agent 工具、任务运行时、团队状态和协调者模式：`src/tools/AgentTool/` 负责派生与运行，`src/tasks/` 负责生命周期，`src/utils/swarm/` 负责团队通信，`src/coordinator/coordinatorMode.ts` 负责领导者的工作协议。

## 二、核心结论

> [!summary] 核心判断
> Multi-Agent 的本质是任务运行时，不是提示词技巧：每个工作者必须拥有明确的任务边界、上下文与权限快照、可取消的生命周期和结构化回报；协调者负责分解、整合和最终验证，而不是把所有工作再做一遍。

## 三、它在 Agent 技术链路中的位置

```text
复杂任务
  → 判断是否可分解为独立子问题
  → 创建任务与工作者上下文
  → 并行研究 / 串行修改 / 独立验证
  → 通过消息与任务状态回传
  → 协调者整合结论、处理冲突、执行最终验证
  → 关闭或恢复团队任务
```

多 Agent 处于 Agent 的规划、工具执行和状态治理三者交界处。没有任务协议，多 Agent 只会把单 Agent 的不确定性放大为并发的不确定性。

## 四、Claude Code 的多 Agent 模块拆分

### 1. 子 Agent：带隔离上下文的专门任务

`AgentTool/runAgent.ts` 会为子 Agent 创建独立的消息链、取消控制器、文件读取缓存和会话日志侧链（sidechain）。子 Agent 可以继承必要的项目上下文、工具和模型配置，也可以按 Agent 定义增加专属模型上下文协议（MCP）服务或工具集合。

这意味着子 Agent 的价值首先是**隔离**：主 Agent 不必把大量探索细节放进自己的活跃上下文，只接收对后续决策有用的结论。并行只是隔离带来的可选收益。

### 2. 任务运行时：把会话变成可管理的实体

`src/tasks/` 将主会话、本地后台 Agent、进程内团队成员（teammate）、命令行（Shell）任务和远程 Agent 表示为不同任务类型。每个任务都应至少有：

| 状态 | 作用 |
|---|---|
| 身份与父子关系 | 将结果、取消和权限归属到正确任务 |
| 生命周期 | waiting、running、completed、failed、killed 等状态转换 |
| 取消控制器 | 停止当前轮，或停止整个工作者 |
| 消息队列与进度 | 支持用户/协调者继续投递任务与观察过程 |
| 结果与错误 | 让上层按结构处理，而非解析终端文本 |

这一层让 Agent 不再只是一次 API 调用，而成为可以后台化、前台化、取消和恢复的长期任务。

### 3. 团队成员（Teammate）：可持续协作的工作者

源码区分一次性后台子 Agent 与进程内 teammate。后者拥有身份、团队名、独立权限模式、待处理消息队列和对话历史，可以在完成一个回合后继续接收后续消息。

因此，适合把“短暂研究”交给一次性子 Agent，把“持续负责某个模块、等待反馈后再修改”的工作交给 teammate。不要为了并行而创建长期 teammate；只有任务确实需要多轮协作时，持续身份才值得其状态成本。

### 4. 协调者（Coordinator）：分工与整合，而不是万能执行者

协调者模式在系统提示中明确划分研究、综合、实现、验证的责任：工作者承担独立调查和定向操作；协调者读取结果、制定可执行规格、处理依赖与冲突、面向用户汇报。

它还强调两条工程纪律：

- 研究任务可广泛并行，写入同一文件区域的实现应串行或隔离到工作树；
- 已完成的工作者应通过继续消息复用其加载的上下文，而不是每次新建一个 Agent。

真正的协调不是把任务广播出去，而是根据依赖图安排“何时并行、何时汇合、谁有最终决策权”。

### 5. 协同协议：任务通知、结构化结果与共享工件

协调者接收的并不是自然语言聊天，而是带任务标识、状态、摘要、结果、用量的任务通知。团队还可以通过消息工具、任务状态和受控的共享暂存目录交换信息。

建议将回报固定为：目标、结论、证据、影响文件、已验证项、未验证项、风险与建议下一步。这样主 Agent 才能压缩和整合结果，而不是重新阅读完整过程。

## 五、分阶段实践

### 1. 第一阶段：先做好单 Agent 任务状态

在引入并发前，实现任务标识、状态机、取消、超时、结果和日志。没有这层，子 Agent 失败后难以定位，更无法可靠恢复。

### 2. 第二阶段：引入一次性子 Agent

只用于边界清晰、主要读取、结果可独立消费的任务，例如代码库探索、方案比较、测试失败定位。要求结构化回报，主 Agent 负责综合。

### 3. 第三阶段：引入团队与协调者

为长期协作增加身份、消息队列、权限模式和任务依赖；用协调者控制并发上限、文件所有权和阶段门禁。

### 4. 第四阶段：引入共享工件与恢复

将计划、接口约定、验证报告等写为可审计工件；将团队拓扑、任务状态和侧链日志纳入会话恢复，避免重启后“谁在做什么”丢失。

## 六、工程落地中的坑

1. **把子 Agent 当成更便宜的并行线程。** 每个 Agent 都有上下文、模型调用和协调成本；小任务直接由主 Agent 完成通常更快。
2. **没有文件所有权。** 多个 Agent 同时编辑同一片区域会产生冲突和互相覆盖；写操作应按文件或工作树隔离。
3. **只收集自然语言结论。** 缺少证据、验证状态和风险字段，协调者无法判断结果是否可用。
4. **权限无限继承。** 子 Agent 的目标通常更窄，应继承最小必要工具和目录访问，而不是默认拥有主 Agent 的全部能力。
5. **协调者既分派又逐步微操。** 这会抵消并行收益；应在任务边界、验收条件和阻塞点介入。

## 七、推荐落地路径

1. 建立统一任务对象与状态机。
2. 增加一次性子 Agent，限定为只读探索和结构化回报。
3. 为每个任务增加父子关系、取消传播、超时和日志侧链。
4. 引入协调者，按任务依赖和写入范围控制并发。
5. 对长期协作增加 teammate、消息队列、共享工件和独立权限。
6. 将团队状态接入会话恢复、预算控制和最终验证流程。

## 九、最终沉淀

多 Agent 系统的生产力来自“把复杂任务拆成可独立验证的工作单元”，而不是同时运行更多模型。清晰的任务协议、受限的共享状态、可靠的取消与结构化回报，才使协调者能够把并行结果重新组合成一个可信的工程交付。

一句话总结：

> Multi-Agent 的关键不是并发数量，而是任务边界、状态协议与最终整合责任是否清晰。
