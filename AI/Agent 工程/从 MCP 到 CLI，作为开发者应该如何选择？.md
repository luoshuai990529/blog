# 从 MCP 到 CLI，作为开发者应该如何选择？

给 Agent 接工具，最容易犯的错是先问“该用 MCP 还是 CLI”。

更好的问题是：**这个能力该以什么方式被发现、被说明、被执行和被约束？**

MCP、CLI 和 Skill 分别擅长不同的一段。它们不是替代关系，更像一套分层：Skill 负责告诉 Agent 怎么做，CLI 或 MCP 负责把事情做完。

> [!summary] 先说结论
> - 本地、标准、组合性强的任务，优先 CLI。
> - 跨系统、需要身份隔离、多人复用和审计的能力，优先 MCP。
> - 工具多、流程复杂时，用 Skill 收起复杂度；不要把几十个工具平铺给 Agent。
> - 最常见的成熟方案不是二选一，而是 **Skill + CLI + MCP**。

## 一、先理解 MCP：它解决的是“怎么连接”

MCP（Model Context Protocol）是 AI 应用连接外部数据和服务的开放协议。它把能力统一成三类：

- **Tools**：可执行的动作，例如查询订单、创建工单、发送消息。
- **Resources**：可读取的上下文，例如文档、配置、报告和数据详情。
- **Prompts**：可复用的提示模板或工作流入口。

它的价值不在于“让模型更聪明”，而在于让一个能力可以被不同 Host / Agent 以相同方式发现、调用和治理。一个团队把内部工单系统做成 MCP Server 后，不必为每个 Agent 框架重复接一遍。

### MCP 不解决什么

MCP 解决工具连接，不解决 Agent 的注意力。

把 100 个 MCP Tool 一次性暴露给 Agent，不会让它更强，只会让它更难选择：相近的名字、复杂的参数和冗长的 Schema 都会占用上下文，并提高误调用概率。MCP 的标准化接入，不能替代工具分组、权限控制、流程设计和评测。

### 最新规范值得关注的变化

[2026-07-28 规范发布](https://blog.modelcontextprotocol.io/posts/2026-07-28/)将 MCP 核心改为无状态的请求/响应模型。对开发者最重要的是：

- 不再依赖初始化握手、`Mcp-Session-Id` 或粘性会话；任一请求都可由任一实例处理，更适合普通负载均衡和弹性扩缩容。
- `Mcp-Method` 与 `Mcp-Name` 进入 HTTP Header，网关可以按方法和 Tool 路由、限流和审计。
- 工具、资源和提示词列表支持缓存提示和稳定排序，减少重复拉取与上下文波动。
- MRTR（多轮往返请求）支持工具在执行中补问用户、请求确认，而不要求长期保持双向连接。
- Tasks 成为正式扩展，适合导出、批处理等长耗时任务；OAuth 授权强化了 issuer 校验，并逐步从 DCR 转向 CIMD。

这些变化让 MCP 更适合作为生产级服务接口，但没有改变它的基本定位：**它是一条受控的集成通道，不是 Agent 的万能工具箱。**

## 二、CLI：AI 最熟悉的执行接口

CLI（命令行接口）就是在终端运行命令：`git`、`rg`、`ffmpeg`、`curl`，或你写的脚本。

对人而言，CLI 是黑色窗口；对 Agent 而言，它是天然的文本接口。模型训练数据中已有大量常用命令、错误信息和排障经验，因此在代码、文件、Git、构建和脚本任务上，CLI 往往不需要额外注入很大的工具 Schema。

CLI 还有一个 MCP 不容易替代的特点：**组合**。

```bash
rg -l 'deprecated_api' src | xargs sed -n '1,20p'
```

Shell 管道把一个命令的输出交给下一个命令。对“找文件 → 过滤 → 转换 → 执行”这类本地任务，CLI 既短又灵活。

### 传统 CLI 与 AI 原生 CLI

传统 CLI 是为人设计的：彩色输出、交互式菜单、默认输出大量信息。这些对 Agent 并不友好。

AI 原生 CLI 应当具备以下特征：

| 设计点 | 为什么重要 |
| --- | --- |
| 非交互模式 | 所有信息可通过参数传入，避免菜单或确认提示让 Agent 卡住。 |
| 结构化输出 | 支持 JSON，必要时支持只返回指定字段，避免把无关内容塞进上下文。 |
| 可预览 | 对写操作提供 `--dry-run`、`--yes` / `--non-interactive` 等明确语义。 |
| 可自查 | `--help`、子命令帮助和版本信息清楚，让 Agent 能按需学习。 |
| 稳定退出码 | 成功、参数错误、权限错误、临时失败可被程序可靠区分。 |

新工具还应提供简短的 Skill：不是把整本手册塞给模型，而是告诉它“何时用、常用命令、参数约束、风险动作和输出怎么读”。

## 三、Skill：不是第三种执行器，而是说明书和路由层

Skill 通常是一份 Markdown 形式的操作说明。它可以包含任务边界、步骤、示例、注意事项，以及对 CLI 或 MCP 的调用方式。

可以把三者理解为：

```text
用户目标
   ↓
Skill：这类任务该怎么做、先用哪个能力、哪些操作需要确认
   ↓
CLI：本地文件、代码、脚本、标准命令
MCP：远程 SaaS、内部服务、受控数据与业务动作
```

Skill 的作用是让 Agent 按需加载正确的说明和少量能力。它能减少“工具全量暴露”带来的噪音，也能把复杂的多步操作固化成可复用 SOP。

但 Skill 不提供权限边界。它可以建议“先预览再删除”，真正阻止误删的仍然是 CLI 的权限控制、Host 的审批和 MCP Server 的服务端授权。

## 四、CLI 与 MCP：差别不在于谁更先进

| 维度 | CLI | MCP |
| --- | --- | --- |
| 本质 | 在本机或容器中执行命令 | 通过标准协议调用外部能力 |
| 最适合 | 代码、文件、构建、脚本、成熟开发工具 | SaaS、内部服务、跨 Agent 共享能力、受控业务动作 |
| 上下文成本 | 常用命令的先验多，按需读帮助即可 | Tool 描述和 Schema 需要被发现与理解；工具过多会变重 |
| 组合能力 | Shell 管道非常强 | 更适合边界清晰的业务操作；复杂编排应由服务或 Skill 承担 |
| 身份与审计 | 依赖本机账号、Shell 环境和沙箱 | 可集中做 OAuth、scope、租户隔离、审计和限流 |
| 分发范围 | 同一环境安装后即可使用 | 适合跨机器、跨团队、跨 Agent 的标准接入 |
| 调试体验 | 最好：人可复现同一条命令 | 需要查看请求、日志、鉴权和服务状态 |

### CLI 的优点与代价

CLI 的优点是快、轻、可组合、可手工复现。已有 CLI 的能力，不要为了“架构统一”马上包成 MCP。许多本地任务直接调用 `git`、`rg`、`ffmpeg`、`docker` 就够了。

CLI 的代价是权限粗。Agent 进入 Shell 后，往往同时接近文件、环境变量、凭据和网络；一个不可信 CLI 也可能读取本机敏感信息或执行破坏性操作。它还受制于安装、依赖、PATH、操作系统差异和进程开销。

所以 CLI 适合放在受控 Workspace 或沙箱中：最小文件范围、最小网络权限、敏感目录隔离、写操作预览和用户确认。不要把“Agent 会谨慎”当成安全机制。

### MCP 的优点与代价

MCP 的优点是边界清晰。Remote MCP 更像一次受身份控制的服务调用：Server 可以只暴露必要的业务动作，按用户、租户和 scope 授权，并记录审计日志。它天然适合 Gmail、飞书、Stripe、工单系统和内部数据服务这类跨系统能力。

MCP 的代价是要维护服务、契约、认证、版本和可观测性。Tool 太多时，发现与 Schema 也会消耗上下文；Tool 描述只是声明，不是安全保证。Server 仍必须在服务端验证身份、对象权限和幂等性。

> [!warning] 不要把 CLI 和 MCP 简化为“开发用 CLI，生产用 MCP”
> 本地生产型 Coding Agent 仍会大量依赖 CLI；一个一次性的企业写操作即使调用频率很低，也可能更应使用 MCP。决定因素是能力边界与风险，而不是环境标签。

## 五、开发者应该如何选择？

按下面顺序判断，通常就足够了。

### 1. 这是本地任务，还是跨系统能力？

- 读写仓库、搜索文件、运行测试、处理媒体、调用成熟开发工具：先选 CLI。
- 访问 SaaS、内部系统、共享数据库或代表用户产生业务影响：先选 MCP。

### 2. 能力是否需要被多个 Agent 或用户复用？

- 只在一个开发环境使用：CLI 成本最低。
- 需要让多个 Host、团队或外部 Agent 使用：MCP 提供更好的标准接口和治理入口。

### 3. 能否接受本机权限？

- 如果能力必须读取当前仓库、执行构建、操作本地产物，CLI 很自然，但要配沙箱。
- 如果只需调用远程服务，不要为了方便强行塞进 Bash；Remote MCP 通常有更干净的权限和数据边界。

### 4. Agent 是否已经“看得太多”？

- 工具、技能和历史越来越多时，问题不是再加一个协议，而是做分组和按需加载。
- 将同一任务域的 Skill、CLI 和 MCP 放入同一个 Workspace；只在进入该 Workspace 后暴露相应能力。

### 一个实用的落地路径

1. 先把底层能力做成可手动运行、可测试的 CLI 或库。
2. 为 Agent 写一份小而准的 Skill，定义何时调用、常用参数和安全边界。
3. 当它需要跨环境共享、统一认证或严格审计时，再将稳定能力封装为 MCP。
4. 保留 CLI：它仍是开发、排障和批量操作的最佳入口。

这不是“CLI 升级为 MCP”的单向路线。一个 MCP Server 可以调用已有 CLI；一个 CLI 也可以启动或配置 MCP。关键是不要复制业务逻辑，而是让不同入口复用同一核心能力。

## 六、未来：不是工具越来越多，而是上下文越来越小

接下来最重要的变化，可能不是 MCP 取代 CLI，也不是 CLI 取代 MCP。

而是 Agent 不再同时看到全部工具。

未来的 Agent Harness 会更像操作系统：主 Agent 先判断任务属于代码、搜索、办公还是业务运营，再进入相应 Workspace。每个 Workspace 只加载它需要的 Skill、上下文、历史、权限和少量执行能力。

这会带来三个趋势：

1. **CLI 更 AI 原生。** JSON 输出、非交互、`--dry-run`、字段裁剪和自描述帮助会成为基础能力；CLI 会同时服务人和 Agent。
2. **MCP 更 Web 化。** 无状态、可缓存、可路由、可扩展的协议形态，会让远程 MCP 成为稳定的企业集成层。
3. **Skill / Workspace 成为组织层。** 它们不负责执行，却决定 Agent 在何时看见什么、拥有什么权限、遵循哪套 SOP。这比继续堆工具更能提升成功率。

最终，好的系统不是让 Agent “拥有所有能力”，而是让它在正确的场景里，看到刚好够用的能力。
