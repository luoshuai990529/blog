# 从 Claude Code 源码学习 Agent 工具运行时：并发、上下文更新与失败处理

## 一、问题背景：工具调用不是模型输出后的附属动作

对能够修改代码、执行命令的 Agent 而言，一次工具调用会改变的不只是对话记录，还可能改变文件系统、工作目录、权限状态、任务状态和后续可用工具。

因此，工具运行时（tool runtime）不能只是“收到工具调用协议（`tool_use`）就执行，再把字符串塞回模型”。一旦模型在同一轮请求里发起多个调用，系统必须回答几个问题：

- 哪些调用可以并行，哪些必须串行？
- 并发结果以什么顺序写回消息链？
- 工具对共享上下文的修改如何避免竞争？
- 拒绝、超时、取消和执行异常如何转化成模型可恢复的反馈？

Claude Code 将这些责任放在独立的工具运行时中，而不是分散在每个工具里。核心入口是 `src/services/tools/toolOrchestration.ts`、`toolExecution.ts`、`StreamingToolExecutor.ts`，主循环 `src/query.ts` 负责将其接回模型调用。

## 二、核心结论

> [!summary] 核心判断
> Agent 工具调用应被实现为一个带调度、状态提交和错误归一化能力的运行时：并发只用于可证明互不影响的读取操作，所有共享状态更新都必须以确定性顺序提交，失败则必须变成可继续推理的结构化事件。

## 三、它在 Agent 技术链路中的位置

```text
用户任务
  → 模型规划与生成工具调用
  → 工具运行时：校验、审批、调度、执行
  → 工具结果与上下文状态提交
  → 模型读取反馈并决定下一步
  → 验证、结束或继续循环
```

工具运行时位于“规划”和“真实执行”之间，是 Agent 的执行内核。它不决定模型是否会做正确规划，但决定错误规划、并发调用和外部失败是否会让整个会话失控。

## 四、Claude Code 的工具运行时拆分

### 1. 工具注册与输入契约

`src/tools.ts` 集中注册文件读写、命令行、搜索、计划、任务、子 Agent 等工具；`src/Tool.ts` 定义工具的输入模式、执行接口与上下文。每个调用先经输入模式（schema）校验，再进入执行。

这层的价值是把“模型生成的 JSON”转为受类型约束的命令。输入无法解析时，应视为不具备并发安全性，也不应猜测其副作用。

### 2. 按副作用分批，而不是盲目并行

`partitionToolCalls()` 将同一轮工具调用切成两类批次：

```text
连续的只读、彼此独立调用
  → 作为一个并发批次执行

任何可能写入或无法证明安全的调用
  → 独占批次，按原顺序串行执行
```

工具通过 `isConcurrencySafe()` 基于已校验的输入判断是否可并行；判断函数抛错、工具不存在或输入不合法时，运行时保守地退回串行。这体现了一个重要原则：**并发许可是白名单，不是默认值。**

### 3. 并发执行，顺序提交

并行读取可以缩短等待时间，但其完成顺序并不稳定。Claude Code 在并发批次中收集每个工具返回的上下文修改器（context modifier），待结果流完后仍按原始工具调用顺序依次应用。

```text
模型顺序：Read(A) → Search(B) → Read(C)
  → 三者可并发执行
  → 结果可先后到达并展示
  → 上下文修改仍按 A → B → C 提交
```

这避免了“谁先完成谁先覆盖状态”的竞态条件。实践中应把工具结果分为两类：

| 类型 | 例子 | 处理方式 |
|---|---|---|
| 事实型结果 | 文件内容、搜索命中、诊断信息 | 可并发获取，按调用顺序写入消息链 |
| 状态型结果 | 修改当前工作目录（cwd）、更新待办、写文件、切换工作树 | 串行执行，执行成功后才提交新上下文 |

### 4. 流式工具执行与取消

`StreamingToolExecutor` 说明工具不一定只有“开始—结束”两态。长命令、后台任务和子 Agent 需要持续输出进度，并能接收取消信号。运行时应将进度和最终结果区分开：前者服务用户界面和可观测性，后者才进入模型的因果消息链。

取消同样不是简单杀掉进程。应向模型补齐失败的工具结果，使先前的工具调用与结果仍然成对；否则下一轮请求可能因消息格式不完整而被接口拒绝。

### 5. 失败归一化与恢复循环

工具层的失败来源很多：权限拒绝、参数错误、进程非零退出、超时、网络异常、用户中断。运行时不应把内部异常直接抛给主 Agent，而应转换成带工具调用标识的错误结果，并保留可行动的信息：

- 哪个动作失败；
- 是被拒绝、不可用还是执行失败；
- 哪些副作用可能已经发生；
- 模型下一步可采取什么替代动作。

`query.ts` 还会处理缺失工具结果、输出长度受限和上下文过长等模型侧失败。可靠 Agent 的关键是让失败成为下一轮决策的输入，而不是让会话停止在半截协议状态。

## 五、分阶段实践

### 1. 第一阶段：建立最小工具协议

每个工具至少具备：名称、严格输入模式、可读的人类错误信息、超时和取消接口。先全部串行执行，明确工具的副作用边界。

### 2. 第二阶段：引入副作用分类

把工具标成只读、可逆写入、不可逆写入和外部副作用四类。只有只读且输入独立的调用才允许并发；写入类工具必须读取最新状态后执行。

### 3. 第三阶段：分离执行与状态提交

不要让工具在任意时刻直接改全局会话对象。让工具返回结果与“如何更新上下文”的描述，由调度器按稳定顺序提交。这样才能重试、记录审计日志和实现确定性回放。

### 4. 第四阶段：治理长任务与失败

增加进度事件、取消传播、幂等键、超时分级和失败重试策略。对外部写操作优先提供“已执行但结果未知”的状态，避免模型把不确定操作重复执行。

## 六、工程落地中的坑

1. **把所有工具都并行。** 文件编辑、Git 提交、数据库写入会因依赖前序状态而产生竞态；并发应由工具声明并经过运行时复核。
2. **只保存文本结果，不保存状态变化。** 下一轮模型可能不知道当前工作目录（cwd）、待办或文件版本已改变，从而在错误现场继续执行。
3. **让异常穿透工具协议。** 未配对的工具调用会破坏消息格式；应该补齐对应的错误结果。
4. **把长输出直接放进上下文。** 进度可展示，最终给模型的应是受预算控制的结果；详见 [[从 ClaudeCode 源码学习 Agent 工程状态治理：记忆管理、上下文压缩与会话恢复]]。
5. **将“退出码为 0”当作成功。** 编译、测试和部署都需要语义级验证；工具成功只表示命令完成，不等于任务完成。

## 七、推荐落地路径

1. 为每个工具定义输入模式、副作用等级、超时和取消语义。
2. 实现串行调度与统一的工具结果消息。
3. 将只读工具分批并发，并固定状态提交顺序。
4. 接入权限审批、结果预算和会话日志。
5. 为长任务增加进度、取消、重试与幂等保护。
6. 用真实失败样本检验：拒绝、超时、半完成、重复调用和并发冲突。

## 九、最终沉淀

工具运行时不是工具函数的集合，而是 Agent 的事务协调层。它要让并行读取提升速度、让写入操作保持顺序、让每个失败都有可恢复的语义；模型负责决定做什么，运行时负责保证“做这件事”不会破坏工程现场。

一句话总结：

> Agent 的工具能力是否可靠，取决于是否把工具调用实现成可调度、可提交、可取消、可恢复的运行时。
