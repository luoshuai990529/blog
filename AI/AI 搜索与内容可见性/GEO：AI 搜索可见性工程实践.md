# GEO：AI 搜索可见性工程实践

## 一、问题背景

传统搜索优化关注页面在搜索结果中的排名；GEO（Generative Engine Optimization，生成式引擎优化）关注的是：当用户向 ChatGPT、Claude、Perplexity、Google AI Overview 等系统提问时，系统能否发现、理解并准确引用自己的内容。

GEO 不是给模型投喂提示词，也不是通过生产垃圾内容刷排名。它更像一项内容基础设施工作：让真实存在的产品、文档和项目具备清晰的入口、稳定的抓取路径、可复用的信息结构和可验证的证据。

## 二、核心结论

1. GEO 的优化对象不是某一个页面的关键词，而是“内容被发现 → 被读取 → 被理解 → 被引用”的完整链路。
2. 搜索引擎收录是前置条件；页面没有进入搜索索引，后续的 `llms.txt`、Markdown 和结构化 API 很可能不会产生效果。
3. 爬虫需要按用途管理。训练爬虫、搜索/检索爬虫和用户主动触发的爬虫，应该分别决定是否放行。
4. AI 更容易使用结构清晰、语义明确、来源可信、包含具体证据的内容；机械堆叠关键词、标题或 FAQ 不能替代内容质量。
5. 被检索到不等于被引用。页面还要与问题高度相关，并且能够被模型切分成独立、完整、可验证的知识片段。
6. `llms.txt`、JSON-LD 等结构化约定仍处于生态早期，适合做低成本实验，不应当被当作所有 AI 平台都支持的硬标准。
7. GEO 当前更适合作为品牌和知识可见性建设，而不是短期流量增长手段；产品价值、文档质量和第三方口碑仍然是核心。

## 三、把 GEO 看成一条可观测链路

```text
内容生产
  → 爬虫允许访问
  → 搜索引擎收录
  → AI 获取页面
  → 模型理解页面主题
  → 选择并引用证据
  → 监测引用准确性并持续修订
```

这条链路中，任何一环都可能成为瓶颈：robots.txt 配错会导致无法抓取；没有 sitemap 会导致新页面迟迟未收录；正文结构混乱会导致模型无法判断页面主题；缺少证据会让页面进入检索池却不进入最终回答。

## 四、GEO 与传统 SEO 的关系

GEO 并不是 SEO 的替代品。搜索索引、站点可访问性、页面质量和外部链接仍然是共同基础，但优化目标存在差异：

| 维度 | 传统 SEO | GEO |
| --- | --- | --- |
| 主要目标 | 提升搜索结果排名和点击 | 提升 AI 回答中的发现、理解与引用概率 |
| 典型结果 | 搜索结果页中的链接位置 | AI 回答中的描述、引用和推荐 |
| 更关注的信号 | 页面质量、链接、技术 SEO | 语义相关性、信息完整性、证据和可引用结构 |
| 主要风险 | 关键词堆叠、低质量外链 | 内容注水、伪造结构化信号、爬虫伪装 |

文章引用的研究指出，部分 AI Overview 引用来自传统排名前十之外的页面。这说明不能只用“是否排进前十”判断 AI 可见性，但也不能据此忽略搜索引擎收录；收录仍然是 AI 发现内容的重要入口。

## 五、第一阶段：先确定目标和边界

### 5.1 明确希望 AI 记住什么

先列出希望用户通过 AI 找到的对象，例如：

- 产品或开源项目是什么，适合谁使用；
- 项目解决了什么问题，和替代方案有什么差异；
- 安装、配置和使用方式是什么；
- 团队或个人有哪些稳定的技术方向。

每个目标都应该能落到一个具体页面或一个可验证的数据接口，而不是只写一句“提升品牌曝光”。

### 5.2 区分可见性和流量目标

AI 引荐流量目前仍受平台入口、索引策略和引用习惯影响。GEO 更适合先作为品牌可见性和知识资产治理项目：让 AI 准确介绍你是谁、做过什么、项目怎么使用。不要为了短期流量牺牲产品开发、文档维护和用户体验。

### 5.3 先做信息增量，再做格式优化

任何新增内容都要回答一个问题：它是否提供了页面中原本没有的信息？如果只是重复正文、堆叠 FAQ 或为了提高审计工具分数而添加段落，通常会增加噪声，降低页面的整体可读性。

## 六、第二阶段：按爬虫类型设计访问策略

不要把 `robots.txt` 当成“全部开放/全部禁止”的开关。不同爬虫的用途不同，应该按数据使用目的和合规要求分别决策。

### 6.1 训练爬虫

常见标识包括 `GPTBot`、`ClaudeBot`、`CCBot` 等。它们主要用于收集训练数据。若不希望内容进入训练数据，可以单独限制它们；这通常不等同于关闭实时 AI 搜索。

### 6.2 搜索与检索爬虫

常见标识包括 `OAI-SearchBot`、`Claude-SearchBot`、`PerplexityBot` 等。它们负责把页面带入实时检索或搜索索引。若希望内容出现在相关 AI 搜索结果中，就不能无条件屏蔽这类爬虫。

### 6.3 用户主动触发的爬虫

例如用户把页面 URL 贴到对话中，并要求 AI 总结页面时，平台可能使用 `ChatGPT-User`、`Claude-User`、`Perplexity-User` 等标识访问页面。屏蔽这类爬虫会影响“让 AI 读取指定链接”的场景。

### 6.4 退出标识和未声明爬虫

`Google-Extended`、`Applebot-Extended` 更接近退出特定 AI 训练用途的声明，不应简单当成普通抓取程序。部分爬虫可能不明确标识身份，也不一定遵守公开约定，因此仍需要配合访问日志、速率限制、CDN/WAF 和合规策略治理。

### 6.5 一个可落地的决策表

| 目标 | 处理建议 |
| --- | --- |
| 允许 AI 搜索发现内容 | 放行搜索/检索爬虫，并监控抓取日志 |
| 允许用户贴链接让 AI 总结 | 放行用户触发爬虫 |
| 不希望内容用于训练 | 单独限制训练爬虫或使用平台提供的退出声明 |
| 防止异常抓取 | 使用速率限制、缓存、WAF 和访问审计，不依赖 User-Agent 判断全部安全性 |

最终规则必须结合版权、隐私、合同和平台政策确认，不能直接复制其他站点的配置。

## 七、第三阶段：确保站点能够被发现和收录

### 7.1 提交 sitemap 并检查索引

在 Google Search Console 和 Bing Webmaster Tools 中验证站点、提交 sitemap，定期检查重要页面是否已收录、是否被阻止抓取、是否存在规范 URL 冲突。对未收录页面先解决站点结构、链接可达性、重复内容和质量问题。

### 7.2 使用 IndexNow 加快 Bing 更新

内容频繁更新的站点可以接入 IndexNow：在站点根目录放置 API key 文件，发布或更新页面后主动提交 URL。它只能加快通知，不保证页面一定收录，也不能替代页面质量和正常抓取。

### 7.3 通过真实查询验证收录结果

不要只看站长平台的索引数量。还要定期用项目名、产品名和典型问题在目标 AI 平台中查询，确认：

- 页面是否被找到；
- AI 对页面主题的描述是否准确；
- 引用是否指向正确页面；
- 页面更新后，旧信息是否仍被反复引用。

## 八、第四阶段：构建 AI 可读的内容入口

### 8.1 `llms.txt`：低成本的站点说明书

可以在站点根目录提供一个 Markdown 文件，说明站点定位、作者或团队、核心项目、重要文档和推荐入口。它的价值在于提供一个干净的导航页，而不是保证所有模型都会优先读取它。

建议内容包括：

```markdown
# 站点名称

## 站点定位
一句话说明站点服务对象和主要内容。

## 核心项目
- [项目 A](https://example.com/projects/a)：解决什么问题，适合谁。
- [项目 B](https://example.com/projects/b)：解决什么问题，适合谁。

## 重要文档
- [快速开始](https://example.com/docs/getting-started)
- [架构说明](https://example.com/docs/architecture)

## 作者与来源
说明作者、维护组织和数据来源。
```

如果维护多个博客、周刊、项目站点，可以互相提供明确链接，形成可发现的内容网络；但每个链接都应真实有效，不能为了增加入口堆叠无关地址。

### 8.2 提供干净的 Markdown 版本

复杂网页往往包含导航、脚本、广告和样式噪声。对核心页面可以提供独立 Markdown 路由，并在 HTML 的 `<head>` 中声明：

```html
<link rel="alternate" type="text/markdown" href="/projects/example.md">
```

这是一种渐进式增强，不应根据 User-Agent 给爬虫和真人返回不同事实内容。所有访问者看到的核心内容应该一致。

### 8.3 建立分层知识入口

对于同时维护多个项目、博客和数据源的个人或团队，可以采用三层结构：

1. **概览层**：`llms.txt`，只放站点定位和关键链接。
2. **完整背景层**：例如 `llms-full.txt`，集中放项目关系、技术方向和完整介绍；30–60KB 可以作为一次实现的容量参考，不是标准要求。
3. **事实页面层**：每个项目、产品或主题拥有独立页面，提供可直接引用的事实和使用方式。

在此基础上，可以提供 `/api/profile`、`/api/projects` 等 JSON 接口，让程序以稳定格式获取项目名称、描述、版本和仓库地址。数据应尽量从 GitHub API 或数据库等上游生成，使用缓存或定时构建避免手工维护多份副本。

### 8.4 给内容增加叙事关系

如果只有项目列表，AI 可能知道“有哪些项目”，却不知道它们之间的关系。应补充一段稳定叙事：项目为何产生、解决的问题如何演进、各项目共同体现了什么技术方向。叙事不是营销口号，而是帮助模型建立实体关系和上下文。

## 九、第五阶段：把页面写成可引用的知识单元

### 9.1 一个项目页面至少回答六个问题

1. 它是什么？
2. 解决什么问题？
3. 适合谁使用？
4. 核心能力和边界是什么？
5. 如何安装或调用？
6. 与替代方案相比有什么差异？

页面开头给出一句可独立引用的摘要，后续再展开背景、步骤、配置、示例、限制和来源。这样即使模型只截取其中一个段落，也不容易丢失主语和适用条件。

### 9.2 标题和 URL 要表达主题

使用“项目名 + 解决的问题”这类自然语言标题和路径，例如 `/projects/pake`，比 `/page?id=47` 更容易让搜索系统和模型在看到 URL 时判断主题。URL 不是决定引用的唯一因素，但它是低成本的语义信号。

### 9.3 具体、可验证、可对比

优先写：真实版本、性能数据、适用条件、操作步骤、限制、来源和横向对比。少写“业界领先”“极致体验”等无法核验的形容词。

文章引用的 GEO 实验显示，包含具体数据、定义、对比和步骤的页面往往比泛泛介绍更容易被引用；研究还观察到 1000–3000 词是较常见的高信息密度区间。这个区间只能作为内容规划参考，不能为了凑字数扩写。

### 9.4 用第三方证据建立可信度

官方文档、代码仓库、版本记录、社区讨论和独立媒体对项目的真实提及，可以帮助模型交叉验证。自有站点的自我介绍仍然重要，但不能只靠“自己说自己好”建立可信度。

## 十、第六阶段：主域名同步和自动维护

AI 从主站发现内容后，不一定会继续遍历所有子域名。因此，关键入口最好在同一主域名下提供：

```text
example.com/llms.txt
example.com/projects/example.md
example.com/api/projects.json
```

可以通过构建时拉取、反向代理或 GitHub Actions 定时同步。同步过程需要记录源数据版本、更新时间和失败状态，避免主域名展示过期内容。

推荐的最小自动化流程：

```text
上游数据更新
  → 生成 Markdown / JSON
  → 构建与校验链接
  → 部署到主域名
  → 提交 sitemap / IndexNow
  → 记录抓取与引用变化
```

## 十一、如何评估 GEO 是否有效

GEO 不能只用一个“AI SEO 分数”衡量，建议把指标拆成四层：

| 层级 | 关注问题 | 示例指标 |
| --- | --- | --- |
| 可抓取 | 爬虫能否访问页面 | 抓取成功率、响应时间、robots 命中情况 |
| 可发现 | 页面是否进入搜索索引 | 收录率、sitemap 状态、索引延迟 |
| 可引用 | 页面是否进入 AI 最终回答 | 目标问题引用率、引用页面覆盖率 |
| 可用 | AI 描述和引用是否正确 | 实体准确率、事实一致性、过期信息比例 |

建立一组固定测试问题，覆盖品牌名、项目名、竞品对比、安装方式和边界问题。每次修改后在多个目标平台重复测试，并记录检索日期、引用 URL、回答摘要和错误类型。

需要区分“检索到”和“最终引用”：进入候选页面池只说明内容可获取，最终是否引用还取决于页面与问题的语义匹配、信息完整度和可信度。文章引用的实验观察到，检索页面中只有一部分最终进入回答，因此不能只看抓取日志判断 GEO 成功。

## 十二、常见误区和工程风险

### 12.1 把所有爬虫一律放行或屏蔽

这会混淆搜索可见性、训练授权和用户主动读取三个不同目标。应按爬虫用途、合规约束和业务价值分别配置。

### 12.2 把 `llms.txt` 当成强制标准

`llms.txt` 是一个正在形成中的社区约定，不是所有 AI 平台都保证支持的接口。它适合作为导航增强，不能替代 sitemap、正常网页内容和搜索收录。

### 12.3 堆叠非官方标签和隐藏提示

`ai-content-url`、`llms` 等非官方 meta 标签、多个竞争性的 `/.well-known/ai.txt` 提案、HTML 注释中的 AI 提示，目前都不能作为通用方案。除非服务商官方文档明确支持，否则会增加维护噪声。

### 12.4 依赖 JSON-LD 解决全部可见性问题

JSON-LD 对部分搜索引擎的富化结果有帮助，但不能假设 ChatGPT、Claude 等平台一定按预期解析其中语义。可保留规范结构化数据，同时把关键事实写入可见正文和 Markdown 页面。

### 12.5 用 User-Agent 嗅探做内容伪装

只给爬虫返回 Markdown、给真人返回另一套内容，容易形成 cloaking 风险，也会造成引用内容和用户看到的页面不一致。应提供对所有访问者一致的事实内容，按协商方式提供格式优化。

### 12.6 为了评分刷 FAQ、刷长度

FAQ、标题层级和篇幅都不是目标本身。重复已有内容会降低信息密度；1000–3000 词也不是硬性配额。应以“是否增加可验证信息”决定是否扩写。

### 12.7 把 AI 引用当成事实证明

AI 可能错误归因、截断上下文或把相邻页面混在一起。文章引用的 CJR/Tow Center 测试也显示，AI 引用存在较高错误率。因此，重要场景仍要回到原始页面、版本记录和人工审核。

## 十三、推荐落地路径

### 阶段一：一小时基础配置

- 确认 Google/Bing 已收录主站；
- 检查 robots.txt，放行需要的检索和用户触发爬虫；
- 增加 sitemap；
- 创建简洁的 `llms.txt`；
- 为核心页面提供清晰标题、摘要和自然语言 URL。

### 阶段二：建设知识入口

- 为每个核心项目建立独立知识页；
- 提供 Markdown 版本；
- 增加项目之间的叙事关系；
- 将关键项目数据整理为 JSON API；
- 把关键入口同步到主域名。

### 阶段三：自动化和评估

- 用 CI 定时生成和校验页面；
- 接入 IndexNow 或其他站点更新通知；
- 建立固定问题集，跟踪不同平台的检索、引用和事实准确率；
- 通过访问日志和版本记录定位“能抓取但不能引用”的页面问题。

## 十四、最终沉淀

GEO 的本质不是让 AI “偏爱”某个网站，而是降低 AI 获取和验证真实信息的成本：内容可访问、入口可发现、页面结构清晰、事实具体可信、引用可以追溯，并且整个链路能够持续监测和更新。

一句话总结：

> 先让内容被正确找到，再让页面被正确理解，最后用可验证的结构和证据提高被准确引用的概率；不要用短期技巧替代产品和内容本身。
