# LLM 关键实体关注与生成控制实践

## 一、问题背景

大模型在生成答案时，经常会出现一种问题：输入里明明有关键实体，但最终回答没有围绕这些实体展开。

这些关键实体可能是：

- 人名。
- 日期。
- 金额。
- 地点。
- 产品名。
- 支付渠道。
- 医疗术语。
- 金融术语。
- 行业专有名词。
- 企业内部黑话。

例如用户问：

```text
刷单被骗多少元，用花呗付款可以追回吗？
```

这个问题里真正关键的信息包括：

```text
刷单：事件类型
被骗金额：损失金额
花呗：支付渠道
追回：用户诉求
```

如果模型没有识别“花呗”是支付渠道，也没有理解“刷单被骗”是风险事件，它就很容易生成泛泛的售后建议，而不是围绕支付渠道、交易证据、资金追回路径给出回答。

这类问题本质上不是“检索不到资料”，而是：

> 模型在推理和生成时没有把关键实体当成足够重要的信息。

## 二、核心结论

LLM 关键实体关注问题，可以分成三层处理：

```text
Prompt 引导
  → 用自然语言要求模型关注实体

实体识别 / RAG 上下文增强
  → 先抽取关键实体，再把实体信息显式提供给模型

微调或 Logit 干预
  → 从模型行为层面提高特定实体或术语的稳定性
```

其中，Prompt 最轻量，但稳定性有限；微调更稳定，但需要数据和训练成本；Logit Hook 更可控，但实现复杂，且容易影响生成自然度。

> [!summary] 核心判断
> 关键实体关注不是单纯 Prompt 问题，而是模型理解、上下文组织、实体识别和生成控制共同作用的结果。工程上应优先使用 Prompt + RAG + 实体抽取，只有在特殊场景下才考虑微调或 Logit Hook。

## 三、它在 LLM 技术链路中的位置

这篇文档关注的是 LLM 推理阶段的生成控制。

它不属于 RAG 的核心检索链路。

更准确的位置是：

```text
用户输入 / 上下文
  → 实体识别
  → Prompt 组织
  → 模型推理
  → 生成控制
  → 输出答案
```

如果结合 RAG，它位于：

```text
RAG 检索上下文
  → 抽取关键实体
  → 构造生成 Prompt
  → 控制模型回答时覆盖关键实体
```

也就是说，RAG 可以把实体检索出来，但最终模型是否关注这些实体，仍然属于生成控制问题。

## 四、为什么模型会忽略关键实体

常见原因有几类。

### 1. 模型对领域实体不熟悉

通用模型训练数据中可能很少出现某些行业词。

例如：

- 金融风控术语。
- 医疗专病术语。
- 企业内部系统名。
- 业务流程缩写。
- 产品线内部叫法。

模型虽然能看到这些词，但不一定理解它们的重要性。

### 2. 实体在上下文中权重不够

有时实体只出现一次，或者被埋在长上下文中。

模型在生成时可能更关注更常见、更通用的表达，而忽略低频但关键的实体。

### 3. Prompt 没有明确任务约束

如果 Prompt 只说“请回答用户问题”，模型可能不会主动提取并覆盖所有关键实体。

更稳的 Prompt 应该明确：

```text
请先识别问题中的关键实体。
回答时必须覆盖这些实体。
如果某个实体无法判断，请明确说明缺失信息。
```

### 4. 生成阶段采样带来随机性

temperature、top_p 等采样参数会影响生成结果。

如果采样随机性较高，即使模型理解了实体，也可能在某次生成中没有覆盖。

## 五、方案一：Prompt 引导

最简单的方案是在 Prompt 中直接告诉模型关注哪些实体。

例如：

```text
请重点关注以下实体：
- 花呗：支付渠道
- 刷单：风险交易类型
- 被骗金额：损失金额
- 追回：用户诉求

回答时必须围绕这些实体分析，不要只给泛泛建议。
```

优点：

- 实现简单。
- 成本低。
- 不需要训练。
- 适合快速验证。

缺点：

- 稳定性不够。
- 对 Prompt 质量依赖大。
- 长上下文中仍可能漏实体。
- 模型可能表面提到实体，但没有真正围绕实体推理。

Prompt 引导适合做第一层控制，但不要把它当成强约束。

## 六、方案二：实体识别与结构化输入

比直接写 Prompt 更稳的方式，是先做实体识别。

例如先把用户输入解析成：

```json
{
  "event_type": "刷单被骗",
  "payment_channel": "花呗",
  "loss_amount": "未知",
  "user_intent": "追回资金"
}
```

然后再把结构化实体交给模型：

```text
已识别实体：
- 事件类型：刷单被骗
- 支付渠道：花呗
- 损失金额：用户未提供
- 用户诉求：追回资金

请基于这些实体回答。
```

实体识别可以通过几种方式实现：

- 规则词典。
- NER 模型。
- LLM 结构化抽取。
- 领域微调模型。
- RAG 检索出的术语词库。

传统 NLP 中常见做法是 `BERT + CRF` 或 Transformer + CRF，用标注数据训练领域实体识别模型。

在 LLM 应用中，也可以让模型直接输出 JSON 格式的实体结果。

这种方式比 Prompt 直接提醒更稳定，因为它把“识别实体”和“生成答案”拆成了两个步骤。

## 七、方案三：微调

如果实体识别和生成要求长期稳定，可以考虑微调。

常见方式包括：

- SFT。
- LoRA。
- Q-LoRA。
- 领域 NER 微调。
- 信息抽取任务微调。

微调适合：

- 领域实体稳定。
- 有足够标注样本。
- 任务长期存在。
- Prompt 和 RAG 仍然不够稳定。

例如训练模型识别：

```text
花呗 → 支付渠道
刷单金额 → 损失金额
吉他、手风琴 → 乐器
```

优点：

- 稳定性更好。
- 对领域实体适配更强。
- 推理时更自然。

缺点：

- 需要标注数据。
- 训练和评估成本高。
- 上线和回滚更复杂。
- 实体体系变化时需要重新维护数据。

微调不适合短期实验，也不适合实体体系频繁变化的场景。

## 八、方案四：Logit Hook 干预

更底层的一类方案是 Hook 干预。

这里需要先明确一个概念：

> 更准确地说，这类实现通常不是直接修改 Attention 权重，而是在模型输出层修改 Logit，从而提高指定 token 被生成的概率。

自回归模型生成下一个 token 的过程可以简化为：

```text
输入上下文
  → Transformer 计算隐藏状态
  → LM Head 输出 logits
  → Softmax 转成概率分布
  → 采样生成下一个 token
```

Logit Hook 的做法是在 Softmax 之前干预：

```text
指定 token 的 logit += boost_value
```

这样这些 token 的生成概率会提高。

例如希望模型更频繁关注：

```text
大模型
人工智能
医疗
自动驾驶
智能客服
```

可以先把这些词转成 token id，然后在生成时提高这些 token id 对应的 logit。

## 九、Logit Hook 的实现流程

一个典型流程是：

```text
加载模型和 tokenizer
  → 设置需要增强的关键词
  → 将关键词转换为 token id
  → 定义 hook 函数
  → 在 lm_head 或输出层注册 hook
  → 执行生成
  → 移除 hook
```

关键点如下。

### 1. 关键词必须转成 token id

模型不直接处理中文词，而是处理 token。

例如：

```text
大模型
```

可能被 tokenizer 切成：

```text
大
模型
```

也可能切成其他 token 组合。

如果没有处理好 token 切分，就可能错误增强“ 大 ”这类泛词，而不是“大模型”这个概念。

### 2. 干预位置要在 Softmax 之前

如果在 Softmax 之后再改，概率分布已经形成，干预价值很低。

如果过早干预 Transformer 内部层，又容易造成输出结构混乱。

更可控的位置通常是：

```text
LM Head 输出 logits 后
Softmax 前
```

### 3. 权重不能过强

如果 boost 太大，模型可能反复生成关键词。

例如：

```text
大模型 大模型 大模型 大模型……
```

这时需要降低权重，或者使用：

```text
no_repeat_ngram_size
```

来限制重复。

### 4. Hook 必须及时移除

Hook 是运行时干预。

如果生成结束后不移除，会影响后续其他请求。

所以流程应该是：

```text
注册 hook
  → 生成
  → remove hook
```

### 5. 设备要一致

如果模型在 CPU / GPU / MPS 上运行，hook 中的 tensor 也必须在同一设备。

否则容易出现 device mismatch 的 Runtime Error。

## 十、ModelScope 示例中的工程要点

以本地小模型实验为例，可以使用 ModelScope 加载 Qwen3-0.6B 观察这类干预效果。

选择小模型的原因是本地 Mac 环境没有 CUDA，大模型推理成本太高。

实现上大致包括：

- 使用 ModelScope pipeline 加载 chat 模型。
- 使用 tokenizer 获取目标关键词 token id。
- 定义 hook 函数，在 logits 上提高指定 token 分数。
- 使用 `max_new_tokens` 控制输出长度。
- 使用 `do_sample=True` 启用采样。
- 使用 `no_repeat_ngram_size=3` 降低重复风险。
- 生成前注册 hook，生成后移除 hook。

实验现象是：

```text
不使用 Hook：
  指定关键词出现次数较少，输出更自然

使用 Hook：
  指定关键词出现次数增加，但重复和不自然风险也增加
```

这说明 Logit Hook 确实可以影响生成倾向，但它不是无成本方案。

## 十一、工程落地中的坑

### 1. 把 Logit 干预误认为直接修改 Attention

问题表现：

- 以为自己在控制模型理解。
- 实际只是提高某些 token 的生成概率。

推荐处理：

- 明确区分 Attention 权重和 Logit。
- Logit 干预影响“更可能说出什么”，不等于模型真正理解了实体。

### 2. 关键词重复

问题表现：

- 目标实体出现次数变多。
- 但文本变得重复、不自然。

推荐处理：

- 降低 boost 强度。
- 使用 `no_repeat_ngram_size`。
- 控制 temperature 和 top_p。
- 只对少量关键 token 加权。

### 3. Token 切分导致误增强

问题表现：

- 想增强“大模型”，结果增强了“大”。
- 生成中出现大量无关词。

推荐处理：

- 打印 tokenizer 输出。
- 检查目标 token id。
- 避免增强过于通用的单字 token。

### 4. 长文本中干预效果衰减

问题表现：

- 开头能关注关键词。
- 生成越长，关键词控制越弱。

推荐处理：

- 控制生成长度。
- 分段生成。
- 在 Prompt 中重复结构化约束。
- 不要只依赖 Logit Hook。

### 5. 默认在生产链路使用 Hook

问题表现：

- 生成不可控。
- 多任务之间互相影响。
- 调试困难。

推荐处理：

- Hook 作为高级实验或特殊控制手段。
- 生产默认优先 Prompt、RAG、实体抽取和微调。
- 使用 Hook 时必须有开关、日志、回滚策略。

## 十二、推荐落地路径

### 1. 先用 Prompt 明确实体关注要求

先把任务写清楚：

```text
请先识别关键实体，再围绕实体回答。
如果关键实体缺失，请明确说明。
```

### 2. 再做实体抽取

把用户问题或 RAG 上下文中的实体先结构化抽出来。

然后把实体表作为显式输入交给模型。

### 3. 建立实体覆盖评估

评估生成结果是否覆盖关键实体。

例如：

| 指标 | 含义 |
|---|---|
| Entity Recall | 标准关键实体是否都被提及 |
| Entity Precision | 输出实体是否多出无关实体 |
| Entity Faithfulness | 实体是否来自输入或检索上下文 |
| Answer Coherence | 强化实体后答案是否仍然自然 |

### 4. 对长期稳定任务考虑微调

如果实体体系稳定，并且有足够标注数据，可以用 LoRA / Q-LoRA 或 NER 微调。

这通常比 Hook 更适合生产。

### 5. 特殊场景再考虑 Logit Hook

Hook 适合：

- 研究实验。
- 特定关键词强制覆盖。
- 本地可控模型。
- 生成控制兜底。

不适合：

- 黑盒 API 模型。
- 高并发通用生产链路。
- 对自然度要求很高的生成场景。

## 十三、最终沉淀

模型忽略关键实体，本质上是生成阶段的控制问题。

解决它不能只靠一个技巧，而要按成本和稳定性分层处理：Prompt 负责轻量提醒，实体抽取负责结构化输入，RAG 负责提供实体上下文，微调负责长期稳定适配，Logit Hook 负责特殊场景下的生成倾向干预。

工程上最容易犯的错误，是把 Logit Hook 当成通用解决方案。它确实能提高指定 token 的生成概率，但也会带来重复、不自然、设备兼容和调试复杂度。

一句话总结：

> LLM 关键实体关注与生成控制的核心，是先把关键实体显式识别和结构化，再通过 Prompt、RAG、微调或 Logit Hook 分层控制模型生成；其中 Logit 干预应作为高级兜底手段，而不是默认生产方案。
