# 你不知道的 Agent：原理、架构与工程实践

> 原文：[Tw93：你不知道的 Agent：原理、架构与工程实践](https://x.com/HiTw93/status/2034627967926825175)

## 一句话总纲

Agent 的核心循环很简单，真正决定它能否稳定工作的，是循环之外的 Harness、上下文、工具、记忆、验证、可观测性和安全边界。

## 核心结论

1. **Agent 的本质是一个稳定循环。** 它反复执行“感知 → 决策 → 行动 → 反馈”，直到模型不再调用工具；新能力通常加在循环外部，而不是修改循环本身。

2. **固定流程优先用 Workflow，开放任务才用 Agent。** 输入边界清晰、路径可预定义的任务用 Workflow 更稳定；只有需要运行时推理、动态选工具和自我修正时，才值得引入 Agent。

3. **常用控制流只有几类基本模式。** 提示链负责顺序处理，路由负责分类分流，并行负责拆分或投票，编排器负责动态委派，评估器负责根据反馈循环优化。

4. **Harness 往往比更贵的模型更重要。** 清晰目标、验收基线、执行边界、反馈信号和回退手段，通常比单纯升级模型更能提高任务成功率。

5. **最适合 Agent 的任务必须同时满足两个条件。** 目标足够明确，而且结果可以自动验证；缺少目标会让系统高效跑偏，缺少验证会让人工审查成为吞吐瓶颈。

6. **工程约束必须写进机器可执行的机制。** 关键知识留在代码仓库，约束进入类型、Linter、CI、测试或 Hook，而不是只写在文档里期待 Agent 自觉遵守。

7. **上下文问题通常是信噪比问题。** Context Rot 不是窗口不够长，而是无关信息稀释了关键信号；上下文越长，不代表 Agent 知道得越多，反而可能决策更差。

8. **上下文应分层并按需加载。** 常驻层只保留身份、硬约束和索引，知识通过 Skills 延迟加载，运行状态动态注入，历史和大结果放到文件系统按需检索。

9. **压缩必须保留决策，而不是只追求摘要短。** 架构决策、关键变更、验证状态、待办和回滚信息应优先保留；UUID、hash、URL、文件名等标识符必须原样保存。

10. **文件系统是理想的上下文接口。** 大量工具结果先落盘，再由 Agent 用搜索或脚本读取，可以降低 token 消耗，同时让状态可查看、可恢复、可审计。

11. **Prompt 缓存会反向影响架构。** 常驻提示越短且稳定，前缀缓存命中率越高；按需加载 Skills 和工具定义，能避免动态内容反复破坏缓存。

12. **Skill 的描述本质上是路由条件。** 它要明确什么时候用、什么时候不用和产出什么；系统只加载最具体的匹配项，没有匹配就不加载。

13. **工具应按 ACI 而不是底层 API 设计。** 工具要面向 Agent 的任务目标，名称和边界清晰，参数能防错，定义与实现一致，失败时返回可执行的修复建议。

14. **调试工具选择错误时，先检查工具描述。** 多数选错工具的问题来自命名、参数和边界含糊，而不一定是模型推理能力不足。

15. **记忆应按解决的问题分成四类。** 上下文窗口保存工作记忆，Skills 保存程序性记忆，会话日志保存情景记忆，MEMORY.md 保存跨会话需要注入的语义记忆。

16. **记忆整合必须可回退。** 旧消息应安全移出活跃上下文而不是直接删除；整合失败时保留原始存档，系统只移动进度指针，确保能够恢复现场。

17. **提高自主度的前提是状态外化。** 长任务应把进度、任务列表、测试状态和提交记录写入文件或 Git，使后续 session 可以恢复，而不是依赖模型“记住”。

18. **长任务要拆成可重入的多个阶段。** Initializer Agent 先建立持久化任务状态，后续 Coding Agent 每轮只完成一个可验证子任务、更新进度并提交，然后安全退出。

19. **慢速 I/O 不应阻塞 Agent Loop。** 后台任务完成后通过通知队列把结果注入下一轮，通常比把整个主循环改造成复杂异步系统更稳定。

20. **多 Agent 的首要问题是隔离和协议，不是并行。** 先建立持久化任务图、角色权限和独立工作区，再让 Agent 协作；子 Agent 只回传结构化摘要，细节留在各自上下文中。

21. **多 Agent 的真正价值是减少人的持续参与。** 人负责设定目标和最终审查，中间产出沉淀为分支、提交或 PR；不是简单地同时多开几个模型。

22. **多 Agent 会放大错误，因此必须独立验证。** 后续 Agent 不能顺着前一个结论盲目强化，应通过独立 Agent、测试、编译器或人工审查打断错误共识。

23. **评测要同时看过程和结果。** Transcript 记录 Agent 如何执行，Outcome 记录环境最终状态；只看最终答案或只看执行轨迹都会漏掉问题。

24. **Pass@k 衡量能力上限，Pass^k 衡量稳定性。** 前者关注多次尝试中能否至少成功一次，后者要求连续多次都成功；上线质量更依赖后者。

25. **看到分数下降，先修评测再改 Agent。** 环境资源不足、评分器 Bug、测试场景失真或聚合方式错误，都可能伪装成模型退化，基于失真信号优化只会越改越错。

26. **Trace 是排查 Agent 的前提。** 主循环应在工具开始、工具结束和回合结束时发出事件，由日志、UI、在线评测和人工审查共同消费，而不是分别侵入主循环。

27. **在线评测应按风险采样。** 负反馈、高 token 消耗、固定时间窗口以及模型或 Prompt 变更后的流量，应优先进入评测队列。

28. **安全设计的目标不是识别所有攻击，而是阻断危险动作。** 对外部内容标记不可信边界，执行最小权限，敏感写操作要求确认，关键路径再引入独立模型复核。

29. **生产级 Agent 必须支持主动触发和故障恢复。** cron、heartbeat 可以在没有用户消息时推进任务，而超过半小时的任务必须把进度持久化并支持断点续跑。

30. **可运行系统靠工程细节收敛。** OpenClaw 的启示是：真正让 Agent 跑稳的不是更复杂的循环，而是消息解耦、状态外化、分层提示、记忆整合、评测追踪和安全边界。

## 我自己的最终理解

做 Agent 工程的重点不是“让模型更自由”，而是先把目标、状态、能力、反馈和风险都变成系统能够管理的结构，再在这些约束之内逐步释放自主度。
