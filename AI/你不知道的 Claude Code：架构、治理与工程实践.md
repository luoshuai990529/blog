# 你不知道的 Claude Code：架构、治理与工程实践

> 原文：[Tw93：你不知道的 Claude Code：架构、治理与工程实践](https://x.com/HiTw93/status/2032091246588518683)

## 一句话总纲

Claude Code 不是一个“更会聊天的模型”，而是一个需要治理的代理系统；真正决定效果的不是提示词写得多漂亮，而是上下文、能力、流程、隔离和验证是否各司其职。

## 核心结论

1. **Claude Code 的本质是代理循环。** 它不断执行“收集上下文 → 采取行动 → 验证结果”，直到任务完成，所以只要求它“给出答案”远远不够。

2. **应把系统拆成六层治理。** CLAUDE.md/rules/memory 管长期上下文，Tools/MCP 提供动作能力，Skills 提供工作方法，Hooks 强制执行规则，Subagents 隔离任务，Verifiers 负责结果可信。

3. **任何一层过度膨胀都会让系统失衡。** 规则太长会污染上下文，工具太多会增加选错概率，Subagents 太多会造成状态漂移，缺少验证则无法判断任务是否真正完成。

4. **上下文问题通常不是“不够长”，而是“太吵”。** 最有效的治理不是盲目扩容，而是减少常驻内容、压缩工具输出，并把信息按使用频率分层加载。

5. **上下文应按需分层。** 项目契约放 CLAUDE.md，路径或语言差异放 rules，工作流和领域知识放 Skills，大量探索放 Subagents，确定性约束放 Hooks；偶尔使用的内容不要每次都加载。

6. **切换任务就开新上下文，同一任务换阶段才压缩。** `/clear` 适合任务切换，`/compact` 适合保持同一任务的连续性；必须在 CLAUDE.md 中明确压缩后要保留的决策、约束、验证状态和风险。

7. **Tool/MCP、Skill、Hook、Subagent 不能混用。** 新增动作能力用 Tool/MCP，固化做事方法用 Skill，强制约束和审计用 Hook，需要独立上下文或权限时用 Subagent，跨项目分发时再用 Plugin。

8. **Skill 应是一种单一、按需加载的方法论。** 好 Skill 的描述触发条件清晰、正文简短、复杂资料拆到 supporting files，并只负责检查清单、标准工作流或一个领域决策框架。

9. **Agent 工具的目标不是功能齐全，而是让模型不易选错。** 工具名称要具体、参数要有语义、返回值只保留下一步需要的信息、错误要给修复建议，能由可靠 shell 完成的事情不必再包装成工具。

10. **Hooks 用来把不可妥协的要求变成确定性机制。** 格式化、lint、受保护文件、轻量校验、动态环境注入和完成通知适合 Hooks；需要大量上下文和推理的判断应交给 Skill 或 Subagent。

11. **可靠流程需要三层叠加。** CLAUDE.md 声明原则，Skill 规定执行步骤，Hook 强制关键校验；只靠自然语言规则或只靠脚本都不完整。

12. **Prompt Caching 会反向决定架构。** 缓存按前缀匹配，因此稳定内容应放在前面、动态内容放在后面；频繁变化的工具定义和规则不仅消耗 token，也会破坏缓存命中率。

13. **Subagent 的价值是隔离，不是无脑并行。** 它适合独立探索、并行研究或受限权限任务，但必须给清晰边界和结构化回报；主 Agent 仍应负责整合决策和最终验证。

14. **CLAUDE.md 应短、硬、可执行。** 只保留每次都必须知道的项目契约、命令、架构边界和禁止事项；纠正 Claude 后可以让它补规则，但要定期删除过时内容。

15. **验证闭环决定代理是否可用于工程。** 每个任务都应有测试、lint、日志、截图或 CI 等可重复证据，使结果可验证、可回滚、可审计；没有验证，就只能算“做过”，不能算“完成”。

## 我自己的最终理解

使用 Claude Code 的能力进阶，不是从“不会写 Prompt”变成“会写 Prompt”，而是从使用工具、优化流程，最终变成设计一个能在约束下自主工作的工程系统。
