# RAG 事实验证链与溯源标注实践

## 一、问题背景

大模型幻觉无法完全消除。

即使 RAG 已经检索到了相关上下文，模型在最终生成时仍然可能：

- 混入上下文里没有的结论。
- 把多个来源的信息错误拼接。
- 改写数字、时间、实体名称。
- 引用过时或不适用的材料。
- 给出看似确定但没有证据支撑的判断。

对用户来说，最麻烦的问题不是“模型一定会错”，而是“很难判断它什么时候错”。

例如答案里出现一句：

```text
去年某地区人均收入为 1700 万。
```

如果系统没有提供来源，用户很难判断：

- 这个数字来自哪份文档。
- 原文是不是写的 1700 万。
- 是否被模型四舍五入或改写过。
- 是否引用了错误年份。
- 是否存在多个来源冲突。

所以企业级 RAG 不能只生成答案，还要让答案有证据链。

> [!summary] 核心判断
> 可信 RAG 的关键不是让模型“自觉不幻觉”，而是让每个关键结论都能追溯到原始证据；没有证据支撑的结论，要么标记不确定，要么不输出。

## 二、核心结论

事实验证链和溯源标注要解决两个问题：

```text
答案是否来自检索上下文
  → 每个关键结论是否有对应证据
  → 证据是否真的支持该结论
```

推荐链路是：

```text
文档入库时保留 metadata
  → 检索时返回 source_nodes
  → 生成时对关键结论标注来源
  → 生成后拆解 claim
  → 为每个 claim 匹配 evidence
  → 判断 evidence 是否支持 claim
  → 输出答案、引用、置信度和不确定项
```

一句话概括：

> RAG 溯源不是在答案末尾堆参考链接，而是建立“结论—证据—原文”的可追踪关系。

## 三、它在 RAG 链路中的位置

事实验证链位于 RAG 的后半段。

```text
文档解析
  → 元数据入库
  → 检索召回
  → 上下文构造
  → 生成答案
  → 来源标注
  → Claim 验证
  → 可信输出
```

它和前面几个环节的关系是：

- 检索负责把可能有用的证据找回来。
- Rerank 负责把更相关的证据排前面。
- 生成负责组织自然语言答案。
- 溯源负责说明答案来自哪里。
- 事实验证负责判断证据是否真的支持结论。

没有溯源和验证，RAG 仍然可能只是“带参考资料的黑箱生成”。

## 四、为什么只列参考链接不够

很多系统会在答案末尾统一列出参考资料：

```text
参考资料：
1. 链接 A
2. 链接 B
3. 链接 C
```

这种方式只能说明“系统检索过这些资料”，不能说明“每个结论分别来自哪里”。

问题在于：

- 某个数字对应哪个链接不清楚。
- 某个判断是否被原文支持不清楚。
- 多个来源冲突时无法定位。
- 用户需要自己在多个链接里反查证据。

更好的方式是句级或 claim 级引用：

```text
深度学习是机器学习的一个子领域 [1]。
该政策对首次认定企业给予一次性 30 万元补贴，最高支持不超过 50 万元 [2]。
```

每个编号都能展开：

```text
[2]
标题：某市高新技术企业补贴政策
URL：https://example.com/policy
原文片段：首次认定为高新技术企业的，给予一次性 30 万元补贴……
相关度：0.889
```

这样用户能直接从结论跳回证据。

## 五、核心方案

### 1. 入库阶段保留 metadata

溯源能力不是生成阶段凭空补出来的。

文档入库时就要保留来源信息：

```json
{
  "doc_id": "doc_001",
  "title": "某市高新技术企业补贴政策",
  "url": "https://example.com/policy",
  "source_type": "web_page",
  "published_at": "2026-01-01",
  "section": "第二章 第四条",
  "content": "首次认定为高新技术企业的，给予一次性 30 万元补贴……"
}
```

至少要保留：

- 文档标题。
- URL 或文件路径。
- 片段 ID。
- 页码或章节位置。
- 发布时间或版本。
- 原文片段。
- 文档来源类型。

没有 metadata，就无法可靠溯源。

### 2. 检索阶段保留 source node

检索时不能只返回文本，还要返回来源节点。

一个 source node 至少应该包含：

```json
{
  "text": "原文片段",
  "metadata": {
    "title": "文档标题",
    "url": "来源链接",
    "page": 3,
    "section": "第二章 第四条"
  },
  "score": 0.889
}
```

其中 score 可以作为“检索相关性”的参考，但不能直接等同于“事实支持度”。

### 3. 生成阶段要求引用来源编号

Prompt 中应该明确要求：

```text
请只基于给定上下文回答。
每个关键结论后必须标注来源编号。
如果上下文不足以支持结论，请回答“不确定”。
不要编造来源。
```

输出形式可以是：

```text
深度学习是机器学习的一个子领域 [1]。
关于人工智能未来十年是否超过人类，目前没有确定结论 [2]。
```

引用编号必须能映射回 source node。

### 4. 生成后拆解 claim

更严谨的做法是把答案拆成多个 claim。

例如答案：

```text
深度学习是机器学习的一个子领域，主要用于图像识别和自然语言处理。
```

可以拆成：

```text
Claim 1：深度学习是机器学习的一个子领域。
Claim 2：深度学习主要用于图像识别。
Claim 3：深度学习主要用于自然语言处理。
```

每个 claim 都需要单独找 evidence。

### 5. 验证 evidence 是否支持 claim

相关性不等于支持性。

一个文档片段可能和问题相关，但并不支持某个具体结论。

事实验证要判断：

```text
evidence 是否支持 claim？
```

结果可以分成：

```text
supported：证据支持
unsupported：证据不支持
contradicted：证据冲突
uncertain：证据不足
```

最终输出时，对 unsupported 或 uncertain 的 claim 应该降级处理。

## 六、LlamaIndex 实现思路

LlamaIndex 的实现重点是保留 Document metadata，并从响应结果中读取 source nodes。

典型流程：

```text
构建 Document
  → metadata 中写入 title、url、content、section
  → VectorStoreIndex 创建索引
  → query_engine 查询
  → response.source_nodes 获取来源节点
  → 输出答案、标题、URL、score、原文片段
```

核心数据来自：

```text
response.source_nodes
```

source node 通常可以拿到：

- node text。
- metadata。
- score。

输出时可以展示：

```text
答案：
深度学习是机器学习的一个子领域 [1]。

证据 [1]：
标题：机器学习概述
URL：https://example.com/ml
相关度：0.889
原文：深度学习是机器学习的一个子领域……
```

LlamaIndex 的优势是 source node 支持相对直接，适合快速实现引用溯源。

## 七、LangChain 实现思路

LangChain 更适合构建复杂验证链。

典型流程：

```text
定义 Document metadata
  → TextSplitter 分割文本
  → 构建向量库，例如 FAISS
  → 创建 retriever
  → 定义自定义 Prompt
  → 创建 RetrievalQA 或自定义 Chain
  → 输出答案、验证结果、置信度、推理过程和证据来源
```

Prompt 可以要求模型输出结构化结果：

```json
{
  "answer": "深度学习是机器学习的一个子领域。",
  "verification_result": "supported",
  "confidence": 0.95,
  "reasoning": "上下文明确说明深度学习属于机器学习分支。",
  "sources": [
    {
      "title": "机器学习概述",
      "url": "https://example.com/ml",
      "quote": "深度学习是机器学习的一个子领域"
    }
  ]
}
```

LangChain 的代码量通常比 LlamaIndex 多，但更适合把检索、生成、验证、格式化输出拆成多个环节。

## 八、置信度和相关度要分开理解

工程上要区分两类分数。

### 1. 检索相关度

例如向量检索返回的 score。

它表示：

```text
query 和 source node 在语义上有多相似
```

但它不能证明 source node 支持答案中的某个 claim。

### 2. 事实支持度

事实支持度表示：

```text
evidence 是否能支撑 claim
```

这通常需要额外判断。

可以通过规则、NLI 模型或 LLM-as-a-Judge 完成。

不要把“相关度高”直接等同于“结论真实”。

## 九、工程落地中的坑

### 1. 只在末尾列参考链接

问题表现：

- 用户不知道每个结论对应哪个证据。
- 精确数字、日期、条件无法快速核对。

推荐处理：

- 做句级或 claim 级引用。
- 每个关键结论旁边标注来源编号。

### 2. metadata 入库不完整

问题表现：

- 能检索到文本，但无法展示来源。
- 答案无法追溯到原文。
- 审计时找不到文档版本。

推荐处理：

- 入库时强制保存 title、url、doc_id、page、section、timestamp。
- 对本地文件也要保存文件路径、页码、章节。

### 3. 引用来源和结论不匹配

问题表现：

- 答案后面标了引用，但引用内容并不支持该结论。

推荐处理：

- 做 claim-evidence 验证。
- 不允许模型随便给句子贴来源编号。
- 对低置信引用做 uncertain 标记。

### 4. 模型自己输出的置信度被误用

问题表现：

- 模型说“置信度 95%”，系统就认为可信。

推荐处理：

- 置信度只能作为参考。
- 更重要的是 evidence 是否存在、是否相关、是否支持 claim。

### 5. 来源过时或冲突

问题表现：

- 模型引用了旧政策。
- 多个来源给出不同数字。

推荐处理：

- metadata 中保存发布时间、版本号。
- 检索时优先最新版本。
- 多来源冲突时明确提示冲突，而不是强行合并。

## 十、质量评估指标

事实验证链可以用以下指标评估：

| 指标 | 说明 |
|---|---|
| Citation Coverage | 有多少关键结论带有引用 |
| Citation Accuracy | 引用是否指向正确来源 |
| Evidence Support Rate | 证据是否支持对应 claim |
| Unsupported Claim Rate | 无证据结论占比 |
| Faithfulness | 答案是否忠实于检索上下文 |
| Source Freshness | 来源是否过时 |
| User Trust Signal | 用户是否点击、采纳或追问来源 |

其中最重要的是 Evidence Support Rate。

引用本身不等于可信，引用必须真的支持结论。

## 十一、推荐落地路径

### 1. 先保留 metadata

先确保所有入库文档都有可追踪来源。

没有 metadata，后面的引用和验证都无法可靠实现。

### 2. 再展示 source nodes

先把检索结果的来源展示出来。

即使还没有句级引用，也要能看到：

- 文档标题。
- URL。
- 页码。
- 原文片段。
- 检索分数。

### 3. 做句级引用

让模型在关键句后面标注来源编号。

同时要保证编号能映射回 source node。

### 4. 做 claim-evidence 验证

把答案拆成 claim，再逐条验证 evidence 是否支持。

不支持的 claim 要标记 uncertain 或移除。

### 5. 做审计与反馈闭环

记录：

- 用户问题。
- 检索 source nodes。
- 最终答案。
- 引用映射。
- claim 验证结果。
- 用户反馈。

这些数据可以反向优化检索、Rerank、Prompt 和知识库质量。

## 十二、最终沉淀

RAG 不能只追求“回答得像”，还要回答得有根据。

事实验证链和溯源标注的价值，是把模型输出从黑箱文本变成可追踪、可验证、可审计的可信答案。

工程上要从入库阶段就保留 metadata，在检索阶段保留 source nodes，在生成阶段做句级或 claim 级引用，在生成后验证 evidence 是否支持 claim。

一句话总结：

> RAG 事实验证链与溯源标注的核心，是让每个关键结论都能回到原始证据，并明确证据是否支持该结论；有证据才输出，证据不足就标记不确定。
