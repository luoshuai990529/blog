# RAG HNSW 索引调优与量化压缩实践

## 一、问题背景

HNSW 是 RAG 向量检索里常见的近似最近邻索引结构。

它的优势是查询速度快、召回率高，适合大规模语义检索、推荐、图像检索、视频检索等场景。

但 HNSW 不是无成本的。

真实工程里使用 HNSW 时，经常会遇到几个问题：

- 内存占用明显高于普通向量索引。
- 建索引时间较长。
- 参数调优复杂，不同参数会影响召回、延迟和内存。
- 小数据量下优势不明显，大数据量下成本又很敏感。
- 量化压缩可以降低内存，但可能带来精度损失。

所以 HNSW 的难点不是“能不能检索”，而是“如何在召回率、查询延迟、索引构建成本和内存占用之间找到可接受的平衡点”。

> [!summary] 核心判断
> HNSW 调优的核心是两件事：通过 `M`、`efConstruction`、`efSearch` 控制图索引质量和搜索深度，通过 SQ8/SQ16/PQ/OPQ 等量化压缩降低向量存储成本。

## 二、核心结论

HNSW 的调优可以拆成两条线：

```text
参数调优
  → 控制召回率、查询延迟、构建成本和图结构内存

量化压缩
  → 控制向量存储内存和精度损失
```

其中：

- `M` 决定图连接密度，影响召回率和内存。
- `efConstruction` 决定建索引时搜索范围，影响索引质量和构建耗时。
- `efSearch` 决定查询时搜索范围，影响召回率和查询延迟。
- `SQ8` 更省内存，但精度损失更明显。
- `SQ16` 精度更稳，但压缩率不如 SQ8。
- `PQ / OPQ` 进一步压缩向量，但会带来额外计算成本。

一句话概括：

> HNSW 的工程调优不是把参数调大，而是根据业务约束，在“更高召回、更低延迟、更少内存、更快构建”之间选择合适组合。

## 三、它在 RAG 链路中的位置

RAG 链路可以简化为：

```text
文档解析
  → 分块
  → Embedding
  → 向量索引构建
  → 向量检索
  → Rerank
  → LLM 生成
```

HNSW 位于“向量索引构建”和“向量检索”阶段。

它解决的是：

```text
如何在大规模向量集合中快速找到近邻向量
```

如果前面的 embedding 质量差、chunk 质量差，HNSW 调得再好也无法稳定召回正确内容。

因此 HNSW 调优要建立在几个前提上：

- 文档解析质量基本可靠。
- 分块没有严重语义割裂。
- embedding 模型适合业务语料。
- 已经确认向量检索是当前召回瓶颈。

## 四、HNSW 为什么需要单独调优

HNSW 和 BM25、IVF 的优化重点不一样。

BM25 的优化重点通常是：

- 分词。
- 停用词。
- 同义词。
- 字段权重。
- 术语词库。
- 查询改写。

FAISS IVF 的优化重点通常是：

- 聚类数量。
- nprobe。
- 训练样本。
- 数据分布。
- PQ / OPQ。

HNSW 的优化重点则是：

- 图连接密度。
- 建图搜索范围。
- 查询搜索范围。
- 图结构内存。
- 向量量化压缩。

HNSW 不只是存向量，还要存图结构连接关系。

所以它的内存大致来自两部分：

```text
向量本身
  + 图结构邻居连接
```

这也是为什么 HNSW 特别适合单独讨论调优。

## 五、HNSW 的三个核心参数

### 1. M：图连接密度

`M` 表示每个节点最多连接多少个邻居。

可以理解为：

```text
M 越大
  → 每个节点连接更多邻居
  → 搜索路径更多
  → 召回率可能更高
  → 内存占用更高
  → 构建成本更高
```

```text
M 越小
  → 图更稀疏
  → 内存更低
  → 构建更快
  → 召回率可能下降
```

如果业务更关注召回质量，可以适当增大 `M`。

如果业务内存敏感或需要快速部署，可以适当减小 `M`。

### 2. efConstruction：建索引时的搜索范围

`efConstruction` 控制构建索引时的搜索范围。

它主要影响离线建图质量。

```text
efConstruction 越大
  → 建图时搜索更充分
  → 图结构质量更好
  → 后续召回率可能更高
  → 建索引更慢
  → 构建阶段资源消耗更高
```

适合调大的场景：

- 离线批量构建索引。
- 数据结构复杂。
- 召回率要求高。
- 可以接受较长构建时间。

如果数据频繁更新、构建时间敏感，就不能盲目调大。

### 3. efSearch：查询时的搜索范围

`efSearch` 控制查询时探索多少候选节点。

它直接影响线上查询质量和延迟。

```text
efSearch 越大
  → 查询时探索更多节点
  → 召回率更高
  → 查询延迟更高
```

```text
efSearch 越小
  → 查询更快
  → 召回可能下降
```

如果业务要求实时响应，可以适当降低 `efSearch`。

如果业务要求更高召回，可以增大 `efSearch`，但要观察 P95 / P99 延迟。

## 六、SQ8 量化压缩是什么

HNSW 内存压力大，除了调整参数，还可以通过量化压缩减少向量本身的存储成本。

SQ8 可以理解为 8 位标量量化。

它把原本高精度浮点向量压缩成 8 位表示。

例如：

```text
float32 向量
  → SQ8 量化
  → int8 近似表示
```

好处是：

- 向量存储明显变小。
- 索引加载和存储压力降低。
- 内存占用下降。
- 某些场景下构建和查询成本也会下降。

代价是：

- 精度会有一定损失。
- 召回率可能下降。
- 需要用评估集验证是否可接受。

文稿中的实验结果可以概括为：

```text
原始 HNSW
  → 构建耗时约 27.73 秒
  → 内存占用约 48.83 MB

HNSW + SQ8
  → 构建耗时约 4.65 秒
  → 内存约降到原来的 1/4
```

这个结果说明：

> SQ8 对 HNSW 的内存压力缓解明显，但它不是免费优化，必须关注精度和召回损失。

## 七、SQ8、SQ16、PQ、OPQ 的取舍

量化压缩不是只有 SQ8。

常见方案包括：

| 方案 | 特点 | 优势 | 代价 | 适合场景 |
|---|---|---|---|---|
| SQ8 | 8 位标量量化 | 压缩率高，内存低 | 精度损失更明显 | 移动端、嵌入式、内存受限 |
| SQ16 | 16 位标量量化 | 精度比 SQ8 更稳 | 内存占用更高 | 服务器、云服务、高精度检索 |
| PQ | 乘积量化 | 进一步压缩向量 | 有编码/解码计算成本 | 大规模向量库 |
| OPQ | 优化乘积量化 | 比 PQ 更关注量化误差 | 训练和实现复杂度更高 | 高压缩率同时要求精度 |

可以这样理解：

```text
SQ8
  → 更省内存
  → 精度损失更明显

SQ16
  → 更保精度
  → 内存节省没那么激进

PQ / OPQ
  → 更适合大规模压缩
  → 需要额外计算和训练成本
```

## 八、典型场景组合方案

### 1. 内存敏感型

适合：

- 移动端。
- 嵌入式。
- 边缘设备。
- 轻量级推荐系统。
- 内存受限的 RAG 服务。

推荐：

```text
HNSW + SQ8
```

特点：

- 内存占用低。
- 构建和加载成本更低。
- 精度略有损失。
- 需要验证 Recall@K 是否可接受。

### 2. 高精度服务器型

适合：

- 云服务。
- 服务器环境。
- 图像检索。
- 视频匹配。
- 高召回要求的 RAG。

推荐：

```text
HNSW + SQ16
```

或者：

```text
HNSW + SQ16 + PQ / OPQ
```

特点：

- 精度更稳。
- 内存节省不如 SQ8。
- 更适合资源相对充足的环境。

### 3. 速度和精度平衡型

推荐：

```text
HNSW + PQ / OPQ
```

适合在存储压力较大，但又不能接受过多精度损失的场景中使用。

需要注意：

> 压缩节省的是空间，但压缩和解压缩会消耗 CPU / GPU 算力。

所以压缩方案不是越多越好，也要看计算资源是否充足。

## 九、调优时应该看哪些指标

HNSW 调优不能只看单个指标。

至少要同时观察：

| 指标 | 说明 |
|---|---|
| Recall@K | 前 K 条是否包含正确结果 |
| MRR | 正确结果排在第几位 |
| P50 / P95 / P99 延迟 | 查询速度和长尾延迟 |
| 内存占用 | 向量和图结构总内存 |
| 索引构建时间 | 建图和量化耗时 |
| QPS | 并发查询能力 |
| 答案正确率 | RAG 最终回答是否正确 |
| Faithfulness | 答案是否忠实于召回上下文 |

推荐用评估集做参数对比：

```text
固定数据集
  → 固定查询集
  → 改 M / efConstruction / efSearch
  → 对比 Recall@K 和延迟
  → 加 SQ8 / SQ16
  → 对比内存、速度和答案质量
```

没有评估集时，不建议凭感觉调参数。

## 十、工程落地中的坑

### 1. 不要把参数都调大

`M`、`efConstruction`、`efSearch` 变大通常会提升召回，但也会增加内存、构建耗时和查询延迟。

生产调优的目标不是参数最大，而是业务指标达标。

### 2. 不要只看平均延迟

HNSW 查询可能平均延迟不错，但长尾延迟仍然影响线上体验。

要重点看：

- P95。
- P99。
- 冷启动。
- 索引加载时间。

### 3. 不要量化后不评估召回损失

SQ8 可以显著省内存，但可能损失召回。

量化前后必须对比：

- Recall@K。
- MRR。
- 最终答案正确率。

### 4. 不要忽略硬件环境

FAISS 有 CPU 和 GPU 版本。

GPU 版本通常依赖 NVIDIA CUDA。

如果是 Mac 或非 NVIDIA 环境，不要直接安装 `faiss-gpu`。

切换 FAISS 安装版本后，Notebook 或运行环境需要重启，避免旧库状态影响测试。

### 5. 不要用小样本结论指导生产

几十条或几百条向量无法体现 HNSW 在大规模数据下的真实表现。

调优要尽量使用：

- 接近生产的数据规模。
- 接近生产的查询分布。
- 接近生产的硬件环境。

### 6. 不要忽略前置质量

HNSW 只能提升近邻搜索效率。

它不能修复：

- 分块语义割裂。
- embedding 模型不适合业务。
- 文档解析错误。
- OCR 错漏。
- 元数据过滤错误。

这些问题要在前置链路解决。

## 十一、推荐落地路径

### 1. 先建立未压缩 HNSW 基线

先用原始 HNSW 跑一组基线：

- Recall@K。
- 查询延迟。
- 内存占用。
- 构建时间。

这一步用于判断 HNSW 本身是否适合业务。

### 2. 调整 M 和 efConstruction

先调离线索引质量：

```text
M
efConstruction
```

目标是让基础召回达标。

### 3. 调整 efSearch

再调线上查询阶段：

```text
efSearch
```

目标是在召回和延迟之间找到平衡点。

### 4. 引入 SQ8 / SQ16

如果内存成为瓶颈，再引入量化压缩。

推荐对比：

```text
原始 HNSW
HNSW + SQ8
HNSW + SQ16
```

观察内存下降和召回损失是否可接受。

### 5. 大规模场景再考虑 PQ / OPQ

如果数据规模继续扩大，可以引入 PQ / OPQ。

但要同时评估：

- 压缩收益。
- 查询延迟。
- 召回损失。
- CPU / GPU 计算成本。

### 6. 最后接入完整 RAG 评估

索引调优最终要回到 RAG 效果。

除了检索指标，还要看：

- 最终答案是否正确。
- 答案是否引用了正确上下文。
- 召回内容是否有噪声。
- 用户反馈是否改善。

## 十二、最终沉淀

HNSW 适合高召回、低延迟的向量检索，但它不是无成本方案。

它的工程复杂度主要来自图索引本身：图连接越密、搜索越深，召回通常越好，但内存、构建成本和查询延迟也会上升。

SQ8、SQ16、PQ、OPQ 这类量化压缩技术可以降低向量存储成本，但会带来不同程度的精度损失或计算开销。

一句话总结：

> HNSW 调优的关键，是通过 `M`、`efConstruction`、`efSearch` 控制图索引质量和搜索深度，通过 SQ8/SQ16/PQ/OPQ 控制内存和精度损失，最终在召回率、延迟、构建成本和资源预算之间找到业务可接受的平衡点。
