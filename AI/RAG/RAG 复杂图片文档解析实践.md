# RAG 复杂图片文档解析实践

## 一、问题背景

RAG 系统处理普通文本时，核心问题通常是分块、索引、召回和生成。

但在真实业务里，很多知识并不是天然文本，而是存在于图片、扫描件、拍照文档、图片型 PDF、表格截图、宣传页、票据、合同扫描件和带复杂版面的资料中。

这些内容如果直接整页 OCR，通常会出现几个问题：

- 图片倾斜、弯曲或透视变形，导致标题、正文或关键字段漏识别。
- 一页里同时存在标题、正文、图片、公式、表格，整页 OCR 后阅读顺序错乱。
- 表格被识别成普通文本，行列关系、单元格关系和表头关系丢失。
- 图片中的文字虽然被识别出来，但没有保留 bbox、区域类型和置信度，后续无法回溯和纠错。
- 所有内容都走同一套 OCR 流程，导致文本、表格、公式、图片的处理方式不匹配。

> [!summary] 核心判断
> 复杂图片文档进入 RAG 前，关键不是“把图片转成文字”，而是先完成图像校正、版面区域检测和区域级分流解析，再把结果转成可检索、可回溯、可结构化使用的知识单元。

## 二、核心结论

复杂图片文档的 RAG 处理链路可以概括为：

```text
原始图片 / 扫描件 / 图片型 PDF
  → 图像质量判断
  → 文本图像校正
  → 版面区域检测
  → 按区域类型分流
  → OCR / 表格识别 / 公式识别 / 图片处理
  → Markdown / JSON / HTML 结构化输出
  → 分块
  → 索引
  → 检索问答
```

它解决的不是向量检索算法本身，而是 RAG 入库前的内容质量问题。

如果图片内容在入库前已经漏识别、错位或结构丢失，后续 embedding、rerank 和 LLM 生成都很难补救。

## 三、它在 RAG 链路中的位置

常规 RAG 链路可以简化为：

```text
文档接入
  → 内容解析
  → 清洗
  → 分块
  → 向量化 / 全文索引
  → 检索
  → 生成
```

复杂图片文档解析属于其中的“内容解析”阶段，但它比普通文本解析更复杂。

普通文本解析通常只需要读取正文和元数据，而复杂图片文档至少要解决：

1. 图片是否需要旋转、拉直、去噪、增强。
2. 页面中有哪些区域：标题、正文、表格、公式、图片、页码、页脚。
3. 每个区域应该走什么解析策略。
4. 解析结果如何保留位置、结构和置信度。
5. 如何输出给后续分块和检索使用。

因此，复杂图片文档解析更像是 RAG 知识入库前的“视觉理解层”。

## 四、第一步：文本图像校正

文本图像校正解决的是图片本身不规整的问题。

常见问题包括：

- 图片倾斜。
- 文本行弯曲。
- 拍摄角度导致透视变形。
- 扫描件边缘不平。
- 背景复杂导致文字区域不稳定。
- 页面局部变形，导致普通 OCR 漏识别。

这一步的目标不是让图片对人眼更好看，而是让文字行、区域边界和后续检测框对机器更友好。

例如一张拍照文档中，标题区域有明显弯曲，普通版面检测可能漏掉标题。先做文本图像校正后，标题行会更接近水平直线，后续 OCR 和版面区域检测更容易识别出来。

工程上可以把文本图像校正设计成一个可选前置模块：

```text
图片质量检测
  → 判断是否倾斜 / 弯曲 / 透视变形
  → 如果异常，则进入文本图像校正
  → 用校正后的图片进入后续 OCR 和版面检测
```

这样做的好处是：

- 不需要所有图片都走重处理流程。
- 对特殊图片进行针对性增强。
- 可以接入现有 RAG 解析流程，而不是重写整套系统。

## 五、第二步：版面区域检测

版面区域检测解决的是“页面内容混在一起”的问题。

一页复杂图片里可能同时包含：

- 标题。
- 正文。
- 图片。
- 表格。
- 公式。
- 页码。
- 页眉页脚。
- 图注。
- 装饰性边框。

如果直接整页 OCR，系统只能得到一段顺序不稳定的文本，后续很难判断哪些是标题、哪些是正文、哪些是表格或图片说明。

版面区域检测的作用是先把页面拆成多个区域，并为每个区域输出：

```json
{
  "bbox": [x1, y1, x2, y2],
  "label": "title",
  "score": 0.93
}
```

这里的关键字段包括：

- `bbox`：区域在图片中的位置坐标。
- `label`：区域类型，例如 title、text、image、formula、table。
- `score`：识别置信度。

有了这些信息，后续就可以按类型分流：

| 区域类型 | 推荐处理方式 |
|---|---|
| title | 作为标题层级或 chunk metadata |
| text | 普通 OCR + 阅读顺序恢复 |
| table | 表格分类、单元格检测、结构识别 |
| formula | 公式识别或保留为图片引用 |
| image | 图片理解、图注抽取或原图索引 |
| page number | 通常作为 metadata，不进入正文 |
| footer / watermark | 根据业务判断过滤或降权 |

> [!note]
> 版面区域检测的价值不是直接提升 embedding，而是避免不同类型内容在 OCR 阶段被混成一段错误文本。

## 六、第三步：按区域类型分流解析

复杂图片文档不能所有区域都走同一套 OCR。

更合理的方式是：

```text
版面区域检测结果
  → title / text 区域：文本 OCR
  → table 区域：表格结构识别
  → formula 区域：公式识别
  → image 区域：图片理解或保留引用
  → 页码 / 页脚 / 水印：过滤或写入 metadata
```

这种设计有几个好处：

1. 文本区域可以重点优化阅读顺序和语义完整性。
2. 表格区域可以保留行列结构，而不是被拍平成一段文本。
3. 公式区域可以避免被错误识别成普通字符。
4. 图片区域可以保留原图、图注和上下文关系。
5. 页码、页脚、水印可以作为元数据或噪声处理，不污染正文。

这也是复杂图片文档解析和普通 OCR 最大的区别：

> 普通 OCR 关心“识别出了哪些字”，复杂图片文档解析关心“这些字属于哪个区域、什么结构、能否被后续 RAG 正确使用”。

## 七、表格区域的专项处理

表格是复杂图片文档里最容易丢结构的内容。

如果只做普通 OCR，表格很容易变成类似下面的文本：

```text
姓名 年龄 部门 张三 28 产品 李四 31 技术
```

这种结果虽然有文字，但字段关系已经不稳定，后续检索和问答很容易出错。

表格区域通常需要单独做三类处理。

### 1. 表格分类

先判断表格类型：

- 有线表格。
- 无线表格。
- 复杂合并单元格表格。
- 普通二维表。
- 嵌套表或多表混排。

这个判断会影响后续策略。

例如：

- 有线表格可以优先利用线框检测。
- 无线表格需要根据文本块、对齐关系和间距推断行列。
- 合并单元格表格需要额外恢复 rowspan / colspan。

### 2. 单元格检测

单元格检测的目标是定位每个 cell 的边界。

也就是先知道：

```text
第 1 行第 1 列在哪里
第 1 行第 2 列在哪里
第 2 行第 1 列在哪里
……
```

然后再把 OCR 文本按 bbox 落到对应单元格中。

这比“整页 OCR 后再猜表格结构”更可靠。

推荐流程是：

```text
检测表格区域
  → 检测单元格 bbox
  → 对每个 cell 内部做 OCR
  → 根据 cell 坐标恢复行列关系
  → 输出 Markdown / HTML / JSON
```

### 3. 表格结构识别

表格结构识别的目标是把图片表格变成可编辑、可检索、可回溯的结构。

常见输出包括：

- HTML table。
- Markdown table。
- JSON table。
- CSV。
- 带 bbox 的结构化单元格列表。

更适合 RAG 的输出通常不是单一格式，而是组合格式：

```json
{
  "type": "table",
  "page": 3,
  "bbox": [120, 220, 880, 640],
  "html": "<table>...</table>",
  "markdown": "| 字段 | 值 |\\n|---|---|",
  "cells": [
    {
      "row": 0,
      "col": 0,
      "text": "姓名",
      "bbox": [120, 220, 260, 260],
      "confidence": 0.98
    }
  ]
}
```

这样既方便人读，也方便程序回溯、纠错和检索。

## 八、PaddleOCR 单功能模块的工程价值

注意：不一定要完整接入 PaddleOCR 或 PP-ChatOCR 的全栈方案。

很多企业已经有自己的 RAG 解析流程，只是在某些特殊场景上能力不足。

这时更合理的做法是按模块接入：

| 模块 | 解决的问题 |
|---|---|
| 文本图像校正 | 处理扭曲、倾斜、透视变形 |
| 版面区域检测 | 识别标题、正文、图片、公式、表格等区域 |
| 表格分类 | 判断表格类型，为后续策略选择做准备 |
| 单元格检测 | 定位每个表格 cell 的 bbox |
| 表格结构识别 | 将图片表格恢复成 HTML / JSON / Markdown |

这种方式的优势是：

- 轻量接入，不需要替换现有 RAG 系统。
- 可以只针对问题文档启用特殊处理。
- 每个模块可以独立调参、独立评估。
- 失败时更容易定位是图像问题、版面问题、OCR 问题还是结构恢复问题。

## 九、推荐的工程落地流程

一套可落地的复杂图片文档解析流程可以设计成下面这样。

### 1. 文档接入和类型判断

先判断输入类型：

- 普通图片。
- 扫描件。
- 图片型 PDF。
- 图文混排 PDF。
- 表格截图。
- 拍照文档。

同时记录基础 metadata：

- 文件名。
- 页码。
- 图片尺寸。
- 来源路径。
- 文档类型。
- 解析时间。

### 2. 图像质量检测

判断是否存在：

- 倾斜。
- 模糊。
- 低分辨率。
- 透视变形。
- 背景噪声。
- 文字区域弯曲。

如果质量较差，先做图像校正和增强。

### 3. 版面区域检测

对页面进行区域检测，得到：

- 区域 bbox。
- 区域 label。
- 置信度 score。
- 区域阅读顺序。

低置信度区域不要直接丢弃，应该保留到人工复核或二次模型处理队列。

### 4. 区域级解析

不同区域走不同处理逻辑：

```text
文本区域 → OCR + 阅读顺序恢复
表格区域 → 表格分类 + 单元格检测 + 结构识别
公式区域 → 公式识别或图片引用
图片区域 → 图像理解 / 图注抽取 / 原图保留
页码页脚 → metadata 或过滤
```

### 5. 结构化输出

最终不要只输出纯文本，而应输出多层结构：

```text
Markdown：面向人读和大模型上下文
JSON：面向程序处理和回溯
HTML：适合表格结构表达
metadata：保留来源、页码、bbox、置信度
```

推荐的最小输出字段包括：

```json
{
  "content": "解析后的文本或 Markdown",
  "type": "text/table/formula/image",
  "source": "原文件名",
  "page": 1,
  "bbox": [0, 0, 100, 100],
  "confidence": 0.95,
  "parser": "layout_detection + ocr",
  "raw": "原始 OCR 结果"
}
```

### 6. 分块和索引

进入 RAG 分块时，要避免把区域结构再次切坏。

建议：

- 标题和正文保持层级关系。
- 表格不要按普通段落粗暴切碎。
- 表格可以按行、业务实体或父子块方式入库。
- 图片区域需要保留原图引用和图注。
- bbox、页码、区域类型写入 metadata。

## 十、工程落地中的坑

### 1. 不要整页 OCR 后直接入库

整页 OCR 看似简单，但对复杂图片文档很容易造成阅读顺序错乱、表格结构丢失和噪声混入。

### 2. 图像校正不是越多越好

校正可能提升 OCR，也可能引入形变。

建议只对低质量图片、倾斜图片、弯曲图片启用校正，并保留原图和校正图，方便回溯。

### 3. bbox 和置信度必须保留

如果只保留文本，不保留 bbox 和 confidence，后续很难判断某段内容来自哪里、是否可靠、是否需要人工复核。

### 4. 表格不能只输出 Markdown

Markdown 表格适合阅读，但不一定足够表达复杂表格。

复杂表格建议同时保留：

- Markdown。
- HTML。
- JSON cells。
- 原始 bbox。
- 单元格置信度。

### 5. 区域分类阈值不能拍脑袋

置信度阈值过高会漏掉标题、图注、小字。

置信度阈值过低会把正文、标题、图片噪声混在一起。

阈值应该基于具体业务文档样本评估，而不是固定套用默认参数。

### 6. 不要把页码、页脚、水印直接当正文

这些内容如果进入正文 chunk，会污染检索结果。

更合理的做法是：

- 页码进入 metadata。
- 页脚按业务判断是否保留。
- 水印、装饰性元素默认过滤。

### 7. 复杂图片解析需要质量回流机制

解析失败不应该静默进入知识库。

建议对以下内容进入复核队列：

- 低置信度区域。
- OCR 识别为空但区域面积较大的块。
- 表格结构识别失败。
- 表格单元格数量异常。
- 标题缺失但正文存在。
- 页面大面积未被任何区域覆盖。

## 十一、最终沉淀

复杂图片文档的 RAG 处理，本质上是把“视觉信息”转换成“可检索知识”的过程。

它不是简单 OCR，而是一个分层解析流程：

```text
图像校正
  → 版面区域检测
  → 区域级分流解析
  → 结构化输出
  → 带来源和置信度入库
```

真正可用的工程方案应该满足四个标准：

1. **信息完整**：标题、正文、表格、公式、图片说明不能轻易丢失。
2. **结构保留**：表格、区域、阅读顺序和层级关系要尽量保留。
3. **结果可回溯**：每段内容都能回到原图、原页和原始 bbox。
4. **质量可评估**：置信度、失败样本和人工复核机制要进入系统设计。

一句话总结：

> 复杂图片文档进入 RAG 前，应先通过图像校正和版面区域检测把页面拆成可理解的结构，再对文本、表格、公式、图片分别解析，最后带着 bbox、置信度和来源信息结构化入库，从源头提升检索和问答质量。
