# RAG 自动化文档预处理流水线设计实践

## 一、问题背景

RAG 项目早期通常会先验证“能不能问答”，因此很多文档入库流程是手工完成的：手动上传 PDF、手动 OCR、手动清洗文本、手动分段、手动补元数据。

但一旦进入真实业务场景，文档来源会变得复杂：

- 有 PDF、图片、扫描件、Word、TXT 等多种格式。
- 有些文档需要 OCR，有些文档可以直接抽取文本。
- 不同文档需要不同清洗规则和分段策略。
- 文档入库后需要保留来源、作者、路径、权限、时间等元数据。
- 文档量变大后，单机同步脚本难以支撑批量处理、失败重试和定时更新。

这时，RAG 的关键问题不再只是“怎么检索”，而是“如何稳定、批量、可维护地把文档变成高质量知识库内容”。

> [!summary] 核心判断
> RAG 文档预处理流水线的核心，不是把 OCR、清洗、分段、上传这些步骤写成一个脚本，而是把它们拆成可配置、可替换、可观测、可异步执行的模块化 pipeline。

## 二、核心结论

RAG 自动化文档预处理流水线应该围绕四个目标设计：

1. **可配置**：OCR 引擎、清洗规则、分段参数、上传目标、元数据字段都从配置文件读取，避免硬编码。
2. **可扩展**：OCR、知识库平台、分段策略、元数据绑定方式都通过模块或适配器替换。
3. **可追踪**：每个文档、每个分段、每次上传和每个元数据绑定结果都能回溯。
4. **可批量运行**：通过异步队列和任务调度支持大批量文档处理、失败重试和定时同步。

一句话概括：

> RAG 入库工程化的关键，是把“文档解析 → 文本清洗 → 分段 → 上传知识库 → 绑定元数据”做成配置驱动的自动化流水线，而不是依赖一次性脚本和人工上传。

## 三、它在 RAG 链路中的位置

完整 RAG 链路可以分为：

```text
文档接入
  → 文档解析
  → 文本清洗
  → 分段
  → 元数据绑定
  → 索引入库
  → 检索
  → 重排
  → 生成
  → 评估反馈
```

这篇文档关注的是“索引入库之前”的自动化预处理阶段。

它和检索算法、rerank、生成提示词不是同一层问题，但它会直接影响后续效果：

- OCR 漏识别，后续无法召回。
- 清洗过度，关键字段被删掉。
- 分段不合理，召回上下文割裂。
- 元数据缺失，答案无法溯源。
- 入库过程不可追踪，线上问题难以定位。

因此，预处理流水线是 RAG 知识质量的基础设施。

## 四、推荐技术流程

推荐把预处理链路设计成下面的结构：

```text
原始文件
  → 文件识别与任务创建
  → OCR / 文本抽取
  → 原始解析结果标准化
  → 文本清洗
  → 分段
  → 结构化输出
  → 知识库 / 向量库写入
  → 元数据绑定
  → 状态记录与失败回流
```

更工程化的实现可以拆成五层：

```text
配置层
  → 管理 OCR、分段、平台、元数据、队列等参数

解析层
  → 负责 OCR、PDF 解析、Word 解析、图片解析

处理层
  → 负责清洗、标准化、分段、结构化

适配层
  → 负责写入 Dify、RAGFlow、向量库或自研知识库

调度层
  → 负责异步队列、定时任务、失败重试、状态记录
```

## 五、第一阶段：配置中心化

自动化流水线最先要解决的是配置分散问题。

如果 OCR 地址、API Key、分段长度、知识库 ID、上传接口、元数据字段都散落在代码中，后续会出现几个问题：

- 换 OCR 引擎需要改代码。
- 换知识库平台需要改主流程。
- 不同环境部署容易配置错。
- 参数调整没有版本记录。
- 多人协作时难以维护。

推荐把所有外部依赖和可变参数集中到配置文件中，例如 `config.yaml`：

```yaml
ocr:
  engine: paddleocr
  api_url: http://localhost:8000/ocr
  keep_raw_json: true

processor:
  remove_url: true
  remove_extra_space: true
  chunk_size: 500
  separators:
    - "\n\n"
    - "\n"
    - "。"

knowledge_base:
  provider: dify
  api_base: https://api.dify.ai
  dataset_id: xxx
  api_key: xxx

metadata:
  fields:
    - source_path
    - author
    - created_at
    - file_type

queue:
  enabled: true
  broker: redis://localhost:6379/0
```

这里的重点不是 YAML 本身，而是把 pipeline 的“行为变化”从代码中抽离出来。

## 六、第二阶段：OCR 和文档解析模块化

文档进入 RAG 之前，第一步是把不同来源的内容解析成统一的中间结果。

常见输入包括：

- 图片。
- 扫描件。
- 图片型 PDF。
- 文本型 PDF。
- Word。
- TXT。
- Markdown。

对于图片和扫描件，需要 OCR；对于 Word、TXT、Markdown，可以直接抽取文本；对于 PDF，则要判断是否有文本层，必要时再走 OCR。

推荐做法是封装一个解析模块，例如：

```text
DocumentParser
  → ImageOCRParser
  → PDFTextParser
  → PDFOCRParser
  → WordParser
  → TextParser
```

OCR 模块可以设计成可替换的引擎：

```text
OCR Engine
  → PaddleOCR
  → 云 OCR
  → Tesseract
  → 自研 OCR 服务
```

这一层有一个关键原则：

> OCR 层不要太早只返回纯文本，应尽量保留完整 JSON，包括文字、坐标、置信度、区域信息和原始结构。

原因是不同 OCR 引擎返回结构不一致，如果在 OCR 层过早写死字段，例如只取 `text`，后续切换 OCR 引擎时会很脆弱。

更合理的做法是：

```text
OCR 原始输出
  → 保留 raw_json
  → 统一标准化为内部结构
  → 下游再决定使用哪些字段
```

## 七、第三阶段：文本清洗和分段

解析完成后，内容还不能直接入库。

需要先做清洗和分段。

### 1. 文本清洗

常见清洗动作包括：

- 去除多余空格。
- 去除无意义 URL。
- 去除扫描噪声字符。
- 去除重复页眉页脚。
- 修复明显编码问题。
- 统一换行和标点。
- 处理异常控制字符。

但清洗不能过度。

例如，URL 在普通知识问答里可能是噪声，但在接口文档、产品文档、合同附件里可能是关键信息。

因此清洗规则应该按业务配置，而不是写死成全局规则。

### 2. 文本分段

分段是 RAG 入库质量的关键步骤。

在自动化 pipeline 中，分段模块至少要支持：

- 按字符长度切分。
- 按段落或换行切分。
- 按标题层级切分。
- 按语义边界切分。
- 保留 overlap。
- 保留父子块关系。

早期 MVP 可以先用简单长度切分，但工程化阶段应该逐步升级为结构感知分段。

更合理的设计是让 `TextProcessor` 提供统一入口：

```text
TextProcessor.process(input)
  → 判断输入类型
  → 标准化为文本或结构化对象
  → 清洗
  → 分段
  → 输出 segments
```

内部可以用策略映射代替大量 `if-else`：

```text
dict/json → _process_json()
str       → _process_text()
table     → _process_table()
markdown  → _process_markdown()
```

## 八、第四阶段：知识库写入适配器

文稿中使用 Dify 作为落地案例，但这套设计不应该绑定 Dify。

更通用的设计是抽象出知识库写入适配器：

```text
KnowledgeBaseAdapter
  → DifyAdapter
  → RAGFlowAdapter
  → VectorDBAdapter
  → ElasticsearchAdapter
  → CustomAPIAdapter
```

适配器负责处理平台差异：

- API 地址。
- 鉴权方式。
- Dataset / Collection / Index ID。
- 文档创建接口。
- 文本上传接口。
- 分段上传格式。
- 元数据绑定方式。

以 Dify 为例，入库时需要关注：

- `API Key`。
- `Dataset ID`。
- 上传原始文件还是上传文本。
- 上传后返回的 `document_id`。
- 后续是否需要绑定 metadata。

如果换成向量库，则可能变成：

- collection 名称。
- embedding 模型。
- chunk ID。
- vector。
- payload metadata。

所以 Dify 只是一个平台实现，真正应该沉淀的是“适配层”思想。

## 九、第五阶段：元数据动态绑定

元数据不是可有可无的附加信息，而是 RAG 工程化中非常关键的部分。

常见元数据包括：

- `source_path`：原始文件路径。
- `file_name`：文件名。
- `page`：页码。
- `chunk_index`：分段编号。
- `author`：作者。
- `created_at`：创建时间。
- `file_type`：文件类型。
- `department`：所属部门。
- `permission`：权限范围。
- `parser`：解析器版本。
- `confidence`：识别置信度。

元数据至少有四个作用：

1. **溯源**：回答引用内容后，可以定位到原始文件。
2. **过滤**：按部门、权限、时间、文档类型筛选。
3. **排障**：识别某个 chunk 是由哪个解析器、哪次任务生成。
4. **评估**：统计哪些来源文档质量差、失败率高、召回率低。

工程上要注意：

> 元数据绑定应该和文档写入解耦，但必须通过稳定 ID 建立关联。

典型流程是：

```text
上传文档 / 分段
  → 返回 document_id / chunk_id
  → 根据 ID 绑定 metadata
  → 记录绑定状态
```

如果平台 API 发生变化，例如 Dify metadata 端点更新，应该在适配层修复，而不是让主流程到处改调用逻辑。

## 十、第六阶段：异步队列和批量调度

当文档数量很少时，一个同步脚本可以工作。

但真实场景中，文档入库通常是 IO 密集型任务：

- 文件读取。
- OCR 调用。
- 网络上传。
- API 限流等待。
- 元数据绑定。
- 失败重试。

这类任务适合用异步队列处理，例如：

```text
Celery + Redis
```

推荐拆成几个任务：

```text
scan_folder_task
  → parse_document_task
  → clean_and_segment_task
  → upload_segments_task
  → bind_metadata_task
  → record_status_task
```

这样可以支持：

- 批量文档入队。
- 多 worker 并发处理。
- 失败重试。
- 定时扫描目录。
- 限速控制。
- 任务状态追踪。

例如每天凌晨 3 点扫描某个文件夹，把新增 PDF 和图片自动处理后写入知识库。

这一步是从 demo 脚本走向生产系统的分界线。

## 十一、工程落地中的坑

### 1. 不要把 Dify API 写死在主流程里

Dify 可以作为一个落地平台，但不要让主流程直接依赖 Dify 的接口细节。

更合理的做法是把 Dify 封装成 adapter。

这样换成 RAGFlow、向量库或自研知识库时，只替换适配层。

### 2. OCR 层不要过早丢弃原始结构

只保留纯文本会让后续无法处理 bbox、置信度、表格结构和版面信息。

建议保留：

- 原始 OCR JSON。
- 标准化文本。
- bbox。
- confidence。
- page。
- parser 信息。

### 3. 清洗规则不能全局粗暴套用

例如 URL、页脚、特殊符号在某些场景是噪声，在另一些场景是关键信息。

清洗规则应该按文档类型和业务场景配置。

### 4. 分段不能只看长度

简单按 500 字切分适合 demo，但不适合复杂文档。

生产环境要逐步支持：

- 标题感知。
- 表格保护。
- 父子分块。
- overlap。
- 语义边界。

### 5. 元数据字段要提前设计

如果入库时没有记录来源、页码、权限和解析器版本，后续很难做溯源、过滤、排障和评估。

元数据应该是 pipeline 设计的一部分，而不是后期补丁。

### 6. API 变更要隔离在适配层

平台接口经常变化。

如果主流程到处直接调用平台 API，接口升级会带来大量修改。

适配层应该对外暴露稳定方法，例如：

```text
upload_document()
upload_text_segments()
bind_metadata()
list_datasets()
```

内部再适配具体平台的新旧接口。

### 7. 批量任务必须有状态记录

自动化 pipeline 不能只看最终是否成功。

至少要记录：

- 待处理。
- 解析中。
- 清洗中。
- 分段完成。
- 上传成功。
- 元数据绑定成功。
- 失败原因。
- 重试次数。

否则一旦处理大量文档，很难知道哪些文档失败、失败在哪一步。

## 十二、推荐落地路径

可以按四个阶段推进。

### 1. MVP 阶段

先跑通最小链路：

```text
单个文件
  → OCR / 文本抽取
  → 简单清洗
  → 简单分段
  → 上传知识库
```

目标是验证链路可用，不追求复杂架构。

### 2. 配置化阶段

把以下内容抽到配置文件：

- OCR 引擎。
- API 地址。
- API Key。
- 分段参数。
- 目标知识库。
- 元数据字段。

目标是减少硬编码。

### 3. 模块化阶段

拆出独立模块：

- Parser。
- OCR Engine。
- TextProcessor。
- Chunker。
- KnowledgeBaseAdapter。
- MetadataManager。

目标是让每个模块可以独立测试、替换和扩展。

### 4. 工程化阶段

加入：

- Celery / Redis 异步队列。
- 定时任务。
- 失败重试。
- 状态记录。
- 质量评估。
- 人工复核队列。

目标是支持批量文档持续入库。

## 十三、质量评估指标

自动化预处理流水线需要评估，不然只能凭感觉判断质量。

建议至少关注这些指标：

| 指标 | 说明 |
|---|---|
| 解析成功率 | 成功提取内容的文档占比 |
| OCR 空结果率 | OCR 后没有有效文本的比例 |
| 分段成功率 | 成功生成 chunk 的文档占比 |
| 元数据完整率 | 必填 metadata 是否齐全 |
| 入库成功率 | 上传知识库成功的比例 |
| 失败重试成功率 | 重试后恢复成功的比例 |
| 平均处理耗时 | 单文档从接入到入库的耗时 |
| 问答召回命中率 | 文档入库后是否能被正确召回 |

其中最容易被忽视的是元数据完整率。

如果元数据不完整，RAG 系统虽然能回答，但无法稳定溯源、过滤和排障。

## 十四、最终沉淀

RAG 自动化文档预处理流水线，本质上是把文档入库从“人工操作”升级为“工程系统”。

它不应该绑定某一个平台，也不应该只是一个顺序执行脚本。

更合理的设计是：

```text
配置驱动
  → 模块化解析
  → 结构化处理
  → 平台适配
  → 元数据绑定
  → 异步调度
  → 状态追踪
```

其中 Dify、RAGFlow、向量库、自研知识库都只是不同的写入目标；真正通用的是 pipeline 的设计方法。

一句话总结：

> RAG 文档预处理工程化的关键，是把 OCR、解析、清洗、分段、上传和元数据绑定拆成配置驱动的模块化流水线，并通过适配器和异步队列支持不同平台、批量任务和持续入库。
