# RAG 切片语义割裂解决方案与最佳实践

## 一、问题背景

在 RAG 系统里，文档不会整体丢给大模型，而是会先被解析、切片、向量化，再通过检索召回相关片段。

如果切片策略不好，原本连贯的一段语义可能被切断，后续检索和生成都会受到影响。

典型问题可以用几句话概括：

- 一个完整观点被切成两块，检索只召回前半句，模型就缺少关键上下文。
- chunk 太小，信息不完整；chunk 太大，又会混入噪声，影响模型判断。
- overlap 设置太小补不回上下文，设置太大又会造成大量重复和无关内容。
- 固定长度切片不懂语义，可能把段落、句子、表格、定义、案例硬切开。
- 向量检索只召回“相似片段”，但如果正确语义分散在多个 chunk 里，模型仍然答不好。

> [!summary] 核心判断
> RAG 切片的目标不是“把文档切成固定大小”，而是把文档切成语义完整、大小可控、可检索、低噪声的知识单元。

## 二、核心解决方案

切片语义割裂问题没有单一最优解，最佳实践通常是组合策略：

> 先保留文档天然结构，再根据文档类型选择结构切分、句子切分、语义切分或滑动窗口；对过大的语义块再做二次切分，必要时结合关键词保护、overlap 和父子块检索补全上下文。

整体链路可以概括为：

```text
原始文档
  → 文档解析：保留标题、段落、表格、代码、页码等结构
  → 识别关键词、术语、标题、条款、字段等边界
  → 按结构 / 句子 / 语义选择切分策略
  → 检查 chunk 大小
  → 过大 chunk 用滑动窗口二次切分
  → 必要时使用父子块或命题化检索补全上下文
  → 保留 overlap、元数据和回溯关系
  → 入向量库 / 全文索引
  → 召回后重排与上下文补全
```

这套方案解决两个核心矛盾：

- 结构切分优先保留文档天然边界，避免把标题、表格、代码、条款和正文混切。
- 语义切分改善相邻文本的话题边界判断。
- 滑动窗口解决局部上下文保留和大小可控问题。
- 父子块和命题化检索解决“小块检索精准，但生成上下文不足”的问题。

## 三、第一阶段：不要直接依赖 Token 切片

Token 切片是最简单的方式：按固定 token 数切。

优点：

- 实现简单。
- 长度可控。
- 适合模型上下文很小的场景。

缺点：

- 容易把句子切断。
- 对中文语义不友好。
- overlap 补偿有限。
- 对复杂文档不稳定。

适合场景：

- 简单文本。
- 对语义完整性要求不高。
- 强制需要控制 token 长度。

Token 切片可以作为兜底策略，但不建议作为复杂 RAG 的默认切片方案。

## 四、第二阶段：使用句子切片作为基础方案

句子切片会优先保证句子完整，再考虑 chunk size。

相比 Token 切片，它至少不会把一句话从中间切断，因此更适合作为普通文本的基础切片方案。

常见流程：

```text
文档
  → 按句号、换行、段落边界切分
  → 保留完整句子
  → 按 chunk_size 聚合句子
  → 加少量 chunk_overlap
```

它的局限是：

- chunk size 是软约束，可能超过设定值。
- overlap 往往以句子为单位，实际长度不容易精确控制。
- 相关上下文如果距离较远，仍然可能被切到另一个 chunk。

适合场景：

- 普通文章。
- FAQ。
- 说明文档。
- 入门级 RAG 系统。

## 五、第三阶段：引入句子窗口补全上下文

句子窗口的核心思路是：

> 以当前句子为中心，把前后 N 句一起作为上下文。

示例：

```text
当前命中句子：第 5 句
window_size = 2

最终上下文：
第 3 句 + 第 4 句 + 第 5 句 + 第 6 句 + 第 7 句
```

它的价值是：

- 检索可以精准命中某一句。
- 生成时又能拿到前后上下文。
- 适合解释型回答、摘要生成、上下文依赖强的问答任务。

但句子窗口仍然是“线性上下文”，只能解决前后连续的问题。

如果两个相关观点分散在文档不同位置，句子窗口无法自动聚合。

## 六、第四阶段：使用句子滑动窗口减少边界割裂

句子滑动窗口是更实用的工程版本。

它不是单句独立处理，而是让窗口不断向后滑动，并保留一定重叠。

示例：

```text
chunk 1: 句子 1-5
chunk 2: 句子 4-8
chunk 3: 句子 7-11
```

优点：

- 相邻 chunk 有重叠，边界不容易断。
- 保留局部上下文。
- chunk 大小比纯语义切分更可控。

缺点：

- 会产生重复内容。
- overlap 太大会增加索引和检索成本。
- 仍然不理解深层语义关系。

适合场景：

- 长文章。
- 技术文档。
- 说明书。
- 政策文件。
- 需要保留上下文的问答任务。

## 七、第五阶段：引入关键词保护

关键词保护的作用不是只防止某个字符串被切成两半，而是防止关键业务语义单元被拆散。

典型需要保护的是：

- 术语 + 定义。
- 指标名 + 计算公式。
- 条款编号 + 条款内容。
- 表格字段 + 对应值。
- FAQ 的问题 + 答案。
- 代码函数名 + 函数说明。

例如：

```text
Transformer
Vision Transformer
Cost Per Unit
卷积神经网络
合同解除条件
```

如果关键概念刚好落在边界附近，就动态调整边界，把关键词、定义、值和必要上下文保留在同一个 chunk 中。

关键词来源可以包括：

- 领域术语词库。
- 标题层级。
- 用户高频查询词。
- 文档里的加粗词、编号、字段名。
- NER 抽取出的实体。
- 业务专家维护的核心概念表。

这一阶段可以和 [[RAG 领域术语词库与检索一致性优化实践]] 结合使用。

## 八、第六阶段：使用语义切分识别话题边界

语义切分的核心是：计算相邻句子之间的语义相似度，判断哪里是话题转换点。

基本逻辑：

```text
句子 1 和句子 2 相似 → 合并
句子 2 和句子 3 相似 → 继续合并
句子 3 和句子 4 不相似 → 切开
```

优点：

- chunk 更符合自然语义。
- 不容易把一个完整观点拆开。
- 适合逻辑性强、主题切换明显的长文档。

缺点：

- 需要 embedding 模型，成本更高。
- 相似度阈值难调。
- chunk 大小不可控。
- 可能生成过长 chunk，导致 embedding 截断。

适合场景：

- 法律文档。
- 医疗文档。
- 政策文件。
- 技术文章。
- 逻辑结构强的知识文档。

需要注意的是，语义切分主要改善“相邻文本”的边界判断，不能自动解决非连续知识聚合问题。

例如一个问题需要同时引用第一章和第五章的内容，语义切分不会自动把它们放进同一个 chunk。跨段、跨章节、多跳问题仍然需要查询改写、混合检索、父子块扩展、Graph 或重排序来补充。

## 九、第七阶段：使用混合切片策略

对于纯文本或结构较弱的长文档，推荐的工程方案是混合切片：

```text
先语义切分，再滑动窗口二次切分
```

完整流程：

1. 先按句子切分文档。
2. 计算相邻句子的语义相似度。
3. 根据阈值切出语义段落。
4. 检查每个语义块的 token 数。
5. 如果语义块小于阈值，直接保留。
6. 如果语义块超过阈值，再用句子滑动窗口切成多个子块。
7. 子块之间保留 overlap。
8. 每个 chunk 保存来源、页码、标题、父级语义块 ID。

这套方案兼顾：

- 语义完整性。
- chunk 大小可控。
- 上下文连续性。
- 检索鲁棒性。
- 后续可追溯性。

可以这样理解：

> 语义切分负责找“该不该切”，滑动窗口负责控制“怎么切得可用”。

对于 Markdown、HTML、Word、PDF、代码、表格等结构明显的文档，应优先使用结构边界；语义切分更适合作为结构缺失或结构不足时的补充。

## 十、第八阶段：动态重叠与父子块检索提升召回覆盖率

前面的策略主要解决“语义不要被切断”的问题。

但在真实 RAG 中，还会遇到另一个问题：切片本身看起来合理，但召回覆盖率仍然不够。

典型表现是：

- 用户问题需要的信息分散在多个 chunk 里，但检索只召回其中一部分。
- chunk 内混入太多无关信息，导致关键语义在 embedding 中被稀释。
- chunk 太小能精准命中，但交给大模型时缺少上下文。
- chunk 太大上下文完整，但检索精度下降。

这时需要进一步引入动态重叠、递归切片、父子块检索和命题化检索。

### 1. LangChain 递归切片：比固定切片更稳的静态方案

递归切片不是简单按固定长度硬切，而是按分隔符层级逐步切分。

典型顺序可以理解为：

```text
先按段落切
  → 段落太长，再按句子切
  → 句子太长，再按更小分隔符切
  → 最后合并相邻小块
  → 加少量 overlap
```

它的优势是：

- 保留段落、句子等自然边界。
- 比纯 token 切片更不容易破坏语义。
- 实现简单，调试成本低。
- 适合 FAQ、说明书、普通知识库等简单场景。

但它仍然不是真正的语义理解，只是比固定长度切片更尊重文本结构。

LangChain 官方文档中，Python 版本推荐从 `langchain_text_splitters` 导入 `RecursiveCharacterTextSplitter`，通用 RAG 场景可以用 `split_documents` 对 `Document` 列表进行切分，并用 `add_start_index=True` 保留切片在原文中的起始位置，方便后续引用和问题排查。

最小示例：

```python
from langchain_core.documents import Document
from langchain_text_splitters import RecursiveCharacterTextSplitter

docs = [
    Document(
        page_content=(
            "RAG 系统通常会先把长文档切成多个 chunk。"
            "如果切片过小，语义可能不完整；"
            "如果切片过大，关键信息又可能被噪声稀释。"
            "\n\n"
            "递归切片会优先按段落、句子等自然边界切分，"
            "尽量让每个 chunk 保持可读和语义连贯。"
        ),
        metadata={"source": "demo"},
    )
]

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,        # 每个 chunk 的最大字符数，官方示例中该值按字符计算
    chunk_overlap=200,      # 相邻 chunk 的重叠字符数
    length_function=len,    # 显式声明按字符长度计算
    add_start_index=True,   # 在 metadata 中记录 chunk 在原文中的起始位置
)

chunks = text_splitter.split_documents(docs)

for i, chunk in enumerate(chunks):
    print(f"chunk {i}")
    print(chunk.page_content)
    print(chunk.metadata)
```

如果希望切片更贴近中文文档，可以显式设置分隔符顺序：

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=80,
    separators=[
        "\n\n",  # 优先按段落切
        "\n",    # 再按换行切
        "。",    # 中文句号
        "！",
        "？",
        "；",
        "，",
        "",      # 最后兜底到字符级
    ],
    add_start_index=True,
)

chunks = text_splitter.split_documents(docs)
```

如果希望按 token 而不是字符控制长度，可以使用 tiktoken 编码器版本：

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
    chunk_size=500,
    chunk_overlap=80,
)

chunks = text_splitter.split_documents(docs)
```

这里要注意：

- `chunk_size` 和 `chunk_overlap` 的单位取决于 length function 或 splitter 构造方式；普通构造更偏字符长度，`from_tiktoken_encoder` 更适合按 token 控制。
- `add_start_index=True` 很重要，它能把 chunk 和原文位置关联起来，后续做引用、溯源、调试召回问题会更方便。
- 中文文档最好补充分隔符，否则默认分隔符对中文句子边界不一定足够友好。
- 中文分隔符需要结合实际输出检查，避免把标点、编号、列表符号、条款编号处理坏。
- 递归切片适合作为通用文本的基础方案，但遇到复杂语义边界、表格、代码、标题层级时，仍然需要结构感知或语义切片补充。

### 2. overlap 推荐从 chunk size 的 10% 到 20% 开始

overlap 的作用是保留相邻 chunk 的边界上下文。

它适合解决这类问题：

```text
chunk A 结尾：因为成本上升……
chunk B 开头：所以需要调整定价策略……
```

如果没有 overlap，chunk B 单独被召回时，“所以”的前提会丢失。

工程上可以从下面范围开始调参：

```text
chunk_overlap = chunk_size * 10% ~ 20%
```

这个比例只是经验起点，不是稳定最优值。最终要结合召回覆盖率、重复率、上下文噪声和答案准确性调参。

但 overlap 只能缓解边界信息丢失，不能解决所有上下文碎片化问题。

如果 overlap 过大，会带来：

- 向量库体积膨胀。
- 索引时间变长。
- 检索结果重复。
- 大模型上下文窗口被重复内容占用。
- 召回看似更多，但新信息并没有增加。

所以 overlap 应该被当成边界补偿机制，而不是主要召回策略。

### 3. Small-to-Big：小块检索，大块生成

固定 chunk 经常面临一个矛盾：

- 小 chunk：检索精准，但上下文不够。
- 大 chunk：上下文完整，但检索不精准。

Small-to-Big 的核心思路是：

> 用小块负责精准检索，用大块负责补全上下文。

基本结构：

```text
父块 Parent Chunk：较大的语义段落，保留完整上下文
子块 Child Chunk：较小的语义单元，用于精准检索
```

检索流程：

```text
用户问题
  → 检索子块
  → 命中最相关子块
  → 回溯所属父块
  → 把父块交给大模型生成答案
```

这类方案本质上是把“召回精度”和“上下文完整性”解耦。

一个更具体的例子：

```text
父块：退款规则

用户在订单支付后 24 小时内可以申请无理由退款。
如果订单已经发货，则需要扣除物流费用。
如果商品属于定制商品，则不支持无理由退款。
退款一般会在 3 到 5 个工作日内原路返回。
```

如果直接把整段作为一个大 chunk，用户问“定制商品能无理由退款吗？”，这个 chunk 虽然包含答案，但同时混有 24 小时、物流费用、到账时间等信息，向量表示可能被稀释，检索不一定精准。

如果只切成很小的子块：

```text
子块 1：用户在订单支付后 24 小时内可以申请无理由退款。
子块 2：如果订单已经发货，则需要扣除物流费用。
子块 3：如果商品属于定制商品，则不支持无理由退款。
子块 4：退款一般会在 3 到 5 个工作日内原路返回。
```

用户问题可以精准命中子块 3，但如果只把子块 3 交给大模型，模型可能缺少“退款规则”这个上层业务上下文。

父子分块的处理方式是：

```text
检索阶段：用子块 3 精准命中“定制商品不支持无理由退款”
生成阶段：回溯到父块“退款规则”，把完整规则交给大模型
```

这样既能精准命中答案，又能保留完整业务上下文。

它适合：

- 多跳问答。
- 法律文书分析。
- 科研论文问答。
- 技术文档问答。
- 复杂业务知识库。

### 4. 命题化检索：把文本拆成最小事实单元

命题化检索比普通子块更细。

它会把一段文本拆成不可再拆的最小语义事实。

例如原文：

```text
埃菲尔铁塔位于巴黎，建于 1889 年。
```

可以拆成两个命题：

```text
埃菲尔铁塔位于巴黎。
埃菲尔铁塔建于 1889 年。
```

命题化检索的核心价值是：

- 每个命题都是独立事实。
- 用户问题更容易精确命中。
- 命中后可以回溯到原始父块，补全上下文。
- 适合知识密集型、多事实、多跳推理场景。

整体流程可以理解为：

```text
原始文档
  → 基础切块
  → LLM 抽取命题
  → 命题作为子节点
  → 原始 chunk 作为父节点
  → 子节点和父节点共同建立索引
  → 查询时先命中命题，再回溯父块
```

它的代价也明显：

- 需要 LLM 抽取命题，成本更高。
- 抽取质量依赖 Prompt 和模型能力。
- 命题和原文之间必须保留映射关系。
- 调试复杂度高于普通切片。
- 可能漏掉限定条件、否定关系、时间范围、主体范围等关键信息。

因此它适合高价值知识库，不适合所有文档默认启用。

命题化结果更适合作为检索入口，而不是最终回答依据。生成答案时仍应回溯到原始父块或原文证据，避免只基于抽取后的命题回答。

### 5. Dify 父子模式：工程化的 Small-to-Big

Dify 的父子模式本质上也是 Small-to-Big。

它会把文档切成：

- 父块：较大的上下文单元。
- 子块：较小的检索单元。

检索时使用子块提升命中精度，生成时回到父块补全上下文。

它相比普通 overlap 的优势是：

- 不必靠大量重复内容维持上下文。
- 子块语义更集中，匹配用户问题更精准。
- 父块保留完整上下文，生成质量更稳定。

但父块也不是越大越好。父块过小补不回上下文，父块过大又会把无关内容带回生成阶段，导致答案被噪声干扰。

父块应该是一个完整但不臃肿的语义区域，例如一个小节、一个条款、一个 FAQ 问答组或一个表格说明区域。

工程注意点：

> Dify 知识库创建后，分段模式通常不能直接修改；如果一开始选择了通用模式，后续想切换到父子模式，往往需要重建知识库并重新导入文档。

所以生产知识库在创建前就要确定切片模式。

### 6. RAGFlow 深度文档理解：按场景模板切片

RAGFlow 的思路更偏结构化文档理解。

它不是只按文件格式切，而是按文档场景模板切。

例如：

- 普通文本用 General 模板。
- 学术论文用 Paper 模板，识别标题、摘要、正文、参考文献。
- 表格文档保留表格结构。
- 复杂 PDF 关注标题层级、列表、版面和视觉结构。

这种方案的价值是：

- 保留文档天然结构。
- 避免把标题、表格、列表和正文混切。
- 对 PDF、论文、报告、表格类文档更稳。
- 支持自动解析后人工微调，适合构建高质量领域知识库。

对于复杂文档，结构感知切片往往比单纯语义切片更可靠。

### 7. 这一阶段的选择建议

可以按场景选择：

| 场景 | 推荐策略 |
|---|---|
| FAQ、说明书、简单知识库 | 递归切片 + 10%~20% overlap |
| 普通长文本 | 语义切片 + 少量 overlap |
| 多跳问答、复杂推理 | Small-to-Big 父子块检索 |
| 法律、科研、金融等知识密集场景 | 命题化检索 + 父块回溯 |
| PDF、论文、表格、报告 | 结构感知切片 / RAGFlow 类模板解析 |

核心判断：

> overlap 解决边界问题，语义切片解决话题边界问题，父子块解决“精准检索和完整上下文不能兼得”的问题，命题化检索解决事实级精准召回问题。

## 十一、工程落地中的坑

### 1. 不要迷信固定 chunk size

很多人一上来就设置：

```text
chunk_size = 512
chunk_overlap = 50
```

这只能作为起点，不能作为最终方案。

不同文档结构差异很大，固定参数无法覆盖所有场景。

### 2. overlap 不是越大越好

overlap 太小，补不回上下文。

overlap 太大，会带来：

- 重复 chunk 增多。
- 向量库膨胀。
- 检索结果重复。
- 上下文噪声增加。
- 成本上升。

overlap 只适合做边界补偿，不应该指望它解决所有语义问题。

### 3. 句子切片可能超出模型限制

句子切片为了保证句子完整，可能让 chunk 超过设定大小。

所以 `chunk_size` 不要贴着 embedding 模型或 LLM 的最大上下文设置，要留安全余量。

### 4. 语义切分阈值很难一次调好

阈值太高：

- 切得太碎。
- 语义块过短。
- 上下文不足。

阈值太低：

- 合并过多。
- chunk 过长。
- 噪声增加。
- embedding 可能截断。

需要基于真实业务问题和召回效果调参。

### 5. 语义切分成本更高

语义切分需要对句子做 embedding，然后计算相似度。

文档量大时，需要考虑：

- 预处理耗时。
- embedding 成本。
- 批处理能力。
- 缓存机制。
- 增量更新。

不适合所有低价值文档都深度处理。

### 6. 关键词保护不能只靠高频词

高频词不一定是重要词。

例如“系统”“方法”“问题”很高频，但价值不大。

关键词最好来自：

- 术语词库。
- 标题。
- 业务指标。
- 用户查询日志。
- 专业实体识别。
- 人工维护的核心概念表。

### 7. 切片必须保留元数据

每个 chunk 至少要保留：

- 原始文档 ID。
- 标题层级。
- 页码 / 段落位置。
- 父级语义块 ID。
- chunk 序号。
- 前后 chunk 关系。
- 关键词 / 术语标签。

否则后续无法做引用、回溯、父子 chunk 扩展和问题排查。

### 8. 切片效果必须用召回评估验证

不能只看切出来的 chunk “感觉还行”。

应该建立测试集：

```text
用户问题
标准答案
应该召回的文档 / 段落
实际召回 chunk
最终生成答案
```

重点看：

- 是否召回正确 chunk。
- 是否召回完整上下文。
- 是否有大量重复。
- 是否有无关噪声。
- 答案是否因为切片缺失而错误。

更工程化的评估指标可以包括：

| 指标 | 关注点 |
|---|---|
| Recall@K | 应该命中的证据是否出现在前 K 个召回结果中 |
| Context Recall | 回答所需上下文是否被完整召回 |
| Context Precision | 召回上下文中有多少是有效信息，噪声比例有多高 |
| Duplicate Ratio | 召回结果中重复 chunk 或高度相似 chunk 的比例 |
| Answer Accuracy | 最终答案是否正确 |
| Faithfulness | 答案是否忠于召回上下文，没有编造 |
| Index Cost | chunk 数量、向量库体积、索引耗时 |
| Latency | 检索、重排、生成的整体延迟 |

### 9. 召回率低不一定都是切片问题

切片是召回质量的基础，但不是唯一变量。

如果召回率低，还需要同时检查：

- 文档解析是否丢内容。
- 表格、图片、公式是否被正确处理。
- embedding 模型是否适配当前领域。
- 是否需要 BM25 / 全文检索补充专有名词召回。
- query 改写是否跑题。
- topK 是否过小。
- metadata filter 是否过滤错了。
- 是否缺少 rerank。
- 生成 Prompt 是否限制模型必须基于上下文回答。

## 十二、推荐落地方案

### 简单文档

使用句子切片即可。

```text
句子切片 + 少量 overlap + 元数据保留
```

### 普通长文档

使用句子滑动窗口。

```text
句子切片 → 滑动窗口 → overlap → 入库
```

### 专业领域文档

优先保留结构边界，再结合语义切分 + 滑动窗口。

```text
文档结构解析
  → 标题 / 条款 / 表格 / 代码边界识别
  → 句子预处理
  → 术语 / 关键词识别
  → 语义切分
  → 大块滑动窗口二次切分
  → 保留元数据
  → 混合检索
```

### 高价值复杂文档

结合结构化解析。

```text
标题层级
  + 段落语义
  + 表格边界
  + 图片说明
  + 术语词库
  + 语义切分
  + 滑动窗口
```

## 十三、最终沉淀

切片语义割裂的最佳实践可以总结为：

> 不要把 RAG 切片理解成“按长度切文本”，而要理解成“构造可检索的语义知识单元”。

核心方案是：

```text
结构优先，句子保底，语义定边界，窗口补上下文，关键词防割裂，元数据保回溯，评测闭环持续调参。
```

更具体地说：

> 能用标题、段落、表格、代码函数、条款编号等结构边界时，不要先用 embedding 猜边界；语义切分和滑动窗口应该作为结构不足时的补充，而不是替代文档解析。

最终可以用一句话概括：

> RAG 切片的工程最佳实践，是结构优先、语义补充：先保留文档天然边界，再用语义切分识别话题变化，用滑动窗口控制大小和补充上下文，并结合关键词保护、父子块检索与元数据回溯，避免 chunk 语义割裂、召回不完整和上下文噪声过多。
