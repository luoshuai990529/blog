# RAG OCR 文本识别、LLM 纠错与图像文档问答实践

## 一、问题背景

RAG 系统处理普通文本、Markdown、Word、PDF 文本层时，核心问题通常是解析、分块、检索和生成。

但在真实业务里，很多关键知识并不是天然文本，而是存在于图片、扫描件、拍照件、票据、合同扫描件、表格截图、手写单据和低质量 PDF 中。

这些内容进入 RAG 前，必须先解决 OCR 识别问题。

典型场景可以用几句话概括：

- 合同扫描件里的“交货时间”没有被 OCR 识别出来，后续 RAG 再强也无法回答相关问题。
- 表格截图里“准乘人数”字段被识别出来，但字段和值的对应关系可能丢失。
- 金额、编号、日期、证件号中出现 `0/O`、`2/Z` 这类字符混淆，直接影响答案准确性。
- 拍照件存在倾斜、低分辨率、阴影、水印、背景干扰，导致漏识别和顺序错乱。
- OCR 输出是一段纯文本，但原始文档中的表格、版面、行列关系和字段结构已经丢失。

> [!summary] 核心判断
> OCR 在 RAG 中不是简单的“图片转文字”，而是把图像文档转成可检索、可校验、可回溯的结构化知识单元。

## 二、OCR 常见错误类型

OCR 错误通常不是单一问题，而是识别、结构、顺序和语义多层问题叠加。

### 1. 字符识别错误

常见问题：

- `0` 和 `O` 混淆。
- `1`、`I`、`l` 混淆。
- `2` 和 `Z` 混淆。
- 中文相似字、繁简体、特殊符号混淆。

这类错误对金额、编码、证件号、订单号、航班号、合同编号影响很大。

### 2. 文字遗漏

常见原因：

- 图片模糊。
- 分辨率低。
- 文字颜色和背景颜色接近。
- 水印或背景图案干扰。
- 字体过小。

遗漏比识别错误更危险，因为后续 RAG 根本拿不到这部分信息。

### 3. 重复识别

常见于手写体、多行文本、表格边界不清、印章和正文重叠的场景。

问题表现是：

- 同一行被识别多次。
- 多行内容被合并。
- 表格相邻单元格内容被混在一起。

### 4. 格式和阅读顺序错乱

OCR 可能识别出了文字，但顺序是错的。

例如：

- 多栏文档从左栏跳到右栏。
- 表格按视觉顺序读错。
- 标题、正文、脚注混在一起。
- 扫描件里的字段和值对应关系丢失。

这类问题会直接影响 RAG 的分块和检索质量。

### 5. 特殊字符和结构元素错误

包括：

- 标点符号。
- 数学符号。
- 单位符号。
- 货币符号。
- 表格线。
- 勾选框。
- 印章。
- 手写批注。

这些内容在合同、票据、财务、医疗和政务文档里经常是关键信息。

## 三、传统 OCR 的局限

传统 OCR 通常可以拆成几个阶段：

```text
图像预处理
  → 文本检测
  → 文本识别
  → 后处理纠错
  → 结果输出
```

它能解决大量基础识别问题，但在复杂业务场景里有明显局限。

### 1. 图像预处理可能造成信息丢失

去噪、增强对比度、二值化可以提高文字可见度，但也可能让细小文字、浅色文字、印章、表格线、特殊符号丢失。

### 2. 规则后处理依赖人工设计

传统纠错通常依赖词典、正则、模板和人工规则。

例如：

```text
如果字段是金额，那么只允许数字、小数点和货币符号。
```

这种规则对固定表单有效，但面对多样化文档时维护成本很高。

### 3. OCR 模型缺少语义理解

OCR 更关注图像和字符形状，不擅长结合上下文判断含义。

例如金额字段里出现 `Z`，从图像上它可能像字母，但结合“金额”上下文，大概率应该是数字 `2`。

这正是 LLM 可以补足的地方。

## 四、LLM 在 OCR 链路中的价值

LLM 的价值不是无条件替代 OCR，而是补足 OCR 的语义理解、上下文推理和结构化整理能力。

更合理的分工是：

```text
OCR：负责从图片中提取原始文字、位置和结构候选
LLM：负责基于上下文纠错、补全、字段归一化和结构化整理
```

### 1. 语义纠错

LLM 可以结合上下文纠正明显不合理的识别结果。

例如：

```text
OCR 原文：金额为 1Z00 元
上下文：这是金额字段
LLM 修正：金额为 1200 元
```

但这类修正必须保留原始 OCR 结果和修正依据，不能直接覆盖原文。

### 2. 字段标准化

OCR 输出可能是松散文本，LLM 可以把它整理成统一字段。

例如：

```json
{
  "签约时间": "2024-05-01",
  "交货时间": "以买方通知为准",
  "准乘人数": "2人"
}
```

### 3. 多语言和格式理解

LLM 对简体中文、繁体中文、英文、拼音、常见缩写有更好的语言理解能力，可以辅助处理多语言混排文档。

### 4. 版面和表格语义补全

当 OCR 识别出文本但没有恢复结构时，LLM 可以结合标题、字段、上下文，把内容整理为 Markdown、JSON 或 key-value。

不过要注意：表格、票据、合同这类高价值信息，不能只靠 LLM 猜结构，仍然需要保留 OCR 的坐标、行列关系和原始图片证据。

## 五、推荐技术流程

面向 RAG 的 OCR 处理流程，不应该只输出纯文本。

更推荐的链路是：

```text
图像 / 扫描件 / 图片型 PDF
  → 图像预处理
  → OCR 文本检测和识别
  → 版面分析
  → 表格 / 字段 / 印章 / 勾选框识别
  → LLM 纠错和结构化
  → 输出 Markdown + JSON + bbox + confidence
  → 分块和索引
  → 检索问答
  → 低置信度结果回流复核
```

其中各类输出的职责不同：

| 输出 | 作用 |
|---|---|
| 原始 OCR 文本 | 保留原始证据，便于回溯 |
| LLM 修正文本 | 用于提升可读性和检索质量 |
| Markdown | 给大模型阅读和生成 |
| JSON | 给系统做字段检索、过滤和结构化处理 |
| bbox | 回到原图位置，支持审计和人工复核 |
| confidence | 判断是否需要人工复核 |
| page / image_id | 支持引用来源和定位 |

## 六、第一阶段：图像预处理

图像预处理的目标是提高 OCR 可识别性，但不能破坏原始证据。

常见处理包括：

- 方向检测和旋转校正。
- 畸变校正。
- 去噪。
- 对比度增强。
- 分辨率提升。
- 裁边和去阴影。
- 竖排文字方向处理。

注意事项：

- 预处理结果和原图都要保留。
- 不要只保存二值化后的图片。
- 对印章、浅色文字、表格线要谨慎处理，避免增强过程中丢失。

## 七、第二阶段：OCR 文本检测和识别

OCR 一般包含两个核心动作：

1. 文本检测：找到图片中哪里有文字。
2. 文本识别：识别每个文本区域的具体内容。

以 PaddleOCR / PP-OCRv5 为例，流程可以理解为：

```text
输入图片
  → 方向分类
  → 畸变校正
  → 文本检测
  → 文本行方向分类
  → 文本识别
  → JSON 输出
```

输出结果不要只看文字，还要关注：

- 文本框坐标。
- 文本行顺序。
- 置信度。
- 是否存在漏识别。
- 是否存在重复识别。
- 是否有竖排文字或旋转文字。

## 八、第三阶段：版面分析和结构恢复

OCR 识别出文字只是第一步。

RAG 更需要知道：

- 哪些是标题。
- 哪些是正文。
- 哪些是表格。
- 哪些是字段名。
- 哪些是字段值。
- 哪些是页眉页脚。
- 哪些是印章、签名、手写批注。

对于复杂文档，需要增加版面分析和结构恢复。

典型结构包括：

```text
标题
段落
表格
列表
字段-值
图片说明
页眉页脚
印章/签名
```

结构恢复的目标是让 RAG 后续可以正确分块、检索、引用和回答。

如果只把所有 OCR 文字拼成一段，很容易出现顺序错乱、字段错配和表格语义丢失。

## 九、第四阶段：LLM 纠错和结构化

LLM 纠错应该有边界。

它适合做：

- 明显字符混淆修正。
- 字段值格式化。
- 日期、金额、单位归一化。
- 文本顺序辅助整理。
- 根据上下文补充字段含义。
- 将 OCR 文本整理成 Markdown / JSON。

不适合做：

- 无证据补全缺失内容。
- 擅自修改金额、合同编号、证件号。
- 覆盖低置信度 OCR 结果但不保留原文。
- 仅凭语言常识猜测表格字段。

推荐的 LLM 纠错输入应包含：

```text
1. 原始 OCR 文本
2. OCR bbox 坐标
3. OCR 置信度
4. 文档类型
5. 字段约束
6. 上下文片段
7. 禁止编造规则
```

推荐输出：

```json
{
  "raw_text": "金额为 1Z00 元",
  "corrected_text": "金额为 1200 元",
  "correction_reason": "字段为金额，Z 在该上下文中更可能是数字 2",
  "confidence": 0.82,
  "need_human_review": true,
  "bbox": [100, 120, 260, 150],
  "page": 1
}
```

核心原则：

> LLM 可以辅助纠错，但必须保留原始 OCR、修正依据、置信度和来源坐标。

## 十、第五阶段：结构化输出和 RAG 入库

OCR + LLM 的最终结果应该同时服务人和系统。

推荐同时保存三类数据：

### 1. Markdown

用于模型阅读。

示例：

```markdown
## 合同信息

- 签约时间：2024-05-01
- 交货时间：以买方通知为准
- 准乘人数：2人
```

### 2. JSON

用于字段检索、过滤、排序和系统处理。

示例：

```json
{
  "document_type": "contract_scan",
  "fields": {
    "签约时间": {
      "value": "2024-05-01",
      "source": "ocr_llm_corrected",
      "confidence": 0.91,
      "bbox": [120, 300, 260, 330],
      "page": 1
    },
    "交货时间": {
      "value": "以买方通知为准",
      "source": "ocr_raw",
      "confidence": 0.63,
      "bbox": [120, 340, 420, 370],
      "page": 1,
      "need_human_review": true
    }
  }
}
```

### 3. 原始证据

包括：

- 原图。
- 预处理图。
- OCR 原始 JSON。
- LLM 修正记录。
- bbox。
- page。
- confidence。

这些信息决定了系统是否可审计、可复核、可回滚。

## 十一、第六阶段：PP-ChatOCR 与 RAG 问答集成

文稿中提到的 PP-ChatOCR V4，本质是把 OCR、文档结构化、检索和大模型问答封装成一个 pipeline。

可以理解为：

```text
扫描件 / PDF / 图片
  → OCR
  → 版面分析
  → 表格结构提取
  → PP-Struct 结构化数据
  → 向量化
  → 用户问题检索
  → LLM 回答
```

它适合希望快速把扫描件、表格图片、图片型 PDF 接入 RAG 问答的场景。

例如用户问：

```text
准乘人数是多少？
```

系统需要先从扫描件表格中识别字段和值，再通过检索和 LLM 回答：

```text
准乘人数是两人。
```

这种系统的关键不只是 OCR 识别文字，而是恢复“字段和值”的对应关系。

## 十二、工程落地难点

### 1. 不要让 LLM 无约束纠错

LLM 纠错容易引入“看起来合理但没有证据”的内容。

尤其是金额、日期、合同编号、证件号、药品名、车牌号等字段，不能让模型自由改写。

建议：

- 高风险字段只允许低幅度纠错。
- 保留原始 OCR。
- 低置信度结果进入人工复核。
- LLM 输出必须带修正原因。

### 2. OCR 漏识别比识别错误更难发现

识别错了还能被规则或 LLM 发现，漏识别则可能完全消失在 RAG 系统中。

建议：

- 保留图像和 bbox 可视化。
- 对关键字段做完整性校验。
- 对合同、票据、表单类文档建立必填字段清单。
- 如果关键字段缺失，应返回“未识别到”，不要让模型猜。

### 3. 表格不能只转成纯文本

表格截图或扫描表格必须保留行列关系。

否则：

- 字段和值可能错配。
- 多列表格会顺序混乱。
- 检索到的文本无法支撑精确回答。

建议：

- 输出 Markdown 表格供模型阅读。
- 输出 JSON 供系统处理。
- 保留单元格 bbox。
- 对跨行、合并单元格、表头重复进行特殊处理。

### 4. 置信度必须进入系统设计

OCR 和 LLM 纠错都不是 100% 可靠。

系统需要根据置信度决定处理方式：

```text
高置信度 → 自动入库
中置信度 → 入库但标记风险
低置信度 → 人工复核或拒绝回答
```

如果没有置信度机制，系统会把错误内容当成事实进入知识库。

### 5. 图像预处理不能覆盖原始证据

增强、去噪、二值化可能提升 OCR 效果，但也可能破坏原图信息。

建议：

- 原图必须保留。
- 预处理图单独保存。
- OCR 结果要能回到原始图像区域。

### 6. OCR 结果入库前需要质量评估

建议建立 OCR 质量指标：

| 指标 | 含义 |
|---|---|
| 字符准确率 | 字符级识别是否正确 |
| 字段准确率 | 关键字段是否识别正确 |
| 字段召回率 | 关键字段是否被识别出来 |
| 表格结构准确率 | 行列关系是否正确 |
| 阅读顺序准确率 | 文本顺序是否符合原文 |
| 低置信度占比 | 需要人工复核的比例 |
| RAG 答案准确率 | 最终问答是否正确 |

### 7. OCR + RAG 问题要分层排查

当图像文档问答失败时，不要直接归因于大模型。

需要按链路排查：

```text
原图质量是否足够？
OCR 是否识别到文字？
版面和表格结构是否恢复？
LLM 是否错误纠正？
字段 JSON 是否正确？
chunk 是否合理？
检索是否召回正确字段？
生成是否忠于上下文？
```

## 十三、推荐落地路径

### 简单图片文字

适合：

- 清晰截图。
- 简单票据。
- 普通拍照文本。

推荐：

```text
OCR → LLM 轻量纠错 → Markdown 入库
```

### 表格截图和扫描表单

适合：

- 表格截图。
- 合同扫描件。
- 票据。
- 表单。

推荐：

```text
OCR → 版面分析 → 表格结构识别 → JSON + Markdown → RAG 入库
```

### 高价值业务文档

适合：

- 合同。
- 医疗单据。
- 金融票据。
- 政务材料。

推荐：

```text
OCR → bbox + confidence → LLM 受约束纠错 → 字段校验 → 人工复核 → 入库
```

### 图像文档问答系统

适合：

- 扫描件问答。
- 图片型 PDF 问答。
- 表格图片问答。

推荐：

```text
OCR / PP-ChatOCR
  → 文档结构化
  → 向量检索
  → LLM 问答
  → 低置信度结果复核
```

## 十四、最终沉淀

OCR + LLM 在 RAG 中的目标，不是简单把图片转成一段文本，而是把图像文档转成可检索、可校验、可回溯的知识单元。

一套可靠的 OCR 入库方案，应该同时保留：

- 原始图像。
- OCR 原始结果。
- LLM 修正结果。
- bbox 坐标。
- 置信度。
- 页码和区域。
- Markdown 阅读格式。
- JSON 结构化格式。
- 人工复核状态。

最终可以用一句话概括：

> RAG 中处理图像文档的最佳实践，是让 OCR 负责原始证据提取，让 LLM 负责受约束纠错和结构化整理，最终同时输出 Markdown 给模型阅读、JSON 给系统处理、bbox 和置信度给系统回溯与质量控制。
