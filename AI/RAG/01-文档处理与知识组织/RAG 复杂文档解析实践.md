# RAG 流程中复杂文档内容提取解析实践和沉淀

## 核心结论

RAG 中复杂文档解析的关键，不是把文件简单转成纯文本，而是把不同来源、不同结构、不同质量的内容统一沉淀为**可索引、可引用、可回溯、可评估**的标准知识单元。

复杂文档解析要解决四个问题：

1. **读得出来**：能从 PDF、Word、Excel、Markdown、网页、图片等来源中提取内容。
2. **结构不丢**：保留标题、段落、表格、图片、链接、页码、行列关系。
3. **后续可用**：转成适合分块、Embedding、检索和生成的中间表示。
4. **结果可信**：每个 chunk 能回到原文件、原页码、原表格或原图片。

## 一、复杂文档解析在 RAG 流程中的位置

RAG 的常见描述是：

```text
用户提问 → 检索 → 召回上下文 → 大模型生成答案
```

但在真实工程里，RAG 效果首先取决于知识如何入库：

```text
原始文档
  → 内容提取
  → 结构标准化
  → 清洗
  → 分块
  → 向量化 / 全文索引 / 元数据索引
  → 检索
  → 生成
```

如果内容提取阶段质量差，后面的问题会被持续放大：

- 表格结构丢失，模型无法理解字段关系。
- 图片未 OCR，图片中的关键知识无法被召回。
- PDF 双栏顺序错乱，导致 chunk 语义混乱。
- 页码、URL、行号丢失，答案无法回溯来源。
- 文档被粗暴切碎，Rerank 也无法恢复完整上下文。

因此，复杂文档解析不是一个“前处理小步骤”，而是 RAG 知识质量的第一道关口。

## 二、推荐的工程分层

一套可维护的复杂文档解析系统，建议拆成四层。

```text
文件接入层
  → 识别文件来源、类型、扩展名、MIME、权限、存储位置

Extractor 层
  → 按格式提取文本、表格、图片、链接和元数据

标准化层
  → 转成 Markdown / JSON / Document 等统一中间表示

索引处理层
  → 清洗、分块、Embedding、全文索引、元数据索引
```

这个分层的核心思想是：

> 文件格式差异应该封装在 Extractor 层，后续 RAG 链路只处理统一的标准内容对象。

以 Dify 的源码设计为例，可以抽象为：

```text
ExtractProcessor
  → 根据 datasource_type 和文件扩展名路由到不同 Extractor

BaseExtractor
  → 约束所有 Extractor 都实现 extract()

Document
  → 统一承载 page_content 和 metadata

IndexProcessor / Splitter
  → 负责真正的分块和索引入库
```

统一接口通常类似：

```python
class BaseExtractor:
    def extract(self) -> list[Document]:
        ...
```

最终输出统一成：

```python
Document(
    page_content="提取后的文本或 Markdown",
    metadata={
        "source": "原文件",
        "page": 1,
        "sheet": "Sheet1",
        "row": 10
    }
)
```

这种设计让后续分块、Embedding、召回和生成不需要关心原始文件是 PDF、Word 还是 Excel。

## 三、提取和分块要分开设计

复杂文档处理里最容易混淆的是：**内容提取不等于最终分块**。

### 1. 提取阶段

提取阶段负责把原始文件变成初步 `Document`。

它关注：

- 文件如何读取。
- 文本如何抽取。
- 表格如何表达。
- 图片如何保存。
- 链接如何保留。
- 页码、行号、来源如何写入 metadata。

不同文件类型在提取阶段的天然粒度不同：

| 文件类型 | 提取阶段适合的初步粒度 | 原因 |
|---|---|---|
| PDF | 页级 | PDF 天然有 page 概念，便于引用 |
| Word | 文档级或块级 | 内部有段落、表格、图片、超链接 |
| Markdown | 标题块级 | 标题天然是语义边界 |
| Excel | 行级 | 行是最自然的数据实体 |
| CSV | 行级 | 行级 key-value 更适合检索 |
| PPT | Slide 级 | 每页幻灯片通常表达一个主题 |
| Notion | 页面或 block 级 | Notion 本身是 block 结构 |
| HTML | 页面级或正文块级 | 取决于正文抽取能力 |

### 2. 分块阶段

分块阶段负责把提取结果变成适合索引和召回的 chunk。

它关注：

- chunk 长度。
- chunk overlap。
- 语义完整性。
- 是否切碎表格、代码块、图片说明。
- 是否保留父子 chunk 关系。
- 是否适配 embedding 模型上下文长度。

从 Dify 当前源码看，最终分块主要在 `index_processor` 和 `splitter` 中完成，而不是在各个 extractor 里分别实现。

典型自动分块优先级是：

```text
空行
  → 中文句号
  → 英文句号
  → 空格
  → 字符级兜底
```

自定义模式支持：

- `separator`
- `max_tokens`
- `chunk_overlap`

这种设计的好处是架构简单，问题是它不是结构感知分块，容易切坏表格、图片说明、代码块和公式。

## 四、不同文档类型的解析实践

### 1. Word / DOCX

Word 是典型结构化文档，适合按原生结构解析。

可提取对象包括：

- 标题
- 段落
- 表格
- 图片
- 超链接
- 分页符
- 块结构

推荐处理方式：

1. 用 `python-docx` 读取文档。
2. 按文档顺序遍历 paragraph 和 table。
3. 段落按文本流保留。
4. 表格转 Markdown 表格。
5. 图片保存到对象存储。
6. 图片位置处插入 Markdown 图片链接。
7. 超链接转 Markdown link。
8. metadata 保留 source、页码、块信息等。

Word 的优势是结构明确，适合作为企业知识库的原始文档格式。

主要难点：

- 嵌套表格。
- 跨页表格。
- 横向/纵向合并单元格。
- 页眉页脚。
- 批注和修订痕迹。
- 图片中的文字。
- 文档内对象顺序和视觉顺序不一致。

实践建议：

> Word 不要粗暴转纯文本，应优先保留段落、表格、链接、图片关系。表格转 Markdown，图片转引用，必要时对图片做 OCR。

### 2. PDF

PDF 是复杂文档解析中最容易出现质量问题的格式。

PDF 的核心问题是：

- 视觉上有结构，底层不一定有语义结构。
- 文本顺序可能和阅读顺序不同。
- 表格经常只是视觉排版，不是结构化表格。
- 图片、公式、脚注、页眉页脚容易干扰正文。
- 扫描 PDF 可能完全没有文本层。

基础处理方式：

1. 如果有文本层，按页提取文本。
2. 提取页面中的图片对象。
3. 图片保存到对象存储。
4. 在文本中插入 Markdown 图片链接。
5. 每页保留 `page` metadata。

增强处理方式：

1. 做版面分析，识别标题、段落、表格、图片区域。
2. 对扫描 PDF 做 OCR。
3. 对表格区域做表格结构识别。
4. 对公式区域做公式识别。
5. 将识别结果转为 Markdown / JSON / HTML。

不同 PDF 的处理深度应区分：

| PDF 类型 | 推荐策略 |
|---|---|
| 普通文字 PDF | 文本层提取 + 页码 metadata |
| 论文 PDF | 双栏识别、图表识别、公式处理 |
| 扫描 PDF | OCR + 版面分析 |
| 票据 PDF | OCR + 字段结构化 |
| 表格 PDF | 表格区域检测 + 行列识别 |
| 合同 PDF | 条款层级、页码、签章、手写内容处理 |

实践建议：

> PDF 不要只看是否能抽出文字，更要看阅读顺序、表格关系、图片上下文和页码引用是否保留。

### 3. Markdown

Markdown 是最适合作为 RAG 中间格式的文档之一。

优势：

- 标题层级清晰。
- 表格、列表、代码块易读。
- LLM 友好。
- 易于人工维护。
- 易于调试分块结果。

推荐处理方式：

1. 按标题层级切分。
2. 保留 heading path。
3. 代码块内不要误判标题。
4. Markdown 表格尽量整体保留。
5. 图片链接保留或转成可访问 URL。
6. 本地附件要转成对象存储文件 ID。

需要注意：

- 长表格不要被普通 splitter 切碎。
- 代码块不要切断。
- 图片说明要和图片链接放在同一 chunk。
- 标题路径要进入 metadata 或 chunk 前缀。

实践建议：

> Markdown 适合作为复杂文档标准化后的目标格式，尤其适合承载标题、列表、表格、图片引用和代码块。

### 4. Excel / CSV

Excel 和 CSV 本质上是结构化数据，不适合当普通文章处理。

推荐处理方式：

1. 自动识别表头。
2. 按行生成一个 Document。
3. 每行转成 key-value 文本。
4. metadata 保留 sheet、row、source。
5. 单元格超链接转 Markdown link。
6. `.xlsx` 图片按锚点单元格映射。
7. 对强结构化查询，额外进入 SQL 或结构化索引。

推荐表示：

```text
"产品":"A";"价格":"100";"地区":"华东";"负责人":"张三"
```

不要简单把整张表拼成一大段文本，原因是：

- 表头和单元格关系容易丢。
- 大表格会超长。
- 行之间通常是独立业务实体。
- 真实查询常涉及筛选、聚合和排序。

更合理的处理架构：

```text
Excel / CSV
  → 行级 Document
  → metadata: sheet, row, source
  → 向量库用于语义问答
  → 结构化数据库用于过滤、排序、聚合
```

实践建议：

> 表格型数据不要只进向量库，应保留字段结构；自然语言问答走向量检索，精确筛选和聚合走结构化查询。

### 5. HTML / 网页

HTML 不能简单 `get_text()`。

直接 `get_text()` 会导致：

- 标题层级丢失。
- 表格结构丢失。
- 链接关系丢失。
- 图片上下文丢失。
- 导航、广告、页脚污染正文。

推荐处理方式：

1. 正文抽取。
2. 去除导航、广告、页脚。
3. 保留标题、段落、列表、表格、链接。
4. 转成干净 Markdown。
5. metadata 保留 URL、title、description。

实践建议：

> 网页解析的重点是正文抽取和结构保留，而不是 HTML 到纯文本的简单转换。

### 6. 图片 / 扫描件

图片和扫描件应走视觉文档解析流程。

推荐流程：

```text
图片 / 扫描件
  → 图像预处理：旋转、纠偏、去噪、增强
  → OCR
  → Layout Analysis
  → 表格 / 印章 / 手写 / 公式识别
  → Markdown / JSON
  → Document
```

主要难点：

- 扫描倾斜。
- 图片模糊。
- 手写识别。
- 印章遮挡。
- 表格线缺失。
- 多栏顺序错误。
- OCR 识别顺序不符合阅读顺序。

实践建议：

> 扫描件不能当作普通 PDF 处理，它本质上是图片，必须先恢复文本和版面结构，再进入 RAG 入库链路。

## 五、表格、图片、公式的标准处理原则

### 1. 表格

表格的核心不是“抽出文字”，而是保留行列关系。

推荐原则：

1. 简单表格转 Markdown。
2. 大表格按行或业务实体切分。
3. 字段明确的表格转 JSON / key-value。
4. PDF 表格需要单独做表格区域检测。
5. 跨页表格需要合并表头和上下页内容。
6. 表格 chunk 要保留表名、页码、sheet、行列信息。

Markdown 表示：

```markdown
| 字段 | 含义 | 示例 |
|---|---|---|
| product | 产品名 | A |
| price | 价格 | 100 |
```

JSON 表示：

```json
{
  "product": "A",
  "price": 100,
  "region": "华东"
}
```

处理取舍：

- 面向 LLM 阅读：Markdown 更自然。
- 面向字段查询：JSON / key-value 更稳定。
- 面向统计分析：进入结构化数据库更合适。

### 2. 图片

图片处理分两层。

第一层：保留和回溯。

```text
提取图片
  → 保存到对象存储
  → 创建文件记录
  → 在正文中插入图片链接
```

第二层：理解和索引。

```text
图片 OCR
  → 图片描述
  → 图表理解
  → 公式识别
  → 与图片链接绑定入库
```

推荐表示：

```markdown
![image](/files/{file_id}/file-preview)

图片内容：该图片展示了产品安装步骤，包括打开设备、连接电源、完成初始化配置。
```

处理取舍：

- 装饰图、logo、重复图不一定需要 OCR。
- 票据、合同截图、产品步骤图、架构图适合 OCR 或多模态理解。
- 图片 OCR 结果必须和原图链接放在一起，避免失去证据链。

### 3. 公式

公式处理原则：

1. 文本公式尽量保留 LaTeX。
2. 图片公式需要公式 OCR。
3. 公式和解释文字不要分离。
4. 公式不要被切到两个 chunk。
5. 论文 PDF 中公式区域需要配合 layout 识别。

## 六、分块策略实践

### 1. 统一 splitter 的价值

统一 splitter 的优点：

- 架构简单。
- 接入新格式容易。
- 后续索引链路稳定。
- 用户可配置 separator、max_tokens、chunk_overlap。
- 大部分普通文本文档能快速跑通。

典型递归切分顺序：

```text
空行
  → 中文句号
  → 英文句号
  → 空格
  → 字符级兜底
```

### 2. 统一 splitter 的不足

统一 splitter 不理解文档结构，因此会出现：

- Markdown 表格被切碎。
- Word 表格被切到多个 chunk。
- 图片链接和图片说明分离。
- 代码块被切断。
- 公式被拆开。
- Excel 行级语义被破坏。
- PDF 页内结构无法恢复。

### 3. 结构感知分块

复杂文档更适合结构感知分块。

推荐策略：

```text
标题感知分块
  → 保留 heading path

表格保护分块
  → 表格整体不切碎，或按行分组

图片绑定分块
  → 图片链接、OCR、图片说明放在同一 chunk

页码感知分块
  → 保留 page metadata

代码块保护
  → 代码块整体切分，不从中间截断

公式保护
  → 公式和解释文本绑定

父子分块
  → 子 chunk 用于召回，父 chunk 用于生成

多粒度分块
  → 小块召回，大块回答
```

### 4. 推荐分块取舍

| 内容类型 | 推荐分块策略 |
|---|---|
| 普通文章 | 标题 + 段落递归切分 |
| Markdown 文档 | heading-aware chunk |
| Word 文档 | 段落/标题/表格感知 |
| PDF | 页级 + layout block |
| Excel/CSV | 行级或业务实体级 |
| 大表格 | 按行组、字段组或 JSON 对象 |
| 图片说明 | 图片链接 + OCR + 上下文绑定 |
| 代码 | 函数/类/代码块级 |
| 公式 | 公式 + 解释段落绑定 |

## 七、复杂文档解析质量评估

复杂文档解析质量不能只看“有没有文字”。

需要评估：

1. **文本完整性**：关键段落是否缺失。
2. **结构完整性**：标题、表格、列表、代码块是否保留。
3. **阅读顺序**：双栏、页眉页脚、脚注是否干扰正文。
4. **表格准确性**：行列关系是否正确。
5. **图片可回溯性**：图片是否保存，链接是否可访问。
6. **OCR 准确率**：扫描件和图片文字是否识别正确。
7. **metadata 完整性**：页码、来源、sheet、行号是否保留。
8. **chunk 质量**：是否语义完整，是否过长或过短。
9. **召回质量**：问题能否召回正确片段。
10. **生成质量**：答案是否基于正确上下文生成。

建议沉淀测试集：

- 普通 Word。
- Word 表格。
- Word 图片。
- 双栏 PDF。
- 扫描 PDF。
- PDF 跨页表格。
- Excel 大表。
- Markdown 长文。
- HTML 网页。
- 图片票据。
- 含公式论文。
- 含代码文档。

每次优化解析器或 splitter，都用这批样本回归测试。

## 八、常见设计误区与处理建议

### 误区一：所有文件都转纯文本

问题：

- 表格行列关系丢失。
- 图片和说明关系丢失。
- 标题层级丢失。
- 来源定位丢失。

建议：

> 正文类内容可以转 Markdown，结构化字段转 JSON/key-value，图片保留链接并按需 OCR。

### 误区二：只做向量索引

问题：

- 错误码、型号、编号等字面匹配不稳定。
- Excel 这类结构化数据不适合只靠语义检索。
- 需要筛选、排序、聚合时向量库不合适。

建议：

```text
文本语义 → 向量索引
专有名词/错误码 → 全文检索
结构化字段 → SQL / 元数据过滤
图片内容 → OCR 文本 + 图片引用
```

### 误区三：所有图片都 OCR

问题：

- 成本高。
- 处理慢。
- 装饰图会引入噪音。
- 图片描述可能污染检索结果。

建议：

> 先保留图片引用，再根据业务价值决定是否 OCR。票据、合同截图、产品步骤图、架构图优先 OCR；logo、装饰图、重复图可以跳过。

### 误区四：忽略 metadata

问题：

- 召回结果无法解释。
- 答案无法引用来源。
- 用户无法回到原文核验。

建议：

metadata 至少保留：

- source
- page
- sheet
- row
- heading path
- block id
- image id
- URL
- created_at / updated_at

### 误区五：统一 splitter 切所有内容

问题：

- 表格被切碎。
- 代码块被截断。
- 图片说明和图片链接分离。
- 公式上下文丢失。

建议：

> 普通文本可以用递归字符 splitter，复杂文档要引入结构感知分块和父子 chunk。

## 九、落地优先级

复杂文档解析不建议一次追求完美。推荐分阶段落地。

### 阶段一：跑通主流程

目标：

- 支持 PDF、Word、Markdown、Excel、CSV、HTML。
- 统一输出 `Document`。
- 保留基础 metadata。
- 完成分块和索引。

### 阶段二：保留关键结构

目标：

- Word 表格转 Markdown。
- Excel 行级 key-value。
- Markdown heading path。
- PDF 页码 metadata。
- 图片保存并插入链接。

### 阶段三：增强非结构化文档

目标：

- 扫描件 OCR。
- PDF layout analysis。
- PDF 表格识别。
- 图片 OCR。
- 公式识别。

### 阶段四：结构感知分块

目标：

- 表格保护。
- 图片和说明绑定。
- 标题层级分块。
- 父子 chunk。
- 多粒度召回。

### 阶段五：评测和持续优化

目标：

- 建立复杂文档测试集。
- 监控解析失败样本。
- 比较不同解析器效果。
- 根据召回失败 case 反推解析和分块问题。

## 十、最终沉淀

复杂文档解析的最佳实践可以概括为：

1. **统一抽象。** 所有格式最终进入统一 `Document`。
2. **分层处理。** 文件接入、Extractor、标准化、索引处理分开。
3. **保留结构。** 标题、表格、图片、链接、页码、行列关系不能随便丢。
4. **按格式定制。** Word 用结构解析，PDF 用文本层 + OCR/Layout，Excel 用行级 key-value。
5. **按业务取舍。** 高价值图片、表格、扫描件深度解析，低价值内容保留引用即可。
6. **结构感知分块。** 不要让普通字符 splitter 切坏表格、代码、公式和图片说明。
7. **可回溯优先。** 每个 chunk 都应尽可能定位回原文档、页码、表格、图片或行号。
8. **持续评估。** 用复杂文档样本集持续回归解析质量。

如果只保留一句话：

> 复杂文档 RAG 的关键不是把文件变成文本，而是把文本、表格、图片、版面和来源关系，转成可检索、可引用、可回溯的标准知识单元。
