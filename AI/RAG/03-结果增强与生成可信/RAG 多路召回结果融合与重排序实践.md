# RAG 多路召回结果融合与重排序实践

## 一、问题背景

生产级 RAG 通常不会只依赖一路向量检索。

真实业务里，用户问题可能同时依赖关键词、语义、实体关系、业务规则和历史上下文。为了尽量不漏掉正确答案，系统通常会做多路召回：

```text
BM25 关键词召回
向量语义召回
规则召回
知识图谱召回
多 Query 召回
HyDE 伪文档召回
```

多路召回能提高候选覆盖率，但也会带来一个新问题：候选结果变多、变杂、重复、分数不可比。

如果直接把多路召回结果拼起来塞给 LLM，会出现几个典型问题：

- 不同召回器的分数体系不一致，无法直接比较。
- 同一个 chunk 可能被多路重复召回，浪费上下文窗口。
- 高分结果不一定真正相关，尤其是向量检索里的“语义相似但事实不对”。
- 低质量候选混入 Top K，导致 LLM 生成时被噪声干扰。
- 召回数量越多，如果没有重排序，最终答案质量反而可能下降。

所以多路召回后必须有一层结果处理机制：融合、去重、归一化、加权、阈值过滤和重排序。

> [!summary] 核心判断
> 多路召回负责“尽量别漏”，结果融合与重排序负责“别把噪声放进上下文”。RAG 的检索质量不只取决于召回了多少内容，更取决于最后进入 LLM 的 Top K 是否真正相关。

## 二、核心结论

多路召回后的结果不能直接拼接使用。

正确做法是把候选结果统一进入一个融合排序层：

```text
多路召回结果
  → 结果合并
  → 文档去重
  → 分数归一化
  → 来源权重融合
  → 动态阈值过滤
  → Rerank 重排序
  → Top K 上下文
```

这一层的目标不是继续扩大召回，而是从候选集合中挑出最适合回答当前问题的内容。

一句话概括：

> 多路召回融合的关键，是先让正确答案进入候选集，再通过归一化、去重、加权、动态阈值和 Rerank，把真正相关的候选排到最前面。

## 三、它在 RAG 链路中的位置

完整 RAG 检索链路可以简化为：

```text
用户问题
  → Query 优化
  → 多路召回
  → 结果融合与重排序
  → 上下文构造
  → LLM 生成
```

这篇文档关注的是“多路召回之后、上下文构造之前”的结果处理阶段。

它解决的不是“如何召回更多”，而是“召回之后如何把结果排好、筛好、控好质量”。

## 四、推荐技术流程

推荐的工程流程是：

```text
输入：用户 query + 多路召回候选
  → 统一候选结构
  → 按 chunk_id / content_hash 去重
  → 对不同召回器分数做归一化
  → 按召回来源设置权重
  → 计算融合分
  → 根据当前 query 的分数分布动态过滤
  → 使用 Reranker 或 LLM 进一步重排
  → 输出 Top K 给上下文构造层
```

候选结果最好统一成类似结构：

```json
{
  "chunk_id": "doc_001_chunk_003",
  "content": "文档片段正文",
  "source": "bm25",
  "raw_score": 12.8,
  "normalized_score": 0.86,
  "final_score": 0.78,
  "metadata": {
    "doc_id": "doc_001",
    "section": "退款规则"
  }
}
```

这样后续才能稳定做融合、排序、排障和评估。

## 五、分阶段实践

### 1. 第一阶段：合并与去重

多路召回后，第一步不是排序，而是合并和去重。

常见重复来源包括：

- BM25 和向量检索命中了同一个 chunk。
- 多个扩展 query 召回了同一段内容。
- 同一文档被不同切片策略重复覆盖。
- 内容相同但格式略有差异。

推荐去重优先级：

```text
chunk_id
  → doc_id + chunk_index
  → canonical_url
  → content_hash
  → 近似文本相似度
```

不要只用纯文本字符串去重，因为解析、清洗、换行、空格都可能导致同一内容变成不同字符串。

去重时还要保留召回来源。

如果一个 chunk 同时被 BM25 和向量检索命中，它不应该简单丢掉其中一路信息，而应该记录：

```json
{
  "chunk_id": "chunk_001",
  "sources": ["bm25", "vector"],
  "scores": {
    "bm25": 12.8,
    "vector": 0.82
  }
}
```

多路同时命中本身就是一种相关性信号。

### 2. 第二阶段：分数归一化

不同召回器的原始分数不能直接比较。

例如：

```text
BM25 score = 18.5
向量相似度 = 0.83
图检索置信度 = 0.6
规则命中 = true
```

这些分数不在同一量纲里，直接相加没有意义。

常见归一化方式包括：

- Min-Max Normalization：把分数压到 0-1。
- Z-score：基于均值和标准差标准化。
- Rank-based Normalization：不看绝对分，只看排名。
- RRF：Reciprocal Rank Fusion，基于排名做融合。

工程上，如果不同召回器分数分布差异很大，RRF 往往比直接加权更稳。

RRF 的直觉是：

```text
一个文档在多路召回中排名都靠前
  → 它更可能是真正相关文档
```

它不依赖不同召回器的原始分数是否可比，因此很适合多路召回融合的初始版本。

### 3. 第三阶段：来源权重融合

归一化后，可以根据业务特点对不同召回来源设置权重。

例如：

```text
final_score =
  bm25_score * 0.4
  + vector_score * 0.4
  + rule_score * 0.2
```

权重不是固定答案，要看业务。

如果业务里有大量精确术语、产品型号、政策编号，BM25 或规则召回的权重可能更高。

如果业务里用户表达非常口语化，向量检索权重可能更高。

如果涉及权限、地域、时间、文档类型，metadata filter 和规则命中甚至应该作为硬约束，而不是普通加分项。

一个常见误区是：所有召回来源统一平均。

这会导致强业务信号被稀释。例如用户明确问“日本办公室报销标准”，如果 metadata 已经识别出 `region = Japan`，不应该让其他区域文档仅凭语义相似进入高排名。

### 4. 第四阶段：动态阈值过滤

静态阈值的问题是不能适配不同 query 的分数分布。

例如固定规则：

```text
score < 0.5 全部丢弃
```

在一些 query 上可能过严，导致没有可用上下文；在另一些 query 上又可能过松，保留大量噪声。

动态阈值的核心是根据当前 query 的候选结果分布来决定过滤标准。

常见策略包括：

```text
基于平均分：
  score >= mean

基于平均分和标准差：
  score >= mean - α * std

基于 Top1 衰减：
  score >= top1_score * ratio

基于分位数：
  保留 top 70% 分位以上

基于最小候选数：
  至少保留 min_k，避免上下文为空
```

动态阈值的目标不是“过滤越多越好”，而是控制噪声，同时保证有足够上下文。

推荐保留两个边界：

```text
min_k：至少保留多少个候选
max_k：最多保留多少个候选
```

否则可能出现两种极端：

- query 稍微难一点，候选全被过滤掉。
- query 很宽泛，候选过多，LLM 上下文被噪声淹没。

### 5. 第五阶段：Rerank 重排序

融合分只能解决一部分问题。

如果业务对答案准确性要求更高，还需要 Rerank。

Rerank 的作用是对候选文档和用户 query 做更细粒度的相关性判断。

常见方案有三类：

```text
规则 Rerank
  → 成本低，适合强业务规则

专用 Reranker / Cross-Encoder
  → 质量和延迟相对平衡，适合线上主链路

LLM Rerank
  → 语义判断强，但成本和延迟高，适合低频高价值场景或兜底
```

LLM Rerank 的典型做法是：

```text
输入：用户 query + 候选文档
输出：0-100 的相关性分数
```

Prompt 应该约束：

- 只判断相关性。
- 不生成答案。
- 只输出整数分数或 JSON。
- `temperature` 设置为 0。

例如输出：

```json
{
  "chunk_id": "chunk_003",
  "score": 85,
  "reason": "文档直接解释了 LlamaIndex 与大语言模型的关系"
}
```

线上使用时，最好不要让 LLM 对大量候选逐个评分。

更稳的策略是：

```text
多路召回得到 Top 50
  → 规则融合过滤到 Top 20
  → 专用 Reranker 排到 Top 5
  → 必要时 LLM 对 Top 5 做最终判断
```

## 六、工程落地中的坑

### 1. 不同召回分数直接相加

问题表现：

- BM25 分数天然更大，压过向量检索。
- 向量分数区间更窄，排序影响被低估。
- 不同 query 下排序不稳定。

推荐处理：

- 先做归一化。
- 或优先使用 RRF 这类基于排名的融合方法。

### 2. 去重时丢掉来源信息

问题表现：

- 一个文档被多路命中，但最终只保留了一路分数。
- 无法判断文档为什么排在前面。
- 后续排障缺少证据。

推荐处理：

- 去重后保留所有召回来源和原始分数。
- 把“多路命中”作为加权信号。

### 3. 动态阈值过于激进

问题表现：

- 有些 query 没有上下文。
- LLM 被迫凭空回答。
- 召回质量看似提高，但覆盖率下降。

推荐处理：

- 设置 `min_k`。
- 对低置信度结果触发追问或降级策略。
- 评估 Recall@K，而不是只看过滤后的 Precision。

### 4. LLM Rerank 默认全量开启

问题表现：

- 延迟明显增加。
- 成本不可控。
- 高并发下吞吐下降。
- 评分偶尔不稳定。

推荐处理：

- 默认使用规则融合或专用 Reranker。
- LLM Rerank 只用于高价值、低频、复杂问题。
- 对 LLM 评分结果做缓存。
- 控制候选数量，避免对几十上百个 chunk 逐个打分。

### 5. 只看最终答案，不看检索中间过程

问题表现：

- 答案错了，但不知道是召回问题、融合问题、Rerank 问题还是生成问题。
- 参数调优靠感觉。

推荐处理：

必须记录：

- 原始 query。
- 扩展 query / HyDE 伪文档。
- 每一路召回结果。
- 原始分数。
- 归一化分数。
- 融合分数。
- 阈值过滤结果。
- Rerank 分数。
- 最终进入上下文的 Top K。

没有这些日志，就无法系统调优 RAG。

## 七、质量评估指标

结果融合与重排序不能只靠主观观察。

推荐评估指标包括：

| 指标 | 作用 |
|---|---|
| Recall@K | 正确文档是否进入候选集合 |
| Precision@K | Top K 中相关文档比例 |
| MRR | 正确答案第一次出现的位置 |
| NDCG | 排序质量，越相关的文档越应该靠前 |
| Context Recall | 生成答案需要的信息是否进入上下文 |
| Answer Faithfulness | 最终答案是否忠实于召回上下文 |
| Latency | 融合和重排带来的额外延迟 |
| Cost | Rerank 尤其是 LLM Rerank 的调用成本 |

其中最容易被忽视的是 NDCG 和 MRR。

RAG 不是只要“召回到”就够了。如果正确文档排在第 20 位，而最终只取 Top 5，那它对生成阶段没有任何帮助。

## 八、推荐落地路径

推荐按下面顺序落地：

### 1. 先做最小可用融合

从 BM25 + 向量检索开始。

先实现：

- 候选合并。
- chunk_id 去重。
- Top K 控制。
- 基础日志。

### 2. 加入 RRF 或简单权重融合

不要一开始就复杂化。

先用 RRF 或简单归一化加权，让多路召回结果有一个稳定的融合排序。

### 3. 加入动态阈值和 min_k / max_k

根据当前 query 的候选分布过滤弱相关结果。

同时保留最小候选数量，避免上下文为空。

### 4. 引入专用 Reranker

当融合排序仍然不能满足质量要求时，再引入专用 Reranker。

这通常比 LLM Rerank 更适合线上主链路。

### 5. 对复杂问题使用 LLM Rerank

LLM Rerank 适合作为增强策略，而不是默认策略。

可以只在以下场景触发：

- 候选结果分数接近，排序不确定。
- 用户问题价值高。
- 检索结果冲突明显。
- 普通 Reranker 置信度低。

### 6. 建立评估集和调参闭环

最终要用评估集调权重和阈值。

不要只凭单个 demo 决定：

- BM25 权重多少。
- 向量权重多少。
- 阈值保留多少。
- Rerank 取 Top 几。

不同业务数据分布差异很大，参数必须通过评估集验证。

## 九、最终沉淀

多路召回能提高覆盖率，但覆盖率不是最终目标。

真正影响 RAG 答案质量的是：正确内容是否被召回、是否排在前面、是否进入最终上下文，以及噪声是否被有效过滤。

工程上不能把多路召回结果简单拼接给 LLM，而应该建立统一的结果融合与重排序层：先去重和归一化，再做权重融合和动态阈值过滤，最后根据质量要求选择规则 Rerank、专用 Reranker 或 LLM Rerank。

一句话总结：

> RAG 多路召回后的核心不是“召回越多越好”，而是通过融合、去重、归一化、动态阈值和重排序，让最相关、最可信、最能回答问题的内容优先进入 LLM 上下文。
