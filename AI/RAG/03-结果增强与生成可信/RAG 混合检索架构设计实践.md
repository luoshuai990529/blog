# RAG 混合检索架构设计实践

## 一、问题背景

RAG 检索阶段最常见的问题不是“完全搜不到”，而是“召回结果不稳定”：有时关键词命中了但语义不对，有时语义相似但缺少关键事实，有时召回了很多片段但真正有用的内容排在后面。

单一路召回方式通常有明显边界：

- BM25 这类关键词检索擅长精确匹配，但不擅长同义表达和语义泛化。
- 向量检索擅长语义相似，但容易召回语义接近却事实不精确的片段。
- 图检索或关系检索适合实体关系明确的场景，但构建成本更高。

真实业务问题往往同时包含关键词、语义和上下文关系。

因此，生产级 RAG 通常不会只依赖单一检索方式，而是通过混合检索把多路召回结果组合起来，再经过分数融合、阈值过滤和重排，得到更可靠的上下文。

> [!summary] 核心判断
> 混合检索的本质不是简单把 BM25 和向量检索结果拼起来，而是通过多路召回、分数归一化、权重融合、阈值过滤和 Rerank，把关键词精确匹配和语义泛化能力组合成更稳定的召回体系。

## 二、核心结论

混合检索要解决的是两个问题：

1. **覆盖率**：正确答案要尽量进入候选集合。
2. **精度**：真正相关的内容要排在前面，并最终进入 LLM 上下文。

可以用一句话理解：

```text
多路召回负责尽量别漏
分数融合负责合并候选
阈值过滤负责去掉弱相关内容
Rerank 负责把真正相关的内容排前面
```

典型链路是：

```text
用户问题
  → BM25 关键词召回
  → 向量语义召回
  → 可选图检索 / 规则召回
  → 合并去重
  → 分数归一化
  → 权重融合
  → Score 阈值过滤
  → Rerank 重排
  → TopK 上下文
  → LLM 生成答案
```

## 三、它在 RAG 链路中的位置

完整 RAG 链路可以简化为：

```text
文档接入
  → 文档解析
  → 清洗
  → 分块
  → 建索引
  → 多路召回
  → 融合排序
  → Rerank
  → LLM 生成
  → 评估反馈
```

混合检索位于“检索召回”和“重排”之间。

它依赖前面的分块质量和索引质量，也会直接影响后面的生成质量。

如果混合检索设计不好，会出现几类问题：

- BM25 和向量检索各自召回了一批结果，但分数不可比，融合后排序失真。
- 召回结果太多，LLM 上下文被弱相关内容污染。
- 召回结果太少，正确答案没有进入候选集合。
- 权重参数拍脑袋设置，线上效果不稳定。
- 没有评估集，无法判断到底是关键词召回差、向量召回差，还是融合策略差。

## 四、混合检索的基本架构

最常见的混合检索架构是：

```text
BM25 / 全文检索
  + Dense Vector Search
  → Merge
  → Normalize
  → Weighted Fusion
  → Rerank
```

其中：

- BM25 负责关键词、术语、编号、专有名词的精确匹配。
- Dense Vector Search 负责语义相似、同义表达、自然语言问题的泛化召回。
- Merge 负责合并多路候选并去重。
- Normalize 负责把不同检索通道的分数拉到可比较尺度。
- Weighted Fusion 负责根据业务偏好调整关键词和语义的占比。
- Rerank 负责用更强的相关性模型做最终排序。

可以把它理解为：

```text
BM25：找“字面上像”的内容
向量检索：找“语义上像”的内容
Rerank：判断“真正该排前面”的内容
```

## 五、关键词检索和语义检索的互补关系

BM25 和向量检索的能力是互补的。

### 1. BM25 更适合精确匹配

例如：

- 错误码。
- 产品型号。
- 政策条款编号。
- API 字段名。
- 法律条文。
- 专有术语。

这类问题如果只依赖向量检索，可能会召回语义相似但事实不精确的内容。

BM25 的价值是：

```text
只要关键词命中明确，召回结果可解释、稳定、成本低。
```

### 2. 向量检索更适合语义泛化

例如：

```text
用户问：账号被封怎么处理？
原文写：账户异常限制后的申诉流程。
```

关键词不完全一致，但语义接近。

这类场景向量检索更容易召回正确内容。

### 3. 混合检索解决两者边界

混合检索不是为了替代其中任何一种，而是让两者互补：

```text
BM25 解决精确性
向量检索解决泛化性
融合和重排解决最终排序
```

## 六、Dify 中的混合检索配置

Dify 知识库中常见三类检索设置：

1. **向量检索**：基于 embedding 做语义相似检索。
2. **全文检索**：基于 BM25 做关键词匹配。
3. **混合检索**：同时使用向量检索和全文检索。

混合检索通常需要配置两个关键参数。

### 1. 权重

权重表示更偏向语义检索还是关键词检索。

例如：

```text
语义检索权重：0.7
关键词检索权重：0.3
```

可以理解为更偏向语义召回。

如果总共取 10 个候选，可以粗略理解为：

```text
语义召回 7 个
关键词召回 3 个
```

实际实现中不一定完全按比例切分，但核心思想是通过权重控制两路召回的影响力。

### 2. Score 阈值

Score 阈值用于过滤低相关结果。

如果召回结果分数太低，即使数量没有达到 TopK，也不应该强行塞给 LLM。

否则会带来两个问题：

- 弱相关上下文污染答案。
- LLM 在无关内容中强行找答案，增加幻觉风险。

因此，混合检索中应该同时控制：

```text
召回数量
  + 分数阈值
  + 最终上下文长度
```

## 七、Milvus 与 LlamaIndex 的实现思路

文稿中用 LlamaIndex + Milvus 演示混合检索实现。

这里的重点不是某几行 API，而是理解几个工程概念。

### 1. Milvus 版本选择

Milvus 常见形态包括：

| 版本 | 特点 | 是否适合混合检索 |
|---|---|---|
| Lite | 类似本地轻量文件库 | 不适合，通常不支持完整全文检索 |
| Standalone | 单机独立进程 | 适合开发和中小规模验证 |
| Distributed | 分布式部署 | 适合更大规模生产 |
| Cloud | 云服务 | 适合托管化使用 |

需要注意：

> Milvus Lite 不支持完整全文搜索能力，因此不适合用来验证 BM25 + 向量的完整混合检索。

开发环境更推荐用 Standalone，通常可以通过 Docker Compose 启动，服务端口常见为 `19530`。

### 2. 稀疏嵌入和密集嵌入

混合检索里经常会看到两个概念：

- 稀疏嵌入：更接近关键词、BM25、全文检索。
- 密集嵌入：常见 embedding 向量，用于语义相似检索。

可以这样理解：

```text
Sparse Embedding
  → 处理关键词匹配

Dense Embedding
  → 处理语义相似
```

混合检索就是同时维护这两类索引，并在查询时同时使用。

### 3. hybrid query mode

在 LlamaIndex 这类框架中，设置：

```text
query_mode = "hybrid"
```

通常表示查询会同时走稀疏检索和密集检索。

然后框架负责把两路结果融合。

但不要误以为设置了 `hybrid` 就万事大吉。

真正影响效果的是：

- 文档分块是否合理。
- 稀疏检索是否命中关键词。
- dense embedding 是否适合业务语料。
- 两路 score 是否可比。
- alpha 权重是否合理。
- 是否有 Rerank 和评估。

## 八、alpha 权重怎么理解

`alpha` 是混合检索中常见的权重参数。

一般可以这样理解：

```text
alpha 越大
  → 越偏向语义 / dense vector 检索

alpha 越小
  → 越偏向关键词 / sparse 检索
```

例如：

```text
alpha = 0.1
  → 更偏关键词

alpha = 0.9
  → 更偏语义
```

不同业务可以有不同倾向：

| 场景 | 建议倾向 |
|---|---|
| 政策条款、错误码、产品型号 | 更偏关键词 |
| 自然语言问答、同义表达多 | 更偏语义 |
| 术语丰富的企业知识库 | 关键词和语义平衡 |
| 古文、长文、表达差异大 | 混合后再重排 |

但是 alpha 不能拍脑袋确定。

更合理的方式是基于评估集调参：

```text
alpha = 0.2 / 0.5 / 0.8
  → 分别跑评估集
  → 比较 Recall@K、MRR、答案正确率
  → 选择最适合业务的配置
```

## 九、分数归一化为什么重要

混合检索最容易踩的坑是：不同检索通道的分数尺度不一致。

例如：

```text
向量检索分数：99、98、97
关键词检索分数：0.99、0.98、0.97
```

如果直接做加权：

```text
0.7 * 向量分 + 0.3 * 关键词分
```

分数量级大的通道会天然占优。

这会导致一个问题：

> 用户以为自己设置了语义 0.7、关键词 0.3，但实际排序几乎完全被某一路分数主导。

所以混合检索中必须关注分数归一化。

常见处理方式包括：

- Min-Max 归一化。
- Z-score 标准化。
- Rank-based fusion。
- Reciprocal Rank Fusion。
- 框架内置归一化策略。

核心不是固定选哪种算法，而是保证不同召回通道的分数能在同一尺度下比较。

## 十、Rerank 在混合检索中的角色

混合检索扩大了召回覆盖，但也会带来更多候选噪声。

因此混合检索后通常需要 Rerank。

推荐链路是：

```text
BM25 TopN
  + Dense TopN
  → 合并去重
  → 分数融合
  → Rerank
  → Final TopK
```

Rerank 的价值是：

- 重新判断 query 和 chunk 的真实相关性。
- 把弱相关但分数高的候选往后排。
- 把关键词不完全匹配但语义真正相关的候选往前排。
- 控制最终进入 LLM 上下文的内容质量。

可以这样分工：

```text
多路召回负责覆盖
Rerank 负责精排
LLM 负责基于高质量上下文生成答案
```

## 十一、可扩展的混合检索方案

混合检索不局限于 BM25 + dense vector。

可以扩展为：

- BM25 + Dense Vector。
- BM42 + Dense Vector。
- BGE-M3 Sparse + Dense。
- SPLADE Sparse + Dense。
- 关键词 + 向量 + 图检索。
- 规则召回 + 关键词召回 + 向量召回。

这些方案本质上都是：

```text
多路召回
  → 统一候选格式
  → 分数处理
  → 融合排序
  → 重排
```

在工程设计上，推荐把召回器抽象成统一接口：

```text
Retriever
  → BM25Retriever
  → DenseRetriever
  → SparseEmbeddingRetriever
  → GraphRetriever
  → RuleRetriever
```

每一路召回器输出统一结构：

```json
{
  "chunk_id": "xxx",
  "content": "候选文本",
  "score": 0.87,
  "source": "bm25",
  "metadata": {
    "doc_id": "doc_1",
    "page": 3
  }
}
```

这样后续合并、归一化、重排和观测都会更容易。

## 十二、工程落地中的坑

### 1. 不要把混合检索理解为简单拼接结果

直接把 BM25 TopK 和向量 TopK 拼起来，容易出现重复、噪声和排序混乱。

至少要做：

- 去重。
- 分数归一化。
- 权重融合。
- 阈值过滤。
- Rerank。

### 2. 不要忽略 score 归一化

不同通道分数不可比时，权重参数会失真。

如果框架没有自动处理，应该自己在融合层做归一化。

### 3. 不要只调 alpha，不建评估集

alpha 不是经验参数。

必须用真实业务问题集评估：

- Recall@K。
- MRR。
- nDCG。
- 最终答案正确率。
- 答案忠实性。

### 4. 不要让低分结果污染上下文

召回结果不足时，不应该强行补满 TopK。

如果 score 低于阈值，应优先过滤，而不是把弱相关内容塞给 LLM。

### 5. 不要忽略文档切片质量

混合检索解决的是召回方式问题，不会自动修复糟糕的分块。

如果 chunk 本身语义割裂、表格结构丢失、标题上下文缺失，混合检索也很难稳定召回正确证据。

### 6. 不要误用 Milvus Lite 验证完整混合检索

如果要验证全文检索 + 向量检索的完整链路，需要确认所用 Milvus 版本支持对应能力。

Lite 版本适合轻量验证，不适合代表完整混合检索生产能力。

## 十三、推荐落地路径

### 1. 先保留单路基线

先分别跑：

```text
BM25 only
Dense only
```

观察各自在哪些问题上有效，在哪些问题上失败。

### 2. 再做 BM25 + Dense 混合召回

引入混合检索后，先用简单配置验证：

```text
BM25 TopN
Dense TopN
Merge
Rerank
```

不要一开始就引入太多召回通道。

### 3. 建立评估集调 alpha 和阈值

准备真实业务问题和标准答案来源。

对比：

- 不同 alpha。
- 不同 TopN。
- 不同 score 阈值。
- 是否开启 Rerank。

### 4. 加入观测和失败样本分析

记录每次查询的：

- BM25 召回结果。
- Dense 召回结果。
- 融合后结果。
- Rerank 后结果。
- 最终进入 LLM 的上下文。
- 用户反馈。

这样才能定位问题发生在哪一层。

### 5. 再扩展稀疏嵌入或图检索

当 BM25 + Dense 仍无法满足业务时，再考虑：

- BGE-M3。
- SPLADE。
- 图检索。
- 规则召回。

扩展前要先确认问题确实出在召回覆盖，而不是分块、元数据过滤、Rerank 或生成阶段。

## 十四、最终沉淀

混合检索是 RAG 从 demo 走向生产的重要一步。

单一路召回只能覆盖一部分问题：BM25 对关键词精确，向量检索对语义泛化，图或规则检索对关系和业务约束更友好。

工程化的混合检索系统，应该把多路召回器抽象成统一接口，再通过分数归一化、权重融合、阈值过滤和 Rerank 得到最终上下文。

一句话总结：

> RAG 混合检索的关键，不是简单叠加 BM25 和向量检索，而是用多路召回扩大候选覆盖，用分数归一化和权重融合控制排序，用阈值过滤和 Rerank 保证最终进入 LLM 的上下文足够相关、准确和可信。
