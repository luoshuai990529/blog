# RAG 垂直领域长文档分层检索实践

## 一、问题背景

政策、法规、合同、制度、标准规范这类文档和普通知识文章不一样。

它们通常有很强的层级结构：

```text
章
  → 节
    → 条
      → 款
        → 解释说明
```

用户真正需要的答案往往不是一个孤立句子，而是一个条款和它所属章节、适用范围、前置条件、例外情况共同组成的完整语境。

例如用户问：

```text
申请高新技术补贴最高多少钱？需要满足什么条件？
```

普通 RAG 可能只召回一句：

```text
最高补贴 50 万元。
```

这句话本身看似命中了答案，但它缺少关键上下文：

- 这是哪份政策。
- 适用于哪个地区。
- 对应第几章第几条。
- 企业需要满足什么认定条件。
- 是否区分首次认定、重新认定、人才支持或财政补贴。
- 是否有注册地、行业、资质、时间范围等限制。

所以这类场景的核心问题不是“完全搜不到”，而是：

> 检索命中了局部细节，但没有带回足够完整的父级上下文，导致答案断章取义。

## 二、核心结论

垂直领域长文档不适合只用单层 chunk 检索。

更稳的方案是分层检索：

```text
小节点负责精准命中
父节点负责补全上下文
Reranker 负责排序去噪
```

它不是所有 RAG 系统的通用必选项，而是针对强结构、长上下文依赖文档的专项检索增强方案。

> [!summary] 核心判断
> 当文档天然存在“章节—条款—解释”的层级关系，并且答案依赖父级上下文时，应该使用分层索引和父子节点合并：先用叶子节点保证召回精度，再合并父节点保证语境完整。

## 三、它在 RAG 链路中的位置

这类方案处在 RAG 的“文档分块、索引构建、检索召回”之间。

完整链路可以理解为：

```text
文档解析
  → 保留章节结构
  → 构建父子节点
  → 叶子节点向量化
  → 检索命中叶子节点
  → 自动合并父节点
  → Rerank 重排序
  → 构造完整上下文
  → LLM 生成答案
```

它和普通分块策略的区别在于：

- 普通分块更关注 chunk 大小和语义连续性。
- 分层检索更关注 chunk 在原文结构中的父子关系。

它和知识图谱也不完全一样。

可以借鉴知识图谱的“实体与关系”思想，但工程落地时，通常先从文档结构关系做起，例如：

```text
章节 contains 条款
条款 contains 解释段落
段落 belongs_to 条款
```

不需要一开始就构建完整的实体关系图谱。

## 四、适用与不适用场景

### 适用场景

分层检索适合处理强结构、强上下文依赖的长文档，例如：

- 政策文件。
- 法律法规。
- 企业制度。
- 合同条款。
- 招投标文件。
- 医疗指南。
- 金融规则。
- 技术标准和行业规范。

这些文档的共同特点是：

```text
局部条款可以被精准命中
但局部条款通常不能独立解释
必须结合父级章节、适用范围和前置条件
```

### 不适用场景

不建议所有 RAG 都默认使用分层检索。

它不太适合：

- 短 FAQ。
- 普通博客文章。
- 无明显层级结构的网页内容。
- 用户只问简单事实的问题。
- 文档本身很短，普通 chunk 已能覆盖完整语义。
- 高并发低延迟场景中，对父节点合并成本非常敏感的链路。

如果文档没有稳定结构，强行做层级索引可能只会增加复杂度。

## 五、推荐技术流程

推荐流程如下：

```text
原始长文档
  → 解析标题、章节、条款、段落
  → 构建父节点、中间节点、叶子节点
  → 叶子节点进入向量索引
  → 用户 query 检索叶子节点
  → 根据父子关系自动合并父节点
  → 对合并后的候选做 Rerank
  → 取 Top K 构造上下文
  → LLM 基于完整上下文回答
```

一种常见的三层设计是：

```text
Level 1：章节级父节点
  → 覆盖一章或较大语义单元

Level 2：条款级中间节点
  → 覆盖一个条款或条款组

Level 3：解释段落 / 句子级叶子节点
  → 用于实际向量检索
```

叶子节点负责命中问题，父节点负责补齐上下文。

## 六、分阶段实践

### 1. 第一阶段：保留文档天然结构

垂直领域长文档的结构本身就是重要信息。

解析时不能只抽纯文本，还要尽量保留：

- 标题。
- 章节编号。
- 条款编号。
- 父级标题。
- 层级路径。
- 适用范围。
- 生效时间。
- 发布机构。
- 文档版本。

推荐在 metadata 中保存结构路径：

```json
{
  "doc_id": "policy_001",
  "doc_title": "某市高新技术企业补贴政策",
  "chapter": "第二章 支持范围",
  "article": "第四条 财政补贴",
  "path": "第二章 支持范围 > 第四条 财政补贴",
  "region": "某市",
  "effective_date": "2026-01-01"
}
```

这些 metadata 后续可以用于过滤、溯源和答案引用。

### 2. 第二阶段：构建父子节点

分层检索的关键是父子节点关系。

可以按下面方式理解：

```text
父节点：
  第二章 支持范围

中间节点：
  第四条 财政补贴

叶子节点：
  首次认定为高新技术企业的，给予一次性 30 万元补贴；符合重点支持条件的，最高不超过 50 万元。
```

检索时命中叶子节点，但返回时可以合并中间节点或父节点。

节点大小没有固定标准，需要根据文档结构调试。

常见经验是：

```text
父节点：覆盖一个章节或较大条款组
中间节点：覆盖一个条款
叶子节点：覆盖一个解释段落或若干句子
```

如果使用 LlamaIndex，可以用 `HierarchicalNodeParser` 构建多层节点，用 `AutoMergingRetriever` 在检索时自动合并父节点。

这里要注意：框架组件只是实现手段，核心不是 API，而是“子节点精准召回，父节点补全语境”这个设计。

### 3. 第三阶段：叶子节点建索引

不建议直接把父节点全部作为向量检索单位。

父节点太大时，embedding 会变得粗糙，容易降低命中精度。

更稳的做法是：

```text
叶子节点进入向量索引
父节点保存在文档存储或节点关系中
```

检索流程是：

```text
query
  → 检索叶子节点
  → 找到叶子节点对应父节点
  → 按规则合并父节点
```

这样可以同时兼顾：

- 小粒度检索的精度。
- 大语境回答的完整性。

### 4. 第四阶段：父节点合并

父节点合并不是无脑越大越好。

需要控制几个参数：

- 命中多少个子节点时触发父节点合并。
- 合并到中间节点还是顶层章节节点。
- 合并后总 token 是否超出上下文预算。
- 多个叶子节点属于同一父节点时是否合并去重。
- 父节点是否包含太多弱相关内容。

推荐策略：

```text
默认合并到条款级父节点
只有多个叶子节点都指向同一章节时，再合并到章节级父节点
```

这样可以避免一个小问题把整章甚至整份文档都带进上下文。

### 5. 第五阶段：Rerank 重排序

分层检索会扩大候选上下文，因此更需要 Rerank。

初步召回结果可能包含：

- 精准命中的叶子节点。
- 合并后的父节点。
- 同章节下的相关条款。
- 分数较低但语境有帮助的补充节点。

这些候选不能只按原始向量相似度排序。

推荐加入专用 Reranker，例如 BGE Reranker，对 query 和候选节点做二次相关性评分。

流程是：

```text
叶子节点召回
  → 父节点合并
  → 候选节点重排
  → 取 Top K
```

如果候选数量很少，Reranker 效果可能不明显；如果候选数量较多，Reranker 对过滤弱相关父节点很有价值。

## 七、工程落地中的坑

### 1. 叶子节点过小，召回碎片化

问题表现：

- 命中的是一个金额、日期或短句。
- 答案缺少适用条件。
- LLM 无法判断这个金额属于哪个条款。

处理方式：

- 保留父子关系。
- 检索叶子节点后合并父节点。
- 在 metadata 中保留章节路径。

### 2. 父节点过大，导致上下文污染

问题表现：

- 一个问题带回整章内容。
- LLM 被大量弱相关条款干扰。
- 答案变得宽泛或混入其他政策。

处理方式：

- 优先合并到条款级节点。
- 控制父节点最大 token。
- 对合并后的候选做 Rerank。

### 3. 条款编号和标题丢失

问题表现：

- 答案能说内容，但无法说明来自哪一条。
- 用户无法溯源。
- 多份政策相似时容易混淆。

处理方式：

- 解析阶段保留标题和条款编号。
- metadata 中保存完整 path。
- 生成答案时要求引用条款来源。

### 4. 把分层检索误当成完整知识图谱

问题表现：

- 一开始就尝试抽取复杂实体关系。
- 工程成本过高。
- 迟迟无法落地。

处理方式：

- 第一阶段只做文档结构层级。
- 等业务确实需要实体关系推理时，再引入知识图谱。
- 不要把 Hi-RAG 概念复杂化成必须建设完整图谱。

### 5. 父节点合并后 Top K 失控

问题表现：

- 原本召回 Top 5，合并父节点后上下文变成十几段。
- LLM 输入成本上升。
- 关键信息被噪声稀释。

处理方式：

- 合并后重新去重。
- 合并后重新计算 token 预算。
- 合并后再做 Rerank。
- 设置最终上下文 `max_k` 和最大 token 数。

## 八、质量评估指标

垂直领域长文档检索不能只看“是否召回到某个句子”。

更应该关注：

| 指标 | 说明 |
|---|---|
| Leaf Recall@K | 叶子节点是否命中具体答案 |
| Parent Recall@K | 父级章节或条款是否被带回 |
| Context Completeness | 答案所需条件、范围、例外是否完整 |
| Citation Accuracy | 引用的章节、条款是否正确 |
| Answer Faithfulness | 答案是否忠实于召回上下文 |
| Token Cost | 父节点合并后上下文成本是否可控 |
| NDCG / MRR | 关键节点是否排在前面 |

尤其要单独评估 Context Completeness。

政策类问答中，答案只说“最高 50 万”是不够的；如果没有说明适用范围和申请条件，这个答案仍然是不完整的。

## 九、推荐落地路径

### 1. 先做结构保留

先确保解析阶段能保留：

- 章节标题。
- 条款编号。
- 文档层级。
- 元数据。

没有结构数据，后续分层检索很难稳定。

### 2. 再做父子分块

先实现最简单的父子关系：

```text
条款正文作为叶子节点
条款标题和所属章节作为父节点
```

不用一开始就做复杂图谱。

### 3. 再做自动父节点合并

当叶子节点命中后，根据父子关系自动带回父节点。

先合并到条款级，再根据需要合并到章节级。

### 4. 加入 Reranker

候选节点变多后，引入 Reranker 做语义重排，避免弱相关父节点进入上下文。

### 5. 建立垂直领域评估集

准备一批真实问题，例如：

- 金额类问题。
- 条件类问题。
- 流程类问题。
- 适用范围类问题。
- 例外条款类问题。

每个问题标注：

- 正确叶子节点。
- 必要父节点。
- 标准答案。
- 引用来源。

用这批评估集调节点大小、合并策略和 Rerank 参数。

## 十、最终沉淀

垂直领域长文档检索的核心矛盾，是“精准命中”和“上下文完整”之间的矛盾。

小 chunk 容易精准命中，但容易丢失父级语境；大 chunk 上下文完整，但检索精度会下降。

分层检索的价值，是把这两个目标拆开：用叶子节点负责命中，用父节点负责补全，用 Reranker 负责排序去噪。

它不应该被当成所有 RAG 系统的默认方案，而应该在政策、法规、合同、制度、标准规范这类强结构长文档场景中使用。

一句话总结：

> RAG 垂直领域长文档分层检索的关键，是先用细粒度叶子节点命中具体条款，再通过父节点合并补全章节、条件和适用范围，最终让答案既精准又不脱离原文语境。
