# RAG 自动化评估与参数调优实践

## 一、问题背景

RAG 系统有很多可以优化的地方：

- 切片长度。
- 滑动窗口。
- Top K。
- Embedding 模型。
- 倒排索引。
- 向量索引。
- 混合检索。
- Rerank。
- Query 改写。
- HyDE。

问题是，这些优化是否真的有效，不能只靠人工观察几次回答。

如果没有稳定的评估集和指标体系，很容易出现几种情况：

- demo 看起来变好了，真实业务问题没有提升。
- 某个参数在一个问题上有效，在另一类问题上变差。
- 检索指标提升了，但最终答案质量没有提升。
- 答案看起来更完整，但其实引入了上下文里没有的内容。
- 引入复杂优化后，质量提升很小，但成本和延迟明显增加。

所以 RAG 调优不能只靠经验拍脑袋，而应该像软件测试一样，有固定测试集、标准答案、指标和批量实验流程。

> [!summary] 核心判断
> RAG 自动化评估的价值，是把“感觉效果更好”变成“指标证明更好”。只有建立评估集和指标体系，才能判断切片、检索、重排、生成等优化是否真的提升业务效果。

## 二、核心结论

RAG 评估要解决三个问题：

```text
检索是否召回了正确上下文
  → 上下文是否足够回答问题
  → 最终答案是否忠实于上下文
```

自动化评估的基本流程是：

```text
构建评估集
  → 固定 question / ground_truth
  → 批量运行不同 RAG 配置
  → 记录 answer / contexts
  → 计算评估指标
  → 比较质量、成本和延迟
  → 选择最适合当前业务的参数组合
```

一句话概括：

> RAG 参数调优的关键，不是找到一个通用最优参数，而是基于业务评估集，在质量、成本和延迟之间找到最稳的组合。

## 三、它在 RAG 链路中的位置

自动化评估不是 RAG 链路中的某一个单点组件，而是贯穿所有阶段的质量反馈层。

它可以评估：

```text
文档解析是否丢信息
分块是否割裂语义
检索是否召回关键上下文
Rerank 是否把正确内容排前面
Prompt 是否让答案忠实于上下文
最终答案是否满足业务标准
```

可以把它理解为 RAG 工程里的测试系统：

```text
RAG 链路变更
  → 运行固定评估集
  → 输出指标变化
  → 判断是否接受变更
```

没有评估体系，RAG 优化就很难持续迭代。

## 四、Ragas 的作用

Ragas 是一个用于评估 RAG 系统的开源工具。

开源地址：[vibrantlabsai/ragas](https://github.com/vibrantlabsai/ragas)

它的核心作用是把 RAG 运行过程中的几个关键字段组织起来，然后计算评估指标。

典型输入包括：

```text
question：用户问题
answer：模型生成答案
contexts：检索到的上下文
ground_truths：人工标注的标准答案
```

这些字段可以对应到 RAG 链路中的不同环节：

| 字段 | 对应环节 | 作用 |
|---|---|---|
| question | 用户输入 | 被评估的问题 |
| contexts | 检索结果 | 判断检索是否召回了有用信息 |
| answer | 生成结果 | 判断最终回答质量 |
| ground_truths | 标准答案 | 用于衡量答案与预期的差距 |

Ragas 的价值不是替代业务判断，而是提供一个可批量执行的评估框架。

工程上仍然需要自己建设高质量评估集。

## 五、核心评估指标

### 1. Answer Relevance：答案相关性

Answer Relevance 衡量最终答案和用户问题是否相关。

例如用户问：

```text
RAG 如何避免切片语义割裂？
```

如果模型回答的是向量数据库部署方式，即使内容本身正确，答案相关性也应该较低。

这个指标主要观察生成阶段是否回答了用户真正问的问题。

### 2. Context Relevancy：上下文相关性

Context Relevancy 衡量检索出来的上下文和用户问题是否相关。

它关注的是检索阶段。

例如用户问：

```text
补贴最高多少钱？
```

如果召回的是政策背景介绍，而不是金额条款，上下文相关性可能不高。

### 3. Recall：召回覆盖

Recall 衡量检索上下文中是否包含回答问题所需的关键信息。

它和上下文相关性不同。

一个上下文可以“看起来相关”，但仍然没有包含关键答案。

例如：

```text
问题：申请补贴最高多少钱？

召回上下文：介绍了高新技术企业补贴政策背景。

缺失信息：最高 50 万元。
```

这种情况上下文可能相关，但召回覆盖不足。

### 4. Faithfulness：忠实度

Faithfulness 衡量最终答案是否基于检索到的上下文生成。

如果答案中出现了 contexts 里没有的信息，就说明模型可能在幻觉。

这个指标在 RAG 里很重要，因为 RAG 的目标不是让模型自由发挥，而是让答案有依据。

## 六、评估集怎么设计

RAG 评估集应该像软件测试用例一样长期维护。

一条评估样本最好包含：

```json
{
  "question": "申请高新技术补贴最高多少钱？",
  "ground_truth": "符合条件的企业最高可获得 50 万元补贴，首次认定可获得 30 万元补贴。",
  "expected_context": [
    "第二章 支持范围",
    "第四条 财政补贴"
  ],
  "tags": ["政策", "金额", "条件"],
  "difficulty": "medium"
}
```

评估集不要只包含简单问题。

建议覆盖：

- 简单事实问题。
- 条件类问题。
- 金额类问题。
- 流程类问题。
- 多跳问题。
- 模糊 query。
- 专业术语 query。
- 需要上下文补全的问题。
- 容易幻觉的问题。

评估集越贴近真实业务，评估结果越有价值。

## 七、典型实验设计

### 1. 倒排索引 vs 向量索引

倒排索引适合关键词精确匹配，例如：

- 政策编号。
- 产品型号。
- 人名地名。
- 合同条款号。
- 专业术语。

向量索引适合语义匹配，例如：

- 用户口语化提问。
- 同义表达。
- 模糊问题。
- 语义相关但关键词不同的问题。

实验设计可以是：

```text
固定评估集
  → 使用 BM25 / TF-IDF 跑一遍
  → 使用向量检索跑一遍
  → 记录 contexts 和 answer
  → 用 Ragas 评估
  → 比较 Context Relevancy、Recall、Faithfulness、Answer Relevance
```

注意不能用一两个问题就得出结论。

示例里向量索引在语义类问题上表现更好，但这不代表向量索引永远优于倒排索引。

真实业务中更常见的是混合检索。

### 2. 切片长度调优

切片长度本身的原理可以放在切片策略文档里。

在评估文档里，更重要的是设计一个可复用的参数实验。

实验设计：

```text
固定文档集
固定评估问题集
固定 Embedding 模型
固定检索方式
只改变 chunk_size
  → 重新切片
  → 重新建索引
  → 重新检索
  → 记录 contexts / answer / latency / token cost
  → 评估 Recall、Context Relevancy、Faithfulness、Answer Relevance
```

建议对比维度：

- 召回是否更完整。
- 上下文是否更相关。
- 答案是否更忠实。
- 索引体积是否增加。
- 检索延迟是否变高。
- 最终 token 成本是否可接受。

不要只看答案相关性。

如果答案相关性高，但 Faithfulness 低，说明模型可能靠自身知识猜对了，不能证明切片策略更好。

### 3. 滑动窗口调优

滑动窗口和 overlap 的原理在切片策略文档里已经展开。

这里关注的是如何验证 overlap 是否真的带来收益。

实验设计：

```text
chunk_size = 200, overlap = 50
chunk_size = 300, overlap = 100
chunk_size = 500, overlap = 100
```

每组参数必须跑同一批评估问题。

比较时不要只看质量指标，还要记录成本指标：

- Context Relevancy。
- Recall。
- Faithfulness。
- Latency。
- 索引体积。
- 重复 chunk 比例。
- 最终上下文 token 数。

判断逻辑：

```text
如果 overlap 增大后 Recall 提升明显，且索引体积和延迟可接受
  → 可以保留

如果 overlap 增大后 Recall 提升很小，但重复内容和成本明显上升
  → 不值得使用更大的 overlap
```

最终选择不是单纯分数最高的一组，而是质量、成本、延迟综合最合适的一组。

### 4. Top K 和 Rerank 调优

Top K 和 Rerank 的原理在检索和重排序文档里已经展开。

在评估文档里，重点是验证不同候选规模和重排策略的收益。

实验设计：

```text
召回池大小：Top 20 / Top 50 / Top 100
最终上下文：Top 3 / Top 5 / Top 10
Rerank：off / 专用 Reranker / LLM Rerank
```

重点比较：

- 正确上下文是否进入召回池。
- 正确上下文是否进入最终 Top K。
- Rerank 后正确文档排名是否提升。
- Faithfulness 是否提升。
- Answer Relevance 是否提升。
- 延迟是否可接受。
- Rerank 成本是否可接受。

一个常见误判是：Rerank 后最终答案变好，就认为 Rerank 一定有效。

实际还要看：

```text
如果正确文档根本没有进入召回池
  → Rerank 无法解决召回问题

如果正确文档进入召回池但排在很后面
  → Rerank 才有优化空间
```

因此 Top K 实验要区分两个概念：

- 召回池 Top K：为了给 Rerank 提供足够候选。
- 最终上下文 Top K：真正进入 LLM 的上下文数量。

## 八、工程落地中的坑

### 1. 测试集太小

问题表现：

- 两三个问题得出结论。
- 参数在 demo 上有效，线上失效。
- 某类问题被忽略。

推荐处理：

- 至少覆盖主要业务问题类型。
- 持续从线上失败案例回流评估集。
- 按问题类型分组看指标。

### 2. ground_truth 标注不准

问题表现：

- 指标看起来低，但实际答案没问题。
- 指标看起来高，但标准答案本身缺关键点。

推荐处理：

- 让业务专家参与标准答案建设。
- 标准答案要包含必要事实点。
- 对复杂问题标注 expected_context。

### 3. 只看答案相关性

问题表现：

- 答案看起来相关，但不是基于上下文。
- 模型靠自身知识猜对。
- 检索链路问题被掩盖。

推荐处理：

- 同时看 Context Relevancy、Recall 和 Faithfulness。
- 对检索阶段和生成阶段分开评估。

### 4. 把某次实验参数当成通用最优

问题表现：

- 某次测试 `chunk_size=300, overlap=100` 表现好，就全系统固定使用。
- 换文档类型后效果下降。

推荐处理：

- 不同文档类型单独评估。
- 不同问题类型单独评估。
- 参数选择必须结合业务数据分布。

### 5. 忽略成本和延迟

问题表现：

- 指标提升了，但接口明显变慢。
- Rerank 或 LLM Judge 成本过高。
- 线上吞吐下降。

推荐处理：

- 每次评估同时记录 latency 和 cost。
- 不只比较质量指标。
- 按业务场景选择质量优先或成本优先。

## 九、推荐落地路径

### 1. 先建立小规模评估集

先选 20-50 个高频真实问题。

每个问题至少包含：

- question。
- ground_truth。
- expected_context。
- 问题类型标签。

### 2. 接入自动化评估

先用 Ragas 跑基础指标：

- Answer Relevance。
- Context Relevancy。
- Recall。
- Faithfulness。

把结果保存成表格，方便对比不同实验。

### 3. 做单变量实验

每次只改一个变量。

例如：

```text
只改 chunk_size
只改 overlap
只改 Top K
只改 Embedding 模型
只打开或关闭 Rerank
```

否则很难判断到底是哪一个改动带来了提升或下降。

### 4. 建立参数实验矩阵

将常见参数组合批量跑一遍：

```text
chunk_size: 200 / 300 / 500
overlap: 50 / 100
top_k: 5 / 10 / 20
rerank: true / false
```

输出质量、延迟、成本三类指标。

### 5. 接入持续评估

当 RAG 链路发生变化时自动跑评估：

- 新增文档解析策略。
- 修改切片参数。
- 更换 Embedding 模型。
- 调整检索权重。
- 改 Prompt。
- 引入 Rerank。

如果指标明显下降，就不能直接上线。

后续可以结合 LangSmith 或 CI 流水线，把评估变成固定回归测试。

## 十、最终沉淀

RAG 优化不是堆技巧，而是做实验。

切片长度、滑动窗口、倒排索引、向量索引、混合检索、Rerank 都只是候选方案；它们是否有效，必须放到固定评估集里验证。

自动化评估的关键是建立一套能复用的测试集和指标体系，把每次链路改动都转化为可比较的数据：召回有没有变好、上下文是否完整、答案是否忠实、成本和延迟是否可接受。

一句话总结：

> RAG 自动化评估与参数调优的核心，是用业务评估集和指标体系替代主观感觉，让每一次分块、检索、重排和生成优化都有可量化的质量、成本和延迟依据。
