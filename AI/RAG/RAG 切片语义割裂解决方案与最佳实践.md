# RAG 切片语义割裂解决方案与最佳实践

## 一、问题背景

在 RAG 系统里，文档不会整体丢给大模型，而是会先被解析、切片、向量化，再通过检索召回相关片段。

如果切片策略不好，原本连贯的一段语义可能被切断，后续检索和生成都会受到影响。

典型问题可以用几句话概括：

- 一个完整观点被切成两块，检索只召回前半句，模型就缺少关键上下文。
- chunk 太小，信息不完整；chunk 太大，又会混入噪声，影响模型判断。
- overlap 设置太小补不回上下文，设置太大又会造成大量重复和无关内容。
- 固定长度切片不懂语义，可能把段落、句子、表格、定义、案例硬切开。
- 向量检索只召回“相似片段”，但如果正确语义分散在多个 chunk 里，模型仍然答不好。

> [!summary] 核心判断
> RAG 切片的目标不是“把文档切成固定大小”，而是把文档切成语义完整、大小可控、可检索、低噪声的知识单元。

## 二、核心解决方案

切片语义割裂问题没有单一最优解，最佳实践通常是组合策略：

> 先用语义切分识别自然语义边界，再对过大的语义块使用句子滑动窗口做二次切分，必要时结合关键词保护和 overlap 保留上下文。

整体链路可以概括为：

```text
原始文档
  → 按句子 / 段落预处理
  → 识别关键词、术语、标题、结构边界
  → 语义切分：找到话题转换点
  → 检查 chunk 大小
  → 过大 chunk 用滑动窗口二次切分
  → 保留 overlap 和元数据
  → 入向量库 / 全文索引
  → 召回后重排与上下文补全
```

这套方案解决两个核心矛盾：

- 语义切分解决“语义完整性”问题。
- 滑动窗口解决“上下文保留和大小可控”问题。

## 三、第一阶段：不要直接依赖 Token 切片

Token 切片是最简单的方式：按固定 token 数切。

优点：

- 实现简单。
- 长度可控。
- 适合模型上下文很小的场景。

缺点：

- 容易把句子切断。
- 对中文语义不友好。
- overlap 补偿有限。
- 对复杂文档不稳定。

适合场景：

- 简单文本。
- 对语义完整性要求不高。
- 强制需要控制 token 长度。

Token 切片可以作为兜底策略，但不建议作为复杂 RAG 的默认切片方案。

## 四、第二阶段：使用句子切片作为基础方案

句子切片会优先保证句子完整，再考虑 chunk size。

相比 Token 切片，它至少不会把一句话从中间切断，因此更适合作为普通文本的基础切片方案。

常见流程：

```text
文档
  → 按句号、换行、段落边界切分
  → 保留完整句子
  → 按 chunk_size 聚合句子
  → 加少量 chunk_overlap
```

它的局限是：

- chunk size 是软约束，可能超过设定值。
- overlap 往往以句子为单位，实际长度不容易精确控制。
- 相关上下文如果距离较远，仍然可能被切到另一个 chunk。

适合场景：

- 普通文章。
- FAQ。
- 说明文档。
- 入门级 RAG 系统。

## 五、第三阶段：引入句子窗口补全上下文

句子窗口的核心思路是：

> 以当前句子为中心，把前后 N 句一起作为上下文。

示例：

```text
当前命中句子：第 5 句
window_size = 2

最终上下文：
第 3 句 + 第 4 句 + 第 5 句 + 第 6 句 + 第 7 句
```

它的价值是：

- 检索可以精准命中某一句。
- 生成时又能拿到前后上下文。
- 适合解释型回答、摘要生成、上下文依赖强的问答任务。

但句子窗口仍然是“线性上下文”，只能解决前后连续的问题。

如果两个相关观点分散在文档不同位置，句子窗口无法自动聚合。

## 六、第四阶段：使用句子滑动窗口减少边界割裂

句子滑动窗口是更实用的工程版本。

它不是单句独立处理，而是让窗口不断向后滑动，并保留一定重叠。

示例：

```text
chunk 1: 句子 1-5
chunk 2: 句子 4-8
chunk 3: 句子 7-11
```

优点：

- 相邻 chunk 有重叠，边界不容易断。
- 保留局部上下文。
- chunk 大小比纯语义切分更可控。

缺点：

- 会产生重复内容。
- overlap 太大会增加索引和检索成本。
- 仍然不理解深层语义关系。

适合场景：

- 长文章。
- 技术文档。
- 说明书。
- 政策文件。
- 需要保留上下文的问答任务。

## 七、第五阶段：引入关键词保护

关键词保护的作用是：在切片时检查重要术语、专有名词、指标名、标题、定义是否被切断。

例如：

```text
Transformer
Vision Transformer
Cost Per Unit
卷积神经网络
合同解除条件
```

如果关键词刚好落在边界附近，就动态调整边界，把关键词和必要上下文保留在同一个 chunk 中。

关键词来源可以包括：

- 领域术语词库。
- 标题层级。
- 用户高频查询词。
- 文档里的加粗词、编号、字段名。
- NER 抽取出的实体。
- 业务专家维护的核心概念表。

这一阶段可以和 [[RAG 领域术语词库与检索一致性优化实践]] 结合使用。

## 八、第六阶段：使用语义切分识别话题边界

语义切分的核心是：计算相邻句子之间的语义相似度，判断哪里是话题转换点。

基本逻辑：

```text
句子 1 和句子 2 相似 → 合并
句子 2 和句子 3 相似 → 继续合并
句子 3 和句子 4 不相似 → 切开
```

优点：

- chunk 更符合自然语义。
- 不容易把一个完整观点拆开。
- 适合逻辑性强、主题切换明显的长文档。

缺点：

- 需要 embedding 模型，成本更高。
- 相似度阈值难调。
- chunk 大小不可控。
- 可能生成过长 chunk，导致 embedding 截断。

适合场景：

- 法律文档。
- 医疗文档。
- 政策文件。
- 技术文章。
- 逻辑结构强的知识文档。

## 九、第七阶段：使用混合切片策略

最终推荐的工程方案是混合切片：

```text
先语义切分，再滑动窗口二次切分
```

完整流程：

1. 先按句子切分文档。
2. 计算相邻句子的语义相似度。
3. 根据阈值切出语义段落。
4. 检查每个语义块的 token 数。
5. 如果语义块小于阈值，直接保留。
6. 如果语义块超过阈值，再用句子滑动窗口切成多个子块。
7. 子块之间保留 overlap。
8. 每个 chunk 保存来源、页码、标题、父级语义块 ID。

这套方案兼顾：

- 语义完整性。
- chunk 大小可控。
- 上下文连续性。
- 检索鲁棒性。
- 后续可追溯性。

可以这样理解：

> 语义切分负责找“该不该切”，滑动窗口负责控制“怎么切得可用”。

## 十、工程落地中的坑

### 1. 不要迷信固定 chunk size

很多人一上来就设置：

```text
chunk_size = 512
chunk_overlap = 50
```

这只能作为起点，不能作为最终方案。

不同文档结构差异很大，固定参数无法覆盖所有场景。

### 2. overlap 不是越大越好

overlap 太小，补不回上下文。

overlap 太大，会带来：

- 重复 chunk 增多。
- 向量库膨胀。
- 检索结果重复。
- 上下文噪声增加。
- 成本上升。

overlap 只适合做边界补偿，不应该指望它解决所有语义问题。

### 3. 句子切片可能超出模型限制

句子切片为了保证句子完整，可能让 chunk 超过设定大小。

所以 `chunk_size` 不要贴着 embedding 模型或 LLM 的最大上下文设置，要留安全余量。

### 4. 语义切分阈值很难一次调好

阈值太高：

- 切得太碎。
- 语义块过短。
- 上下文不足。

阈值太低：

- 合并过多。
- chunk 过长。
- 噪声增加。
- embedding 可能截断。

需要基于真实业务问题和召回效果调参。

### 5. 语义切分成本更高

语义切分需要对句子做 embedding，然后计算相似度。

文档量大时，需要考虑：

- 预处理耗时。
- embedding 成本。
- 批处理能力。
- 缓存机制。
- 增量更新。

不适合所有低价值文档都深度处理。

### 6. 关键词保护不能只靠高频词

高频词不一定是重要词。

例如“系统”“方法”“问题”很高频，但价值不大。

关键词最好来自：

- 术语词库。
- 标题。
- 业务指标。
- 用户查询日志。
- 专业实体识别。
- 人工维护的核心概念表。

### 7. 切片必须保留元数据

每个 chunk 至少要保留：

- 原始文档 ID。
- 标题层级。
- 页码 / 段落位置。
- 父级语义块 ID。
- chunk 序号。
- 前后 chunk 关系。
- 关键词 / 术语标签。

否则后续无法做引用、回溯、父子 chunk 扩展和问题排查。

### 8. 切片效果必须用召回评估验证

不能只看切出来的 chunk “感觉还行”。

应该建立测试集：

```text
用户问题
标准答案
应该召回的文档 / 段落
实际召回 chunk
最终生成答案
```

重点看：

- 是否召回正确 chunk。
- 是否召回完整上下文。
- 是否有大量重复。
- 是否有无关噪声。
- 答案是否因为切片缺失而错误。

## 十一、推荐落地方案

### 简单文档

使用句子切片即可。

```text
句子切片 + 少量 overlap + 元数据保留
```

### 普通长文档

使用句子滑动窗口。

```text
句子切片 → 滑动窗口 → overlap → 入库
```

### 专业领域文档

使用语义切分 + 滑动窗口。

```text
句子预处理
  → 术语 / 关键词识别
  → 语义切分
  → 大块滑动窗口二次切分
  → 保留元数据
  → 混合检索
```

### 高价值复杂文档

结合结构化解析。

```text
标题层级
  + 段落语义
  + 表格边界
  + 图片说明
  + 术语词库
  + 语义切分
  + 滑动窗口
```

## 十二、最终沉淀

切片语义割裂的最佳实践可以总结为：

> 不要把 RAG 切片理解成“按长度切文本”，而要理解成“构造可检索的语义知识单元”。

核心方案是：

```text
结构优先，句子保底，语义定边界，窗口补上下文，关键词防割裂，元数据保回溯，评测闭环持续调参。
```

最终可以用一句话概括：

> RAG 切片的工程最佳实践，是先用语义切分识别自然话题边界，再用句子滑动窗口控制大小和补充上下文，并结合关键词保护与元数据回溯，避免 chunk 语义割裂、召回不完整和上下文噪声过多。
