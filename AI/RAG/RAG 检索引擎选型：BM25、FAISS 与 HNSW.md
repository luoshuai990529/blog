# RAG 检索引擎选型：BM25、FAISS 与 HNSW

## 一、问题背景

RAG 系统的核心不是简单把文档丢进向量库，而是在用户提问时，能从大量知识片段中快速找出最相关的 Top K 上下文。

如果检索阶段找错了内容，后面的 LLM 再强也只能基于错误上下文回答。

真实业务里经常会遇到这类问题：

- FAQ、政策条文、说明书这类内容，用户问题里有明确关键词，但向量检索不一定稳定命中原文。
- 新闻、文章、知识库这类长文本，用户表达和原文不完全一致，需要语义相似召回。
- 电商搜索、客服搜索这类场景，对召回率和延迟要求都很高，普通检索方式可能不够。
- 数据量从几万条增长到几百万、几千万条后，原来的索引方式在内存、延迟和构建时间上开始失控。

所以 RAG 检索引擎选型不能简单理解为“向量检索一定比关键词检索好”，而是要根据业务数据、查询类型、延迟要求、成本预算和可解释性要求做取舍。

> [!summary] 核心判断
> BM25、FAISS IVF、HNSW 解决的是不同检索约束下的召回问题：BM25 擅长关键词精确匹配，FAISS IVF 擅长中大规模语义检索的平衡取舍，HNSW 擅长高召回、低延迟但更吃内存的实时语义检索。

## 二、核心结论

RAG 检索引擎选型可以先记住一个基本判断：

```text
关键词明确、需要解释性、数据量不大
  → 优先考虑 BM25

需要语义相似、数据量中大、希望成本和效果平衡
  → 优先考虑 FAISS IVF

需要高召回、低延迟、内存预算充足
  → 考虑 HNSW

复杂业务场景
  → 通常走 BM25 + 向量检索 + Rerank 的混合检索
```

不要只用“召回率最高”或“速度最快”作为唯一标准。

更合理的选型维度是：

- 数据量。
- 查询类型。
- 召回率。
- 查询延迟。
- 内存占用。
- 建索引成本。
- 增量更新能力。
- 可解释性。
- 部署和合规要求。

## 三、它在 RAG 链路中的位置

RAG 链路可以简化为：

```text
文档接入
  → 文档解析
  → 文本清洗
  → 分块
  → 建索引
  → 检索召回
  → 重排
  → 生成答案
  → 评估反馈
```

这篇文档关注的是“建索引”和“检索召回”阶段。

如果检索引擎选错，会出现几类问题：

- 明明文档里有答案，但召回不到。
- 关键词很明确，却被语义相似但不精确的内容干扰。
- 向量索引很准，但内存成本过高。
- 小数据量用复杂索引，系统复杂度超过收益。
- 大数据量仍用简单方案，延迟和吞吐无法接受。

## 四、三类检索方式的整体对比

| 检索方式 | 本质 | 优势 | 不足 | 适合场景 |
|---|---|---|---|---|
| BM25 | 关键词相关性打分 | 成本低、可解释性强、冷启动快、CPU 友好 | 不擅长语义相似 | FAQ、政策、说明书、法律条文 |
| FAISS IVF | 向量近似搜索 | 速度、召回、成本较平衡 | 可解释性弱，需要 embedding 和索引训练 | 新闻、文章、大规模知识库 |
| HNSW | 图结构近邻搜索 | 召回高、查询延迟低 | 内存占用高、建索引慢 | 电商搜索、客服搜索、实时语义检索 |

这三种方式不是互相替代关系，而是面向不同约束的不同方案。

工程上更常见的做法是：

```text
BM25 负责关键词精确召回
向量检索负责语义相似召回
Rerank 负责统一重排
```

## 五、先区分检索算法、索引结构和检索系统

在工程选型前，需要先区分三个层次。

| 层次 | 代表 | 解决的问题 |
|---|---|---|
| 检索算法 | BM25、向量相似度计算 | 怎么计算相关性 |
| 索引结构 | Flat、IVF、HNSW | 怎么更快地找到候选结果 |
| 检索系统 / 向量数据库 | FAISS、Milvus、Qdrant、Elasticsearch、Weaviate | 怎么存储、过滤、更新、部署和运维 |

BM25 更偏关键词相关性算法。

IVF、HNSW 更偏索引结构。

FAISS 是向量检索库，它提供多种索引结构，但本身不是完整的在线数据库系统。

Milvus、Qdrant、Weaviate、Elasticsearch 这类系统除了检索能力，还会提供：

- 数据持久化。
- 元数据过滤。
- 增量写入。
- 集群部署。
- 权限隔离。
- 监控和运维能力。

所以生产选型不能只问“用 BM25、IVF 还是 HNSW”，还要问：

```text
用什么检索算法
  → 用什么索引结构
  → 用什么数据库或检索系统承载
  → 如何做权限、过滤、更新和观测
```

## 六、第一类：BM25 关键词检索

BM25 是传统搜索引擎里常用的关键词相关性算法。

它关注的是：

- 查询词是否出现在文档中。
- 词在文档中出现的频率。
- 词在整个语料中是否稀有。
- 文档长度对得分的影响。

可以把 BM25 理解成一种增强版关键词匹配。

它不是简单的 SQL `like`，也不是只看是否包含关键词，而是会综合考虑词频、逆文档频率和文档长度。

### 1. BM25 的优势

BM25 在 RAG 中仍然很有价值。

它的优势包括：

- **可解释性强**：能说明为什么某段内容被召回，因为关键词命中了。
- **冷启动快**：不依赖 embedding 模型和向量训练。
- **成本低**：CPU 友好，内存和计算开销较低。
- **增量更新简单**：新增、删除文本通常比向量索引更直接。
- **精确匹配强**：对编号、术语、政策条款、产品型号、错误码非常有效。

### 2. BM25 的局限

BM25 不擅长处理“同义表达”和“语义相似”。

例如：

```text
用户问：怎么申请退款？
原文写：售后退费流程如下。
```

如果没有明显关键词重合，BM25 可能召回效果不稳定。

所以它更适合关键词明确、术语稳定、文本结构强的场景。

### 3. 适合 BM25 的业务

BM25 适合：

- FAQ。
- 政策条文。
- 法律法规。
- 产品说明书。
- 错误码查询。
- API 文档。
- 企业制度。
- 术语词库检索。

如果业务要求“为什么召回这段内容必须能解释”，BM25 往往是必须保留的一路召回。

## 七、第二类：FAISS IVF 向量检索

FAISS 是常见的向量检索库，适合做 embedding 后的相似度搜索。

RAG 中常见流程是：

```text
文本 chunk
  → embedding 模型转向量
  → 写入 FAISS 索引
  → 用户问题转向量
  → 查找相似向量
  → 返回相关 chunk
```

向量检索解决的是“语义相似但关键词不完全一致”的问题。

例如：

```text
用户问：账号被封了怎么办？
原文写：账户异常限制后的申诉流程。
```

关键词不完全一致，但语义接近，向量检索更容易召回。

### 1. IVF 是什么

IVF 可以理解为向量检索里的“先分桶，再查桶”。

它会先把向量空间聚类成多个区域：

```text
全部向量
  → 聚类成多个 bucket
  → 查询时先找到相关 bucket
  → 再在 bucket 内搜索相似向量
```

相比暴力搜索所有向量，IVF 能减少搜索范围，提高查询速度。

代价是：如果 bucket 选错，召回率可能下降。

### 2. FAISS IVF 的优势

FAISS IVF 的核心价值是平衡：

- 比 Flat 暴力搜索更快。
- 召回率通常可以接受。
- 成本比高内存图索引更可控。
- 适合中大规模语义检索。

因此它经常成为 RAG 系统的默认向量检索方案。

### 3. FAISS IVF 的局限

它也有明显限制：

- 可解释性弱，很难说明“为什么这个向量相似”。
- 依赖 embedding 模型质量。
- 需要关注向量维度和索引参数。
- IVF 聚类质量会影响召回效果。
- 大规模数据下需要考虑训练时间和索引维护。

文稿中特别强调了一个坑：

> embedding 模型输出多少维，就应该按对应维度建索引；维度乱设只会浪费内存，甚至导致实际配置无效。

## 八、第三类：HNSW 图结构近邻搜索

HNSW 是一种基于图结构的近似最近邻搜索算法。

它的核心思想是构建多层小世界图。

可以这样理解：

```text
高层图：粗粒度快速跳转
中层图：缩小搜索范围
底层图：精细查找最近邻
```

类似查书：

```text
先看目录
  → 跳到章节
  → 再找具体段落
```

### 1. HNSW 的优势

HNSW 的优势是：

- 召回率高。
- 查询延迟低。
- 适合实时语义搜索。
- 在大规模近邻搜索中表现稳定。

它适合对召回率和延迟要求都很高的业务。

例如：

- 电商搜索。
- 客服知识库。
- 推荐召回。
- 实时语义检索。

### 2. HNSW 的代价

HNSW 不是无脑更好。

它的代价包括：

- 内存占用高。
- 建索引慢。
- 参数调优复杂。
- 小数据量下优势不明显。
- 增量维护成本更高。

因此，在数据量较小、延迟要求不高、内存预算有限时，直接上 HNSW 可能是过度设计。

需要特别注意：

> HNSW 使用图结构做近邻搜索，但它不是知识图谱。

知识图谱强调实体、关系和语义推理；HNSW 的图只是向量索引结构，目的是加速近邻搜索。

如果业务需要表达“公司 A 投资了公司 B”“药品 A 治疗疾病 B”这类实体关系，那是知识图谱问题，不是 HNSW 本身能解决的问题。

## 九、metadata filter 对检索选型的影响

真实 RAG 系统很少是全库无条件检索。

多数业务查询都会带过滤条件：

- 只查某个部门的文档。
- 只查某个项目。
- 只查某个时间范围。
- 只查某个租户的数据。
- 只查用户有权限访问的文档。
- 只查某类文档，例如合同、制度、FAQ、工单。

这会直接影响检索系统选型。

如果系统只支持“先向量召回，再做权限过滤”，可能出现这种问题：

```text
向量检索 Top 20
  → 权限过滤
  → 只剩 1 条甚至 0 条
```

这时不是向量模型不准，而是检索链路设计有问题。

更合理的方式通常是：

```text
先做 metadata pre-filter
  → 在候选集合内做 BM25 / 向量检索
  → 再合并和重排
```

所以如果业务强依赖权限、租户、时间、文档类型过滤，选型时不能只看向量召回性能，还要看检索系统是否支持高效 metadata filter。

这一点也是 FAISS 这类库和 Milvus、Qdrant、Elasticsearch 这类完整系统之间的重要差异。

## 十、召回池、TopK 和 Rerank 的关系

RAG 生产系统里，检索引擎返回的结果通常不应该直接塞给 LLM。

更常见的链路是：

```text
BM25 召回 TopN
  + 向量召回 TopN
  → 合并去重
  → Rerank 重排
  → 截断 TopK
  → 放入 LLM 上下文
```

这里要区分两个概念：

- `TopN`：召回池，目标是尽量别漏掉正确候选。
- `TopK`：最终上下文，目标是在 token 预算内放入最有价值内容。

检索引擎更偏“召回”，Rerank 更偏“排序”。

可以这样理解：

```text
检索引擎负责尽量别漏
Rerank 负责从候选里排准
LLM 上下文负责只放最值得读的内容
```

如果直接让单一路检索返回 TopK 给 LLM，很容易出现两个问题：

- 召回池太小，正确答案没进入候选。
- 候选排序不准，LLM 读到的上下文质量低。

因此，BM25、向量检索、HNSW 的选型不应该孤立看，而要放到“召回 + 融合 + 重排”的完整链路里看。

## 十一、如何评估检索引擎

检索引擎选型不能只看单次 demo 结果。

至少要用以下指标评估：

| 指标 | 说明 | 关注点 |
|---|---|---|
| Recall@K | 前 K 条是否包含正确答案 | 召回质量 |
| MRR | 正确结果排在第几位 | 首个正确结果位置 |
| nDCG | 排序质量 | 多个相关结果的排序效果 |
| P50 延迟 | 50% 请求的响应时间 | 平均体验 |
| P95 / P99 延迟 | 长尾请求耗时 | 线上稳定性 |
| RAM 占用 | 索引占用内存 | 硬件成本 |
| 索引构建时间 | 建索引需要多久 | 冷启动和重建成本 |
| 增量更新成本 | 新增、删除、更新是否方便 | 数据持续变化能力 |
| QPS | 支持多少并发查询 | 服务容量 |

文稿中的测试思路是：

```text
准备固定数据集
  → 构建 BM25 / FAISS / HNSW 检索器
  → 准备查询集
  → 评估 Recall@K
  → 统计查询延迟
  → 统计内存占用
  → 对比结果
```

需要注意：

> 本地笔记本、小样本、单次查询的测试结果只能看趋势，不能直接作为生产选型依据。

正式评估应该在接近生产的数据量、硬件和查询分布下进行。

RAG 还需要额外关注生成质量。

检索评估可以分成两层：

```text
检索层
  → Recall@K、MRR、nDCG、延迟、内存、QPS

生成层
  → Answer Correctness、Faithfulness、Context Precision、Context Recall
```

检索指标好，不代表最终答案一定好；但检索指标差，最终答案通常很难好。

因此，生产环境应该同时保留：

- 检索日志。
- 召回结果。
- Rerank 分数。
- 最终上下文。
- LLM 答案。
- 用户反馈。

否则很难判断问题到底出在分块、召回、重排还是生成阶段。

## 十二、按数据规模做初步选型

可以先用数据规模做粗略判断。

| 数据规模 | 推荐方案 | 原因 |
|---|---|---|
| 小于 10 万条 | BM25 或简单向量检索 | 成本低，系统简单，冷启动快 |
| 10 万 - 100 万条 | FAISS IVF | 兼顾召回、速度和成本 |
| 100 万 - 1000 万条 | FAISS IVF + 更严格参数调优 | 需要关注训练时间、内存和 GPU |
| 大于 1000 万条 | 向量集群 + 分层索引 | 单机索引压力大，需要分布式和多级召回 |

对于超大规模场景，可以考虑：

```text
IVF 做一级粗召回
  → HNSW 做二级近邻搜索
  → Rerank 做最终排序
```

但这个方案复杂度更高，只有在数据量和性能要求达到一定规模时才值得做。

## 十三、更新频率对选型的影响

检索引擎选型不能只看查询速度，还要看索引更新模式。

不同业务的数据更新频率差别很大：

| 更新模式 | 典型场景 | 选型关注点 |
|---|---|---|
| 低频批量更新 | 企业制度、知识手册 | 可以接受离线重建索引 |
| 高频增量更新 | 工单、客服记录、新闻 | 要关注增量写入和删除成本 |
| 实时写入实时查询 | 商品、交易、告警 | 要支持在线更新和低延迟可见 |
| 大规模定期重建 | 全量知识库刷新 | 要关注索引构建时间和灰度切换 |

例如，HNSW 查询很快，但建索引和维护成本更高；FAISS IVF 对大规模批量索引比较友好，但在线增量更新和复杂过滤能力需要额外设计；BM25 在文本增删改和关键词索引上通常更直接。

所以选型时要明确：

```text
数据是一次性导入，还是持续更新？
更新后要求多久可检索？
是否需要删除旧文档？
是否需要灰度切换新旧索引？
```

如果这些问题没有提前设计，后续会在知识库持续更新时暴露出来。

## 十四、工程落地中的坑

### 1. 不要认为向量检索一定优于 BM25

如果用户问题和文档存在明确关键词匹配，BM25 可能比向量检索更稳定。

例如：

- 政策条款编号。
- 错误码。
- 产品型号。
- 法律条文。
- API 字段名。

这些内容往往需要精确匹配，而不是语义泛化。

### 2. 不要只看平均延迟

平均延迟好看，不代表线上体验稳定。

需要同时看：

- P50。
- P95。
- P99。
- 索引加载时间。
- 冷启动耗时。

尤其是 HNSW 和大规模 FAISS 索引，冷启动和索引构建成本不能忽略。

### 3. 向量维度必须匹配 embedding 模型

embedding 模型输出多少维，索引维度就应该是多少。

维度乱设会带来：

- 内存浪费。
- 查询异常。
- 索引不可用。
- 结果不可信。

### 4. IVF 聚类前要关注数据分布

IVF 依赖聚类。

如果数据分布很偏，或者没有打散数据，可能导致部分 bucket 过大、部分 bucket 过小，查询退化或召回下降。

因此建索引前需要关注：

- 数据 shuffle。
- 聚类数量。
- nprobe 参数。
- 数据分布是否均衡。

### 5. 小样本测试不能代表生产效果

用几十条数据测试 BM25、FAISS、HNSW，只能帮助理解接口和结果形态。

生产选型至少要用：

- 真实业务文档。
- 真实用户问题。
- 足够数量的查询集。
- 接近生产的数据规模。
- 接近生产的硬件环境。

### 6. 合规场景要考虑私有化部署

金融、医疗、政务等场景，知识库内容可能不能出公网。

这时需要考虑：

- 私有化向量库。
- 本地 embedding 模型。
- 本地 rerank 模型。
- 数据权限隔离。
- 审计和日志。

FAISS、Milvus、Qdrant、Elasticsearch 等私有化方案都需要纳入选型。

### 7. 不要忽略 metadata filter

如果业务有权限、租户、部门、时间范围过滤，检索系统必须支持高效 metadata filter。

否则会出现“向量召回很准，但过滤后结果为空”的问题。

推荐优先设计：

```text
metadata pre-filter
  → 关键词 / 向量召回
  → 合并重排
```

而不是简单地先全库召回再过滤。

### 8. 不要把 HNSW 当成知识图谱

HNSW 是向量近邻搜索的图索引结构，不是实体关系图谱。

如果业务需要关系推理、实体路径分析、规则约束，那需要知识图谱或图数据库；如果只是加速向量近邻搜索，HNSW 才是合适工具。

### 9. 不要只评估检索，不评估最终答案

RAG 的最终目标不是返回相似片段，而是生成正确、可信、有依据的答案。

因此除了 Recall@K、MRR、nDCG，还要看：

- 答案是否正确。
- 答案是否忠实于上下文。
- 上下文是否包含必要证据。
- 召回内容是否有大量噪声。

## 十五、推荐落地路径

### 1. 先用 BM25 建立关键词基线

先跑一版 BM25，尤其适合 FAQ、说明书、政策制度、术语类文档。

它可以作为关键词召回基线，也可以帮助发现文档和问题中的显式匹配关系。

### 2. 再加入向量检索覆盖语义表达

当用户问题和原文表达不一致时，引入向量检索。

推荐先从 FAISS IVF 或托管向量库开始，不要一开始就做复杂图索引。

### 3. 建立评估集

准备一批真实问题和标准答案来源。

至少评估：

- Recall@5。
- Recall@10。
- MRR。
- nDCG。
- P50 / P95 延迟。
- 错误召回样本。
- 无召回样本。
- 最终答案正确率。
- 答案忠实性。

### 4. 根据瓶颈选择 HNSW 或集群方案

当数据规模、召回要求和延迟要求都提升后，再考虑 HNSW 或分层索引。

不要在小数据量阶段过早引入高复杂度索引。

### 5. 根据更新频率设计索引维护方式

如果文档低频更新，可以接受定期离线重建索引。

如果文档高频更新，需要重点验证：

- 新增文档多久可检索。
- 删除文档是否能及时生效。
- 索引重建是否影响线上查询。
- 是否需要新旧索引灰度切换。

这一步决定系统能不能从 demo 走向持续运行。

### 6. 用召回池 + Rerank，而不是直接把检索 TopK 给 LLM

推荐设计：

```text
多路召回 TopN
  → 合并去重
  → Rerank
  → 截断 TopK
  → 送入 LLM
```

这样可以降低单一检索方式漏召回的风险。

### 7. 最终走向混合检索

真实业务中更推荐：

```text
BM25 召回
  + 向量召回
  → 结果合并
  → Rerank 重排
  → Top K 上下文
  → LLM 生成
```

这样可以同时利用：

- BM25 的精确匹配和可解释性。
- 向量检索的语义泛化能力。
- Rerank 的排序优化能力。

如果已经明确需要同时利用关键词精确匹配和语义召回能力，可以继续参考 [[RAG 混合检索架构设计实践]]，重点关注多路召回、分数归一化、权重融合、阈值过滤和 Rerank。

## 十六、最终沉淀

BM25、FAISS IVF、HNSW 不是简单的优劣关系，而是不同业务约束下的检索工具。

BM25 适合关键词明确、需要可解释性和低成本的场景；FAISS IVF 适合中大规模语义检索，是召回、速度、成本之间的平衡方案；HNSW 适合高召回、低延迟、内存预算充足的实时语义检索。

真正工程化的 RAG 系统，通常不会只依赖单一检索方式，而是通过 BM25、向量检索、metadata filter、Rerank、评估集和线上观测组合成完整检索链路。

总结：

> RAG 检索引擎选型的关键不是判断 BM25、FAISS、HNSW 谁更先进，而是同时考虑索引结构、检索系统、元数据过滤、更新频率、召回池大小、Rerank 和最终答案质量，选择适合业务约束的混合检索体系。
