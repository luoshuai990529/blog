# RAG 检索前 Query 优化实践

## 一、问题背景

RAG 系统经常假设用户会提出一个清晰、完整、适合检索的问题。

但真实用户的问题通常不是这样。

用户可能会问：

```text
我想去好玩的地方
这个能退吗
附近有没有能坐下来的地方
有没有推荐的
这个政策怎么走
```

这些问题的问题不在于 LLM 不会回答，而在于检索系统很难理解“应该去知识库里找什么”。

常见问题包括：

- 用户表达太短。
- 问题过于口语化。
- 缺少主语、地点、对象、时间、约束条件。
- 用户表达和知识库表达不一致。
- 一个问题里混合了多个子任务。
- 高风险场景下缺少关键参数，不能直接猜。

如果直接把原始 query 丢给 BM25 或向量检索，容易出现：

- 召回结果太宽泛。
- 召回不到真正相关 chunk。
- 检索结果包含大量弱相关内容。
- LLM 最终回答宽泛、不聚焦，甚至产生幻觉。

> [!summary] 核心判断
> 检索前 Query 优化是 RAG 中位于“用户提问”和“检索召回”之间的 Query Processing 环节，目标是把模糊、口语化、不完整的问题转换成更适合检索的表达。

## 二、核心结论

Query 优化不是单纯 Prompt 工程。

Prompt 是实现 query 改写、扩展、拆解的一种手段；Query 优化本身属于 RAG 检索策略。

它关注的是：

```text
用户原始问题是否适合直接检索
  → 是否需要改写
  → 是否需要扩展
  → 是否需要拆解
  → 是否需要追问
  → 是否需要抽取 metadata filter
  → 最终如何提升召回质量
```

一句话概括：

> Query 优化的价值，是在检索前把用户自然语言问题变成更容易命中知识库的检索表达，从源头提升 Recall@K、Context Recall 和最终答案质量。

## 三、它在 RAG 链路中的位置

RAG 检索链路可以拆成：

```text
用户问题
  → Query 理解 / Query 优化
  → 检索召回
  → 多路融合
  → Rerank
  → 上下文构造
  → LLM 生成
```

Query 优化处在检索之前。

它不直接负责生成答案，也不直接负责重排结果，而是决定“用什么问题去检索”。

如果 query 表达错误，后面检索和重排都会受到影响。

例如：

```text
原问题：这个能退吗？
```

系统需要判断：

- “这个”指什么商品？
- 是退货、退款还是售后？
- 是否需要结合对话上下文？
- 是否需要提取商品类型作为 metadata filter？
- 是否应该追问用户，而不是直接检索？

## 四、Query 优化和 Prompt 工程的关系

Query 优化和 Prompt 工程有交集，但不是同一个概念。

可以这样区分：

```text
Prompt 工程
  → 怎么写指令，让 LLM 完成改写、扩展、拆解

Query 优化
  → 为什么要改写，什么时候改写，怎么验证改写是否提升检索

RAG 检索工程
  → 改写后的 query 如何进入 BM25、向量检索、混合检索和 Rerank
```

所以：

```text
Prompt 工程 = 实现手段
Query 优化 = 检索策略
RAG = 所属系统链路
```

例如用户问：

```text
我想去好玩的地方
```

Prompt 工程关注：

```text
如何写 prompt，让 LLM 把问题改写得更具体。
```

Query 优化关注：

```text
是否应该改写？
改写成亲子游会不会偏离意图？
是否应该生成多个 query？
是否应该追问用户？
改写后 Recall@K 是否提升？
```

## 五、常见 Query 优化方法

常见方法可以分成几类：

| 方法 | 作用 | 适用场景 |
|---|---|---|
| Query Rewriting | 把问题改写得更清楚 | 用户表达模糊、口语化 |
| Query Expansion | 扩展同义词、术语、相关表达 | 用户问题缺少检索关键词 |
| Query Decomposition | 把复杂问题拆成多个子问题 | 多条件、多步骤问题 |
| HyDE | 先生成假设答案或假设文档再检索 | 原 query 太短、语义空间不稳定 |
| Clarification | 追问用户补齐关键信息 | 高风险或关键参数缺失 |
| 术语标准化 | 将黑话、缩写、别名转成标准表达 | 专业领域、企业内部术语 |
| Metadata Filter 提取 | 从问题中抽取时间、地区、权限、类型等过滤条件 | 多租户、权限、地域、时间过滤 |
| Multi-Query | 生成多个等价 query 并合并召回 | 表达多样、召回不足 |

这些方法都属于检索前处理，但风险和适用边界不同。

## 六、问题改写：Query Rewriting

Query Rewriting 的目标是把用户原始问题改写得更完整、更适合检索。

例如：

```text
原始问题：
我想去好玩的地方

改写后：
有没有适合亲子游的好玩景点推荐？
```

改写后，检索会更容易命中“亲子游”“景点”“推荐”等相关内容。

常见实现方式是 LLM + Prompt。

Prompt 中通常要说明：

- 模型角色是问题改写器。
- 保留用户原意。
- 补充缺失上下文。
- 输出只包含改写后的问题。

但要注意：

> 改写不是越具体越好，过度改写会带来意图漂移。

如果用户没有任何亲子上下文，直接改写成“亲子游”可能是错的。

更稳妥的方式是：

```text
有上下文
  → 根据上下文改写

无上下文
  → 生成多个候选 query 或追问用户
```

## 七、查询扩展：Query Expansion

Query Expansion 的目标是补充更多可能命中知识库的表达。

它可以扩展：

- 同义词。
- 别名。
- 缩写。
- 领域术语。
- 用户黑话。
- 相关业务标签。

例如：

```text
原始 query：
怎么退款

扩展 query：
退款、退货、售后、退费、无理由退换、退款流程
```

这样可以提升 BM25 和混合检索的召回覆盖。

但扩展也有风险。

如果无脑把所有相关词都拼进去，会带来噪声：

```text
退款
  → 扩展到售后、维修、换货、投诉、赔偿
  → 召回范围过大
  → 上下文污染
```

所以扩展应该结合：

- 当前问题意图。
- 领域词库。
- 用户上下文。
- 文档类型。
- 召回效果评估。

## 八、问题拆解：Query Decomposition

复杂问题通常不适合一次检索完成。

例如：

```text
我想找一个带小朋友玩的地方，最好附近有餐厅。
```

这个问题可以拆成：

```text
子问题 1：有哪些适合亲子游的景点？
子问题 2：这些景点附近有哪些餐厅？
```

执行流程是：

```text
先检索亲子景点
  → 得到候选景点
  → 基于景点继续检索餐厅
  → 合并结果
  → 生成最终答案
```

这类方法适合：

- 多约束问题。
- 多跳问题。
- 需要中间结果的问题。
- 需要工具调用的问题。

可以用普通 pipeline 实现，也可以用 Agent 实现。

## 九、Agent 拆解和工具调用

当问题需要动态选择工具或多步决策时，可以用 Agent。

例如定义两个工具：

```text
find_family_friendly_attractions(query)
find_nearby_restaurants(attraction)
```

Agent 可以根据用户问题决定：

```text
先找亲子景点
  → 再查景点附近餐厅
  → 最后综合推荐
```

但工程上要注意：

> 简单固定流程不一定需要 Agent。

如果流程是固定的，例如永远都是“先查景点再查餐厅”，普通 pipeline 更稳定、更便宜、更可控。

Agent 更适合：

- 工具很多。
- 调用路径不固定。
- 需要根据中间结果动态决策。
- 需要多轮规划。

否则 Agent 会引入额外不确定性、成本和调试难度。

## 十、HyDE：假设文档生成

HyDE，全称是 Hypothetical Document Embeddings，可以理解为“假设文档检索”。

它解决的问题不是“用户问题写得不规范”，而是“用户问题太短、太稀疏，和知识库里的正式文档表达距离太远”。

例如知识库里有一段真实内容：

```text
本产品支持 7 天无理由退货，但定制类商品、生鲜商品、拆封后的数字产品不支持无理由退货。
```

用户可能只问：

```text
这个能退吗？
```

如果直接用这个 query 去检索，会遇到几个问题：

- query 太短，语义信息不足。
- “这个”缺少明确对象。
- “能退吗”是口语表达，和知识库里的“7 天无理由退货”“定制类商品”“生鲜商品”等正式表达距离较远。
- 向量检索只能根据很少的词生成 embedding，容易召回宽泛的售后说明，而不是精确退货规则。

HyDE 的思路是：不直接用原始问题检索，而是先让 LLM 生成一段“假想答案 / 伪文档”，再用这段更像知识库文档的文本去检索。

```text
用户 query 太短或太模糊
  → 先让 LLM 生成一个可能的答案或假设文档
  → 对这个假设文档做 embedding
  → 用它去检索真实文档
```

例如：

```text
原始 query：
这个能退吗？

HyDE 生成的伪文档：
商品退货通常需要查看退货规则，例如是否支持 7 天无理由退货，是否属于定制类商品、生鲜商品、已拆封数字产品等不支持退货的范围。如果商品符合平台退货条件，可以申请退款或退货。
```

这段伪文档虽然不是最终答案，但它包含了更多可能命中知识库的表达：

- 7 天无理由退货。
- 定制类商品。
- 生鲜商品。
- 已拆封数字产品。
- 退款、退货、售后。

这些表达更接近真实文档，因此更容易召回正确 chunk。

### HyDE 和 Query Rewriting 的区别

HyDE 和 Query Rewriting 都属于检索前 Query 优化，但它们生成的东西不同。

Query Rewriting 是把“问题”改写成另一个更清晰的问题。

```text
原始问题：
这个能退吗？

Query Rewriting：
该商品是否支持退货？具体退货规则是什么？
```

HyDE 是把“问题”扩展成一段可能的答案或说明文档。

```text
原始问题：
这个能退吗？

HyDE：
商品是否支持退货通常取决于平台退货规则、商品类型、是否属于定制商品、生鲜商品或已拆封数字产品，以及是否符合 7 天无理由退货条件。
```

可以这样区分：

| 对比点 | Query Rewriting | HyDE |
|---|---|---|
| 生成结果 | 一个更清晰的问题 | 一段假想答案 / 伪文档 |
| 文本形态 | Query | Document |
| 目标 | 让问题更明确 | 让查询文本更像知识库内容 |
| 适合场景 | 用户表达口语化、有歧义、不完整 | query 很短、语义稀疏、和文档表达差距大 |
| 主要风险 | 改错用户意图 | 伪文档幻觉、引入不存在实体 |
| 检索方式 | 用改写后的问题检索 | 用伪文档 embedding 检索 |

一句话理解：

> Query Rewriting 是把问题改成更好的问题；HyDE 是先假装已经有一个答案，用这个假想答案去找真正的知识库答案。

### HyDE 的适用场景

HyDE 更适合：

- 用户 query 非常短，例如“这个能退吗”“怎么走”“有推荐吗”。
- 用户表达和知识库表达差异很大。
- 知识库是说明文、政策、规则、产品文档等“答案型文本”。
- 向量检索召回不足，但 BM25 关键词又很难命中。
- 第一轮对话没有上下文，存在冷启动问题。

例如旅游场景：

```text
原问题：
带娃去哪玩？

HyDE 伪文档：
适合带孩子游玩的地方通常包括主题公园、动物园、科技馆、亲子乐园和儿童友好的度假区，例如上海迪士尼、广州长隆、北京环球影城等。这类地点通常有儿童项目、亲子互动体验和适合家庭游玩的配套设施。
```

这段伪文档比“带娃去哪玩”更容易命中“亲子游”“主题公园”“儿童友好”“家庭游玩”等真实文档内容。

### HyDE 不适合的场景

HyDE 不适合直接用于：

- 高风险事实判断，例如医疗、法律、金融结论。
- 用户问题缺少关键约束，必须先追问。
- 知识库内容非常结构化，metadata filter 比伪文档更可靠。
- 用户 query 已经足够清晰，直接检索效果已经稳定。
- 业务不能接受 LLM 在检索前引入额外假设。

HyDE 的风险是：

- 假设答案可能带偏检索方向。
- 伪文档可能引入知识库中不存在的实体。
- 生成内容越长，越可能引入噪声。
- 高风险业务中不能把假设内容当事实。
- 最终答案必须基于真实召回文档，而不是基于伪文档本身。
- 需要保留原 query、改写 query、HyDE 伪文档和召回结果，便于排查。

工程上更稳的做法是：

```text
原始 query
  → Query Rewriting
  → 必要时生成 HyDE 伪文档
  → 原始 query + 改写 query + HyDE 伪文档一起参与召回
  → Rerank 去噪
  → 只基于真实文档生成答案
```

## 十一、什么时候应该追问用户

不是所有模糊问题都应该自动改写。

在高风险或强约束场景，缺少关键信息时应该追问用户。

例如：

```text
我想买个电脑，有推荐吗？
```

如果系统直接改写成：

```text
推荐适合办公的轻薄本。
```

可能偏离用户真实需求。

更合理的是追问：

```text
你主要用于办公、游戏、剪辑还是编程？预算大概是多少？
```

适合追问的场景：

- 医疗。
- 法律。
- 金融。
- 购物决策。
- 业务审批。
- 参数缺失会影响结果正确性的场景。

可以建立规则：

```text
低风险泛场景
  → 允许 query expansion

高风险决策场景
  → 优先 clarification
```

## 十二、metadata filter 提取

Query 优化不只是改写文本，也可以从 query 中抽取过滤条件。

例如：

```text
日本办公室的报销标准是多少？
```

可以抽取：

```json
{
  "region": "Japan",
  "doc_type": "Expense Policy"
}
```

然后检索时先做 metadata filter：

```text
region = Japan
doc_type = Expense Policy
```

再进入 BM25 或向量检索。

这能减少无关内容干扰，也能保证权限和范围正确。

所以 Query 优化还包括：

- 地区识别。
- 时间范围识别。
- 文档类型识别。
- 用户权限识别。
- 业务对象识别。

## 十三、工程落地中的坑

### 1. 不要对所有问题默认改写

如果用户问题已经足够明确，改写可能反而降低精度。

例如：

```text
iPhone 15 Pro Max 重量是多少？
```

如果扩展成“iPhone 15 系列参数对比”，可能召回更多无关内容。

### 2. 不要让 LLM 擅自补充关键事实

Query 优化可以补充表达，但不能凭空补事实。

例如用户没有说“亲子游”，系统不能默认用户就是亲子游，除非上下文中已有相关信息。

### 3. 不要忽略意图漂移

改写前后要保留意图一致。

建议记录：

```json
{
  "original_query": "我想去好玩的地方",
  "rewritten_query": "有没有适合亲子游的好玩的地方推荐？",
  "strategy": "query_rewrite"
}
```

方便排查和回滚。

### 4. 不要把 query expansion 做成关键词堆砌

扩展词太多会扩大召回范围，导致上下文噪声增加。

扩展要有选择性，并通过评估集验证。

### 5. 不要把 Agent 用在固定流程上

固定流程用 pipeline 更稳定。

Agent 适合动态规划，不适合所有多步检索。

### 6. 不要只看答案相似度

查询优化效果要分层评估：

```text
检索层
  → Recall@K、MRR、nDCG、Context Recall

生成层
  → Answer Correctness、Faithfulness
```

只看最终答案相似度，无法判断到底是改写有效、检索有效，还是 LLM 猜对了。

## 十四、推荐落地路径

### 1. 先识别哪些 query 需要优化

不要全量启用。

优先处理：

- 过短 query。
- 口语化 query。
- 无主语 query。
- 多意图 query。
- 历史召回失败 query。

### 2. 先做 Query Rewriting

从问题改写开始，成本最低。

要求：

- 保留用户原意。
- 不补充没有依据的事实。
- 输出可追踪。

### 3. 再做 Query Expansion、Multi-Query 和 HyDE

对召回不足的问题，引入：

- 同义词扩展。
- 术语扩展。
- 多 query 生成。
- HyDE 伪文档生成。
- 多路召回合并。

其中 Query Expansion 和 Multi-Query 更偏“生成更多检索问题”，HyDE 更偏“生成一个更像知识库答案的伪文档”。

如果用户问题只是口语化，优先 Query Rewriting。

如果用户问题短到几乎没有可用语义，或者和知识库文档表达差距很大，再考虑 HyDE。

### 4. 对复杂问题引入 Query Decomposition

如果问题包含多个子目标，拆成多个检索任务。

先用固定 pipeline，必要时再引入 Agent。

### 5. 对高风险场景加入 Clarification

当缺少关键参数时，不要擅自猜。

优先追问用户。

### 6. 建立评估和日志

必须记录：

- 原始 query。
- 改写 query。
- 扩展 query。
- 使用策略。
- 召回结果。
- Rerank 结果。
- 最终答案。
- 用户反馈。

用这些数据评估 query 优化是否真的提升 RAG 效果。

## 十五、最终沉淀

检索前 Query 优化是 RAG 检索质量的前置环节。

它不是单纯 Prompt 工程，而是 Query Processing：判断用户原始问题是否适合检索，并选择改写、扩展、拆解、追问、HyDE、术语标准化或 metadata filter 提取等策略。

好的 Query 优化能提升召回质量；错误的 Query 优化也会带来意图漂移、噪声扩展和错误召回。

一句话总结：

> RAG 检索前 Query 优化的关键，是在不偏离用户意图的前提下，把模糊、口语化、不完整的问题转换成更适合检索的表达，并通过日志和评估集验证它是否真正提升召回和最终答案质量。
