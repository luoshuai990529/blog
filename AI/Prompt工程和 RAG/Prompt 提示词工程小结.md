# Prompt 提示词工程小结

## 一句话总结

Prompt 工程不是写“神奇咒语”，而是把任务目标、上下文、输入输出、约束、示例和验收标准组织成模型可稳定执行的指令协议。

## 核心结论

1. **Prompt 的本质是任务说明书。** 它告诉模型现在扮演什么角色、要解决什么问题、可以依据哪些信息、应该按什么格式输出。

2. **好 Prompt 的目标是减少歧义。** 指令越模糊，模型越容易补全、猜测和跑偏；生产场景里多轮纠偏会增加成本，也会放大上下文污染。

3. **一次性说清需求通常更稳定。** 对业务任务而言，背景、目标、输入、输出、约束和验收标准越完整，模型第一次输出可用结果的概率越高。

4. **Prompt 可以扩展模型能力，但不能替代真实知识。** 提示词能组织任务和补充少量上下文，但专业知识、实时数据和企业私有知识仍需要 RAG、工具或数据库接入。

5. **清晰具体比花哨技巧更重要。** 大多数任务优先解决“说清楚”问题，再考虑角色设定、Few-shot、反思、改写等高级技巧。

6. **结构化输入输出能降低误解。** JSON、Markdown、XML 标签、分隔符、章节标题可以帮助模型区分系统要求、用户输入、资料区和输出格式。

7. **结构化格式只能降低注入风险，不能彻底防注入。** 防 Prompt Injection 还需要权限隔离、工具调用审批、输入转义、来源标记和不信任外部内容的系统规则。

8. **推理模型更适合简单直接的提示。** 对具备强推理能力的模型，过度引导、复杂模板和冗长技巧可能反而限制模型发挥。

9. **不要要求模型展示完整思维链。** 更推荐要求“给出简要理由”“列出关键步骤”“说明依据和结论”，避免索取隐藏推理过程。

10. **CoT 的价值在于引导分解，不在于暴露全部思考。** 如果需要可解释性，可以让模型输出简短推理摘要、检查清单或最终判断依据。

11. **Few-shot 适合复杂格式和风格对齐。** 当输出格式、判断标准或业务口径难以一句话讲清时，给 1 到 3 个高质量示例通常比继续解释更有效。

12. **角色设定只在影响判断标准时有用。** “你是资深律师/产品经理/客服专家”只有在同时明确任务、约束和输出标准时才有价值。

13. **Step-back Prompting 适合复杂问题。** 先让模型抽象出原则、背景或判断框架，再处理具体问题，可以减少局部误判。

14. **序列思考适合流程型任务。** 对需求分析、排障、规划、审查等任务，可以要求模型按“理解问题 → 制定方案 → 执行 → 验证”的流程输出。

15. **压缩思维链不应理解为压缩隐藏推理。** 更合理的用法是要求模型输出简短步骤摘要，减少冗长解释和 Token 消耗。

16. **ICIO、CRISPE、CO-STAR 本质都是信息清单。** 它们不是固定公式，而是提醒你补齐指令、背景、目标、风格、受众和输出要求。

17. **工程化 Prompt 要分层设计。** 先定义角色和目标，再定义输入输出接口，然后定义工具规则、示例和全局约束。

18. **输入规范要明确边界。** 例如用 `<context>`、`<user_input>`、`<output_format>` 分隔不同信息，避免模型把资料内容误当成指令。

19. **输出规范要可验证。** “写得专业一点”不如明确字数、结构、字段、禁止项、引用方式和验收标准。

20. **工具使用规则必须写清楚。** 如果模型可以调用搜索、数据库、代码执行或业务 API，需要明确什么时候调用、参数怎么填、失败时怎么办。

21. **行为边界是生产 Prompt 的必要部分。** 要明确不能编造、不能泄露系统提示、不能越权调用工具、不能处理超出权限的数据。

22. **Claude 类系统提示的关键价值是能力透明。** 说明知识截止时间、工具能力、不能做什么和遇到不确定时怎么处理，可以让用户形成稳定预期。

23. **对无法完成的任务要直接说明原因。** 比起泛泛道歉，更好的输出是说明限制、缺失信息和可行替代方案。

24. **争议问题要区分事实、观点和不确定性。** 好 Prompt 应要求模型保持中立、给出依据、避免替用户做价值判断。

25. **数学和逻辑题要强调可检查步骤。** 不需要展示完整思维链，但应输出关键推导、公式、假设和最终答案，方便验算。

26. **代码类 Prompt 要约束交付形态。** 需要说明语言、框架、文件结构、边界条件、测试方式和是否允许大范围重构。

27. **Prompt 优化要迭代，不要一次追求完美。** 先写最小可用版本，再用真实样例测试，针对失败案例逐步补规则和示例。

28. **优秀 Prompt 可以复用，但不能照抄。** 官方示例和开源项目适合作为结构参考，具体业务仍要改成自己的数据、边界和验收方式。

29. **让 AI 反问需求是有效的 Prompt 生成方式。** 当任务不清楚时，可以让模型先扮演提示词工程师，提出澄清问题，再生成模板。

30. **Prompt 工程的最终目标是稳定性。** 好 Prompt 不是看起来复杂，而是在不同输入、不同场景、不同用户下仍能输出可控结果。

## 补充结论

1. **不要把 CoT 理解成“展示完整思考过程”。** 对复杂问题，可以要求模型拆解任务并输出关键推理摘要，但不应要求展示完整隐藏思维链；需要可解释性时，输出依据、关键步骤和可验证结论即可。

2. **结构化格式不是安全边界本身。** JSON、Markdown、XML 等格式可以明确资料和指令的边界，降低模型误解概率，但不能单独防止 Prompt Injection；生产系统仍需要权限控制、工具调用约束、来源标记和安全策略。

3. **推理模型更需要清晰目标，而不是复杂模板。** 推理模型通常不需要复杂 CoT 模板；提示应保持目标清晰、约束明确，并要求输出简明理由或验证过程。

## 可复用 Prompt 模板

```markdown
你是一个 {角色}。

## 任务目标
{明确要完成的事情}

## 背景信息
{业务背景、用户场景、已知约束}

## 输入数据
<input>
{用户输入或资料}
</input>

## 输出要求
- 使用 {格式}
- 包含 {必须字段}
- 不要包含 {禁止内容}
- 如果信息不足，请说明缺失项，不要编造

## 判断标准
- {标准 1}
- {标准 2}
- {标准 3}
```

## 最终理解

Prompt 工程的核心能力不是记住多少模板，而是把模糊任务转成可执行协议：目标清楚、资料边界清楚、输出格式清楚、行为约束清楚、失败处理清楚。
