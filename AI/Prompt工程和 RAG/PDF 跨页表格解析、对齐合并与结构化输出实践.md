# PDF 跨页表格解析、对齐合并与结构化输出实践

## 核心结论

PDF 跨页表格解析的难点不在“识别出文字”，而在于同时恢复表格的**版面位置、行列结构、跨页连续关系和单元格内容**，并将结果转成 Markdown、JSON 或结构化字段，供 RAG 后续分块、检索、引用和生成使用。

跨页表格处理的核心链路可以概括为：

```text
PDF 页面
  → 版面分析：找到表格区域
  → 表格结构识别：识别行、列、边框、单元格
  → OCR：识别单元格文字
  → 跨页判断：识别上下页表格是否连续
  → 表头对齐：统一列名和列顺序
  → 内容合并：拼接跨页表格
  → 结构化输出：Markdown / HTML / JSON
  → RAG 入库：分块、索引、引用回溯
```

## 一、为什么跨页表格是 RAG 文档解析难点

在 RAG 系统中，表格类内容经常承载关键事实，例如：

- 合同条款清单
- 案件信息表
- 财务报表
- 产品参数表
- 项目进度表
- 票据字段
- 医疗/法律/政务类结构化记录

普通文本解析只需要保证段落顺序基本正确，但表格解析还要保证：

1. **行列关系正确。** 单元格内容必须落在正确字段下。
2. **表头识别正确。** 没有表头，数据无法解释。
3. **跨页连续正确。** 上一页和下一页可能属于同一张表。
4. **干扰内容剔除。** 页眉、页脚、页码、注释不能混入表格。
5. **OCR 错误可控。** 表格线、数字、专有名词、符号都容易识别错。
6. **结果可回溯。** 结构化结果要能定位回原 PDF 页和原图区域。

如果跨页表格被错误解析，RAG 最终会出现典型问题：

- 答案字段错位。
- 漏掉下一页表格内容。
- 把页码当作表格数据。
- 把两个不同表格误合并。
- 检索能命中表格文本，但模型无法理解行列语义。

## 二、Word 表格和 PDF 表格的本质差异

Word 表格和 PDF 表格在视觉上都像表格，但底层结构完全不同。

| 类型 | 底层结构 | 解析方式 | 难点 |
|---|---|---|---|
| Word 表格 | 有明确 table、row、cell 对象 | 可直接用 `python-docx` 遍历 | 合并单元格、嵌套表格、跨页显示 |
| PDF 表格 | 可能只是坐标、线条、文字或图片 | 需要版面分析、表格识别、OCR | 行列恢复、阅读顺序、跨页合并 |
| 扫描 PDF 表格 | 本质是图片 | 必须 OCR + Layout | 图像质量、倾斜、手写、表格线缺失 |

因此，Word 表格可以从文档结构里“读出来”，PDF 表格更多时候需要从视觉结果里“识别出来”。

## 三、跨页表格的主要挑战

### 1. 表格可能是图片

很多 PDF 不是由可选中文本直接生成，而是扫描件或图片型 PDF。此时：

- 普通 PDF 文本提取拿不到表格内容。
- OCR 可以拿到文字，但不一定知道行列结构。
- 只得到一串文本无法恢复表格语义。

### 2. 表头和数据可能分离

跨页表格中，下一页可能没有重复表头，也可能只保留部分表头。

常见情况：

- 第一页有完整表头，第二页只有数据。
- 第二页重复表头，但列宽略有变化。
- 表头被页眉或页码打断。
- 多级表头跨页后层级丢失。

### 3. 行列可能错位

PDF 中表格线、文本块、坐标识别存在误差，跨页后容易出现：

- 列数不一致。
- 单元格被拆开。
- 多行文本被当成多行数据。
- 一行数据跨两页。
- 合并单元格无法还原。

### 4. 页眉页脚干扰

跨页表格中间经常夹杂：

- 页码
- 页眉
- 页脚
- 水印
- 文档标题
- 注释

这些内容如果没有过滤，会被错误并入表格。

### 5. OCR 本身有错误

OCR 对以下内容容易出错：

- 数字和符号
- 专有名词
- 法律/医学术语
- 表格边框附近的文字
- 低清晰度扫描件
- 手写内容

因此跨页表格解析不能只依赖 OCR 文本，必须结合布局和结构。

## 四、推荐的技术流程

### 1. 版面分析 Layout Analysis

第一步不是 OCR，而是先判断页面中有哪些区域。

版面分析要识别：

- 标题区域
- 正文区域
- 表格区域
- 图片区域
- 公式区域
- 页眉页脚
- 注释区域

对跨页表格来说，最重要的是先判断：

> 当前页是否存在表格区域，以及表格区域是否延续到页面底部或从页面顶部开始。

如果 layout 阶段没有识别出表格区域，后续 OCR 再准也很难恢复结构。

### 2. 表格检测 Table Detection

版面分析找到表格候选区域后，需要进一步判断表格边界。

关键任务：

- 找到表格外框。
- 找到横线和竖线。
- 判断行边界。
- 判断列边界。
- 识别合并单元格。
- 识别无框表格或弱线表格。

对于无边框或弱边框表格，还需要根据文本对齐、坐标分布和列间距推断结构。

### 3. 单元格 OCR

表格结构确定后，再对每个单元格执行 OCR。

这样做比整页 OCR 更稳定，因为：

- 每个单元格的识别范围更小。
- OCR 结果能绑定到具体行列。
- 可以避免页眉页脚混入表格。
- 后续可以针对单元格做校验和修正。

输出最好不是一段纯文本，而是：

```json
{
  "page": 1,
  "table_id": "table_1",
  "cell": {
    "row": 3,
    "col": 2,
    "text": "案件类型",
    "bbox": [100, 200, 300, 240]
  }
}
```

### 4. 跨页连续性判断

跨页表格合并前，需要判断两页表格是否属于同一张表。

判断信号包括：

1. **表格位置连续。** 上一页表格接近页底，下一页表格接近页顶。
2. **列数一致。** 两页表格列数相同或高度相似。
3. **列宽相似。** 各列横向坐标分布相近。
4. **表头一致。** 下一页重复表头或可继承上一页表头。
5. **字段语义一致。** 列内容类型一致，例如日期列、金额列、说明列。
6. **文档上下文一致。** 两页之间没有新的章节标题或不同表格标题。

不能只靠“相邻两页都有表格”来合并，否则容易把两个不同表格误合并。

### 5. 表头对齐 Header Alignment

跨页合并的关键是表头对齐。

常见处理方式：

- 如果下一页没有表头，继承上一页表头。
- 如果下一页有表头，和上一页表头做相似度匹配。
- 如果列名 OCR 有误，用语义相似度和位置关系修正。
- 如果列数不同，尝试识别合并单元格或缺失列。

表头对齐可以综合使用：

- 字符串相似度
- Embedding 相似度
- 列坐标相似度
- 字段类型校验
- LLM 辅助判断

### 6. 表格合并

合并阶段要做：

1. 去掉重复表头。
2. 删除页眉、页脚、页码。
3. 对齐列顺序。
4. 合并被分页拆断的行。
5. 保留每一行的原始页码和 bbox。
6. 输出统一 Markdown 或 JSON。

推荐保留两类结果：

- **面向 LLM 的 Markdown 表格。**
- **面向程序处理和回溯的 JSON 结构。**

Markdown 适合直接进入 RAG 文本索引：

```markdown
| 序号 | 案件名称 | 案件类型 | 处理结果 |
|---|---|---|---|
| 1 | xxx | 民事 | 已结案 |
| 2 | yyy | 行政 | 审理中 |
```

JSON 适合溯源、调试和结构化查询：

```json
{
  "table_id": "table_1",
  "pages": [1, 2],
  "headers": ["序号", "案件名称", "案件类型", "处理结果"],
  "rows": [
    {
      "values": ["1", "xxx", "民事", "已结案"],
      "source": {
        "page": 1,
        "bbox": [100, 200, 500, 240]
      }
    }
  ]
}
```

## 五、MinerU 在跨页表格解析中的实践价值

它的价值在于把 PDF 解析拆成一条完整 pipeline：

```text
模型初始化
  → 版面预测
  → 文档格式检测
  → OCR 识别
  → 表格预测
  → 内容输出
```

在跨页表格场景中，它通常会输出：

- layout 中间结果
- 表格区域图像
- OCR 结果
- Markdown 文件
- JSON 文件
- 原始文件副本

这些中间产物非常重要，因为它们可以用来判断问题发生在哪一层。

| 中间结果 | 用途 |
|---|---|
| layout 可视化 | 检查是否正确识别表格区域 |
| 表格裁剪图 | 检查表格区域是否完整 |
| OCR 结果 | 检查文字识别是否正确 |
| Markdown | 供 LLM 阅读和 RAG 入库 |
| JSON | 供结构化处理、坐标回溯和调试 |
| 原始 PDF | 供人工核验和答案引用 |

## 六、Markdown 与 JSON 的分工

跨页表格解析后，不建议只保留一种格式。

### Markdown

适合：

- LLM 阅读
- RAG 文本索引
- 快速预览
- 人工编辑
- 轻量表格问答

优点：

- 语义清晰。
- LLM 友好。
- 可以直接作为上下文。

缺点：

- 坐标、页码、置信度等结构信息表达弱。
- 大表格容易过长。
- 不适合复杂程序化处理。

### JSON

适合：

- 坐标回溯
- 表格合并
- 字段校验
- 结构化查询
- 错误分析
- 与原图对齐

优点：

- 结构明确。
- 可保留 bbox、page、confidence、cell_id。
- 方便程序化处理。

缺点：

- 不如 Markdown 适合直接给 LLM 阅读。
- 需要额外转换为可读文本。

最佳实践：

> Markdown 负责进入 RAG 文本链路，JSON 负责结构化处理和溯源，两者都应该保留。

## 七、LLM 在跨页表格合并中的角色

跨页表格合并可以分成两类任务：

### 1. 确定性任务

适合用规则和代码处理：

- 删除重复表头。
- 过滤页码。
- 根据列坐标对齐。
- 合并相同列数表格。
- 保留 page 和 bbox。
- 输出 Markdown / JSON。

### 2. 语义判断任务

适合引入 LLM 辅助：

- 判断两个表格是否语义连续。
- 修正 OCR 错误列名。
- 判断下一页表格是否继承上一页表头。
- 将多个 Markdown 表格合并成完整表格。
- 对不规范表格做字段归一化。

LLM 不适合替代 OCR 和版面检测，但适合做结构化结果后的语义对齐。

推荐流程：

```text
Layout / OCR / Table Detection
  → 生成 Markdown + JSON
  → 规则先做基础合并
  → LLM 处理语义对齐和异常判断
  → 输出最终结构化表格
```

## 八、跨页表格入 RAG 的推荐方式

跨页表格不建议直接整表塞进一个超长 chunk。

推荐方式：

### 1. 小表格

直接转 Markdown 表格，作为一个完整 chunk。

适合：

- 行数少
- 列数少
- 查询主要围绕整张表

### 2. 中等表格

按行组切分。

示例：

```text
表格标题 + 表头 + 第 1-20 行
表格标题 + 表头 + 第 21-40 行
表格标题 + 表头 + 第 41-60 行
```

每个 chunk 都带上表头，避免召回时丢字段语义。

### 3. 大表格

按业务实体或字段分组。

例如：

- 按案件编号
- 按产品分类
- 按部门
- 按日期区间
- 按地区

大表格还应考虑进入结构化数据库，而不是只依赖向量库。

### 4. 高精度查询场景

同时构建：

```text
Markdown 文本索引
  → 支持自然语言问答

JSON / SQL 结构化索引
  → 支持精确过滤、统计、排序

全文检索索引
  → 支持编号、金额、专有名词、错误码
```

## 九、跨页表格解析质量评估

评估跨页表格解析不能只看 OCR 文本是否存在。

需要检查：

1. **表格区域是否识别完整。**
2. **上下页表格是否正确判定为连续。**
3. **表头是否正确继承或对齐。**
4. **列数是否一致。**
5. **行内容是否错位。**
6. **跨页断行是否合并。**
7. **页眉页脚是否被过滤。**
8. **OCR 字段是否有明显错误。**
9. **Markdown 表格是否可读。**
10. **JSON 是否保留 page、bbox、confidence。**
11. **最终 chunk 是否保留表头。**
12. **用户问题是否能召回正确行或正确表格。**

建议建立跨页表格测试集：

- 单页规则表格
- 双页连续表格
- 多页连续表格
- 下一页无表头表格
- 重复表头表格
- 跨页断行表格
- 有页眉页脚干扰的表格
- 无边框表格
- 扫描件表格
- 手写字段表格

## 十、工程落地注意事项

### 1. 模型下载和业务处理要分离

文稿里提到 MinerU 首次运行会下载模型，耗时可能很长。

生产系统中不能在用户上传文档时临时下载模型。

正确做法：

- 部署阶段提前下载模型。
- 启动阶段检查模型完整性。
- 业务处理阶段只执行推理。
- 模型缺失要提前报警，而不是用户请求时失败。

### 2. CPU 和 GPU 路径要区分

CPU pipeline 可以用于测试和轻量任务，但速度慢。

GPU / SGLang 路径适合生产批量处理，但部署成本更高。

建议：

- 本地验证：CPU pipeline。
- 批量生产：GPU 服务。
- 高并发：异步任务队列。
- 大文件：离线批处理。

### 3. 解析任务应该异步化

跨页表格解析通常耗时较长，不适合阻塞用户请求。

推荐架构：

```text
用户上传 PDF
  → 创建解析任务
  → 后台队列处理
  → 保存中间产物
  → 生成 Markdown / JSON
  → 进入 RAG 索引
  → 前端展示处理状态
```

### 4. 中间产物必须保留

复杂表格解析很难一次完全正确。

必须保留：

- 原始 PDF
- 页面图片
- layout 标注图
- 表格裁剪图
- OCR 结果
- Markdown
- JSON

这些产物用于：

- 人工校验
- 错误定位
- 模型调参
- 答案溯源
- 后续重跑

### 5. 表格合并要保守

跨页表格误合并比不合并更危险。

建议：

- 低置信度时不要自动合并。
- 给出人工确认入口。
- 保留合并前后的表格。
- 给每次合并记录置信度和依据。

## 十一、常见问题与处理建议

### 1. OCR 能识别文字，但表格结构混乱

原因：

- 只做了整页 OCR，没有做表格结构识别。

处理：

- 增加 table detection。
- 单元格级 OCR。
- 输出 JSON 保留 row、col、bbox。

### 2. 下一页表格没有表头，字段语义丢失

原因：

- 跨页连续关系没有识别。

处理：

- 根据列坐标和上页表头继承。
- 每个 chunk 都补充表头。
- JSON 中记录 `continued_from`。

### 3. 页眉页脚混入表格

原因：

- 没有做版面区域过滤。

处理：

- layout 阶段识别 header/footer。
- 根据固定区域和重复文本过滤。
- 对页码和页眉做规则清洗。

### 4. 两个不同表格被错误合并

原因：

- 只根据相邻页判断连续。

处理：

- 同时判断表格标题、列数、列宽、表头语义、章节标题。
- 低置信度时拆开处理。

### 5. Markdown 表格进入 RAG 后召回不准

原因：

- 表格太长。
- chunk 没有保留表头。
- 用户问题是字段级或行级查询。

处理：

- 按行组切分。
- 每个 chunk 重复表头。
- 同步构建 JSON/SQL 索引。
- 对专有名词加全文检索。

## 十二、最终沉淀

跨页表格解析是复杂文档 RAG 中最典型的结构恢复问题。

它的关键不是 OCR，而是：

1. **先找位置。** 识别页面中的表格区域。
2. **再识结构。** 恢复行、列、单元格和表头。
3. **再读内容。** 对单元格做 OCR。
4. **再判连续。** 判断上下页表格是否属于同一张表。
5. **再做合并。** 对齐表头、去除干扰、合并断行。
6. **最后入库。** 同时保留 Markdown、JSON 和来源坐标。

如果只保留一句话：

> PDF 跨页表格入 RAG 的最佳实践，是用 Layout + Table Detection + OCR 恢复表格结构，再用规则和 LLM 做跨页语义对齐，最终同时输出 Markdown 给模型阅读、JSON 给系统溯源和结构化处理。
