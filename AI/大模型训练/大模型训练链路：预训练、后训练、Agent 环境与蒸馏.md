# 大模型训练链路：预训练、后训练、Agent 环境与蒸馏

## 一、问题背景

大模型能力不是一次预训练产生的单一结果，而是数据、模型结构、分布式训练、后训练、评测、奖励、Agent 环境、蒸馏和部署共同作用的结果。

用户感受到的“模型变聪明了”，可能来自多种变化：模型获得了更多知识，更会遵循指令，更擅长推理和工具调用，回答更符合偏好，长任务更稳定，或者同等能力下成本更低。

因此，理解训练不能只看参数量和预训练语料，而要把它看成一条围绕真实任务持续反馈的工程流水线。

## 二、核心结论

大模型训练的核心不是单纯把模型做大，而是让“数据—训练—评测—奖励—环境—部署”形成闭环。

预训练决定基础能力上限，后训练决定模型是否会按用户期望工作，Agent 环境决定模型能否在真实任务中持续行动，蒸馏和部署决定能力能否以可接受的成本交付。

## 三、完整训练链路

~~~
原始数据
  → 数据清洗与配方设计
  → 模型结构与训练系统设计
  → 预训练
  → 指令微调与冷启动
  → 偏好优化与强化学习
  → 评测、Grader 与 Reward 闭环
  → Agent 环境与 Harness 训练
  → 蒸馏和模型压缩
  → 部署、生产反馈和下一轮训练
~~~

这不是严格线性的流程。生产流量会回流到数据工程，离线评测会反过来影响训练配方，失败轨迹会成为后续 SFT、RL 或 Harness 优化的数据。

## 四、数据工程决定模型能学到什么

### 原始数据不是可以直接训练的燃料

网页、代码仓库、书籍、论坛和业务文档，需要经过文本抽取、语言识别、质量过滤、隐私处理、安全过滤、文档级和行级去重、污染检测、许可证管理和数据混合。

重复模板、镜像网页、低质量内容和训练集泄漏，会让模型记住容易复制的模式，却不一定形成真正可迁移的能力。

### 数据配方本身就是能力设计

代码、数学、百科、对话、推理和多语言内容的比例，会直接影响模型的能力结构。数据混合不是最后的清洗步骤，而是模型产品设计的一部分。

合成数据也已经成为正式训练流程。更强模型可以生成指令数据、推理轨迹、代码样本和评测样本，再经过筛选和验证，用于训练更小或更新的模型。

## 五、预训练是能力底座，不是最终产品

### 预训练解决什么问题

预训练通过下一个 token 预测学习语言分布，把语料中的知识、模式和表达规律压缩进参数。

它主要决定模型能接触到哪些知识、能否泛化到新表达、能否形成语言和推理的基础模式，以及后续训练可以激活多少能力。

但预训练不会自动让模型成为好用的助手。听懂指令、遵守格式、拒绝危险任务、稳定调用工具和输出符合用户习惯的答案，都需要后训练继续塑造。

### 参数量不是唯一目标

在固定算力下，需要同时权衡参数量、训练 token 数、总计算预算、训练时长、上下文长度和推理成本。

模型太大但训练不足，可能不如参数更小但训练充分的模型。评价训练配方时，不能只看参数量，还要看训练 token 和总 FLOPs。

### Tokenizer 是长期成本决策

Tokenizer 的词表和切分方式会持续影响中文、代码和数学公式的 token 效率、上下文窗口容量、推理成本、多语言能力以及训练吞吐。

Tokenizer 如果把中文或代码切得过碎，后续每次训练和推理都会承担额外成本，因此应该在训练早期作为长期基础设施设计。

## 六、系统和架构约束要在训练前决定

### 大模型训练首先是分布式系统问题

真正训练大模型时，需要提前设计 GPU 和显存、节点通信、数据并行、张量并行、流水线并行、Checkpoint、故障恢复、混合精度、吞吐和成本。

训练运行数周后出现 loss spike、静默硬件错误、通信异常或错误梯度，都会污染训练结果。大规模训练的快速检测、隔离和恢复，本身就是核心工程能力。

### MoE 是容量、计算和系统复杂度的折中

MoE 通过路由让每个 token 只激活部分专家，从而在相近计算量下扩大总参数容量。代价是路由、负载均衡、专家通信、训练稳定性和部署基础设施都更复杂。

### 长上下文和多模态会改变训练配方

长上下文会同时影响 Attention 成本、Batch size、数据编排、并行策略、训练稳定性和推理成本。多模态也不只是增加一个图像编码器，还会改变数据混合、编码器设计、训练任务和安全评测。

单卡可运行、长上下文、量化部署等目标，应该在训练配方阶段确定，而不是发布时再补成产品功能。

## 七、后训练决定模型是否会用

### 指令微调建立正确起点

SFT 使用高质量的指令—回答样本，让模型学会理解任务、组织回答、遵守格式、表现出稳定的助手行为和调用工具。

SFT 学到的不只是知识，也会学到回答风格。数据长度、表达格式、是否带引用和是否偏好详细回答，都会影响最终体验。

### 偏好优化和强化学习

RLHF 通过人类偏好训练奖励模型再进行强化学习；DPO 直接从偏好对比数据中优化；RFT 则把任务定义、评测器和奖励信号组合成更容易产品化的强化微调流程。

它们共同解决的问题是：如何把“什么是更好的回答”纳入训练目标。

### 冷启动、RL、拒绝采样和对齐是一个循环

复杂推理模型的后训练可以拆成：

~~~
冷启动 SFT
  → 在可验证任务上强化学习
  → 过滤成功轨迹
  → 拒绝采样微调
  → 有益性和安全性对齐
~~~

冷启动让强化学习有稳定起点；RL 探索更好的轨迹；拒绝采样把成功轨迹转成新的 SFT 数据；最终对齐把行为收敛到可发布的助手形态。

### GRPO 的工程价值

在数学、代码和逻辑等可验证任务中，可以对同一个问题采样多个回答，通过组内相对排序计算优势信号，不需要额外维护独立的价值网络，能降低大模型强化学习的工程负担。

## 八、评测、Grader 和 Reward 决定模型追求什么

可以这样理解：

- Eval：决定测什么任务。
- Grader：把一次输出转换成分数。
- Reward：决定模型后续被推向哪个方向。

完整反馈链路是：

~~~
任务定义
  → Rollout 产生执行轨迹
  → Grader 评分
  → Reward 优化
  → 再次 Rollout
  → 重新评测
~~~

如果只看最终答案，模型可能学会走捷径；如果评分过粗，噪声会被强化；如果只优化榜单，真实任务体验不一定变好。

### ORM 和 PRM 的取舍

ORM 只评价最终结果，成本较低、容易启动，但反馈稀疏，容易忽略错误过程。PRM 评价中间过程，反馈更密，适合数学、代码和复杂推理，但标注和系统成本更高。

工程上可以先用 ORM 建立基础闭环，再对高价值可验证任务增加过程检查和程序化验证。

### 防止 Reward Hacking

模型会优化评分通道，而不一定真正完成任务。常见风险包括过拟合测试、迎合 Judge、利用评测分布、只优化短期结果和生成看似合理但没有依据的解释。

评测不能只看最终分数，还要结合中间轨迹、工具调用、过程约束、未见数据、安全性、泛化能力和真实任务反馈。

## 九、对齐和安全不是训练后的补丁

对齐训练要让模型在任务能力、安全边界和用户意图之间保持稳定行为。安全原则应该进入训练数据、评测任务、Grader、工具权限、运行环境和人工审批流程。

系统测什么、如何评分、奖励什么，模型就会朝什么方向发展。不能只在模型发布前增加一层表面拒答规则。

## 十、Agent 训练的核心从数据转向环境

### Agent 训练和普通 SFT 的区别

SFT 更关注样本多样性；Agent 训练更关注环境质量和完整任务表现：

~~~
理解目标
  → 规划步骤
  → 调用工具
  → 接收环境反馈
  → 修正计划
  → 持续执行
  → 交付可验证产物
~~~

训练环境必须具备稳定性、真实性、任务覆盖度、难度分布、反馈丰富度、状态可复现和抗利用能力。

工具返回值不稳定、浏览器环境和生产环境不一致、文件系统状态不可复现时，Grader 会先出错，模型学到的可能是环境漏洞，而不是任务能力。

### Harness 进入训练系统

Agent 训练时，Harness 会决定模型看到什么输入、Prompt 如何构造、何时检索和裁剪上下文、何时更新记忆、工具如何编排以及环境反馈如何返回。

训练对象已经从单个回答模型扩展为：

~~~
模型
  + 工具
  + 环境
  + 记忆
  + 上下文管理
  + 编排逻辑
  + 评测与奖励
~~~

### 多 Agent 训练先解决信用分配

多 Agent 系统中，如果同时优化所有子 Agent，很难判断成功或失败应该归因给谁。更稳的做法是先训练负责规划和编排的 orchestrator，把奖励归因集中到可控层，并评估任务成功、有效并行、完成约束和关键路径长度。

并行数量本身不是目标。只有关键路径变短、总成本可控、结果质量没有下降，才说明并行策略真正有效。

## 十一、Harness 本身也可以被优化

Harness 的优化对象可以逐步升级：

~~~
Prompt
  → 结构化上下文
  → 工作流
  → Harness 代码
  → 优化 Harness 的程序
~~~

可靠的 Harness 优化闭环应该是：

~~~
采集失败轨迹
  → 聚类重复失败模式
  → 提出边界明确的修改候选
  → 在已知集和未见集上回归测试
  → 通过后合并
  → 失败方案保留记录但不启用
~~~

关键不是让 Agent 自由修改整个系统，而是限制可编辑范围，并把评估器、权限控制和安全边界放在优化循环之外。

## 十二、蒸馏是能力迁移和成本解耦

蒸馏的核心不是简单复制答案，而是让大模型先完成复杂推理，再把高质量轨迹、结果和行为模式迁移给小模型：

~~~
大模型探索和验证
  → 筛选高质量轨迹
  → 构造成 SFT / 蒸馏数据
  → 训练更小模型
  → 用真实任务评估迁移效果
~~~

大模型负责发现能力，小模型负责低成本执行。蒸馏后仍要重新验证推理过程、安全行为、工具调用和真实任务效果。

## 十三、部署和生产反馈会继续影响训练

上线版本不是训练分数最高的 Checkpoint，而是综合考虑真实任务成功率、成本、延迟、拒答行为、工具稳定性、长任务表现和回归风险后的产品选择。

生产系统可以持续回流：

~~~
真实请求
  → 失败轨迹和用户反馈
  → 数据清洗与难例构建
  → 离线评测
  → 后训练或 Harness 优化
  → 新版本灰度发布
~~~

训练因此从一次性项目变成持续迭代系统。

## 十四、工程落地中的关键风险

### 训练数据只追求数量

没有去重、污染控制和质量配方，训练成本会被低价值数据消耗。

### 只看模型参数和榜单

参数量和单项 benchmark 不能代表真实 Agent 能力，还要看任务成功率、成本、稳定性、工具调用和长任务表现。

### Grader 只看最终结果

只看结果会鼓励模型走捷径。高价值任务应同时评估过程、证据、工具调用和安全边界。

### 训练环境不稳定

如果工具返回值、文件系统、浏览器或数据库状态不可复现，模型会学到环境漏洞，训练结果无法迁移到生产。

### 自我改进权限过大

让 Agent 修改 Harness 或运行环境时，必须限制可编辑目录、命令范围和配置边界，避免破坏系统抽象和安全隔离。

### 忽略失败数据

只保存成功轨迹会造成过度乐观，也会让系统重复走错路。失败原因、未完成任务和被拒绝的候选方案同样应该持久化。

## 十五、推荐学习和落地路径

### 第一阶段：理解训练分层

先区分预训练、SFT、偏好优化、RL、蒸馏各自解决的问题。

### 第二阶段：建立评测和数据闭环

为真实任务建立数据集、Grader、离线评测和失败轨迹记录，不要只依赖公开榜单。

### 第三阶段：把 Agent 环境工程化

固定工具接口、环境状态、反馈结构、权限边界和任务验收方式，保证 Rollout 可复现。

### 第四阶段：优化 Harness

先优化 Prompt 和上下文，再优化工作流、记忆、检索、工具编排和状态管理。只有有稳定评估集后，才考虑自动搜索 Harness。

### 第五阶段：做模型分层和蒸馏

让强模型负责复杂规划和能力发现，让小模型承担分类、路由、抽取和高频低风险任务，降低成本和延迟。

## 十六、最终沉淀

大模型训练不是“预训练完成就结束”，而是一条围绕真实任务持续反馈的工程闭环：

~~~
数据配方决定模型学什么
预训练决定基础能力上限
后训练决定模型是否会用
Grader 和 Reward 决定模型追求什么
Agent 环境决定模型能否完成长任务
Harness 决定能力如何被组织和放大
蒸馏和部署决定能力能否低成本交付
生产反馈决定下一轮如何继续改进
~~~

对 Agent 工程师来说，模型、工具、环境、上下文、评测和奖励不是彼此独立的模块，而是一套共同决定 Agent 行为的系统。真正可持续的能力提升，来自这套系统能否稳定产生数据、验证结果、吸收失败并安全迭代。
