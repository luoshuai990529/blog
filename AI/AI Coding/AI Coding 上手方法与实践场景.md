# AI Coding 上手方法与实践场景

## 一、问题背景

AI Coding 的门槛正在从“能不能写代码”转向“能不能把问题交给 Agent 可靠执行”。传统对话式 AI 主要负责生成片段，使用者还要自己复制、粘贴、运行和排错；Coding Agent 则可以直接读取项目、修改文件、执行命令、查看错误并继续迭代。

这带来了更高的效率，也带来了新的要求：需求必须清楚，执行范围必须受控，结果必须可验证，重要状态必须可恢复。

## 二、核心结论

AI Coding 的入门重点不是先学会完整编程，而是建立一套“描述任务—让 Agent 执行—检查结果—必要时回滚”的工作方法。

真正影响结果的不是模型输出速度，而是以下几件事：

- 是否把问题背景、目标、范围和验收标准说清楚。
- 是否给 Agent 提供足够的项目上下文。
- 是否把大任务拆成可以独立验证的小任务。
- 是否保留 Git 检查点和可恢复状态。
- 是否让 Agent 通过测试、页面检查或数据校验完成验收。
- 是否对命令执行、文件修改、账号、支付和个人信息设置安全边界。

## 三、AI Coding 的正确理解

### AI Coding 不只是代码补全

成熟的 Coding Agent 更接近一个运行在项目环境里的通用 Agent：

~~~
读取项目上下文
  → 理解需求
  → 规划修改范围
  → 修改多个文件
  → 执行命令和测试
  → 分析报错
  → 继续修复
  → 输出可验收结果
~~~

它可以处理代码，也可以处理数据、文档、报表、原型和自动化脚本。所谓“Coding”更多是因为它能直接操作文件和运行环境，而不是只能写代码。

### 非技术人需要掌握的最低知识

不需要先成为专业程序员，但至少要知道这些概念大概解决什么问题：

- 终端：执行命令和启动项目的入口。
- Git：保存检查点、查看差异和回滚改动。
- 文件与目录：理解项目结构和修改范围。
- 函数、变量、状态：帮助把需求拆成可执行逻辑。
- 常用框架：知道 React、Vue、Next.js 等大概负责什么。
- 浏览器开发者工具：查看页面、网络请求和运行时错误。
- 报错信息：定位失败位置和失败原因。

读懂 Agent 改了什么、为什么报错，通常比一开始自己从零写代码更重要。

## 四、从小任务建立使用习惯

### 先做 software for one

第一次不要直接做面向大量用户的完整产品。更适合从只服务自己的小工具开始，例如：

- 把语音批注转换成会议纪要。
- 把多个表格合并成个人日报。
- 把一批链接整理成主题清单。
- 做一个提醒固定事项的小面板。
- 把重复的网页操作封装成命令。

这类任务的好处是：需求边界清楚，反馈速度快，使用者最了解真实问题，结果也容易判断。

### 按产出节奏逐步升级

可以按照下面的节奏建立能力：

~~~
第 1 天：修改一个现成的 Markdown、CSV 或 Excel 文件
第 1 周：做一个单页工具或个人仪表盘
第 1 个月：把每周重复操作变成命令或页面
第 3 个月：完成一个只服务自己的小软件
~~~

每一步都应该有可以运行或交付的结果，而不是停留在学习工具按钮。

## 五、需求描述决定 Agent 的执行分支

### 先写问题，再写功能

不要只写：

~~~
帮我做一个客户跟进工具。
~~~

应该先说明：

- 谁在什么场景下使用。
- 当前遇到什么问题。
- 现有流程哪里低效。
- 做成后什么结果算成功。

例如：

~~~
销售目前用多个表格记录客户跟进，无法快速找到即将逾期的客户。
需要一个单页本地工具，集中查看客户、下次跟进时间和沟通记录。
第一版只服务个人，不做登录、分享和后端同步。
~~~

问题背景会影响后续所有产品判断，比单纯罗列功能更重要。

### 明确目标、范围和不做什么

需求中应该同时写清：

- 目标：这次要解决什么问题。
- 范围：本次允许修改哪些文件、模块或数据。
- 非目标：明确暂时不做登录、分享、SEO、权限等功能。
- 约束：技术栈、运行环境、数据存储和依赖限制。
- 异常：接口超时、数据为空、图片失效、权限不足时怎么处理。

如果不写边界，Agent 很容易主动增加功能、顺手重构代码或引入不必要的依赖。

### 验收标准必须可判断

“页面要快”“布局正常”“体验好”都无法直接验收。更有效的标准应该可以被执行或观察：

- 375px 和 1440px 宽度下布局不发生错位。
- 首屏在指定环境下 1.5 秒内完成展示。
- 空数据时显示明确的空状态。
- 接口失败时保留可重试入口。
- 完成后通过构建、测试和指定命令检查。

需求越具体，Agent 需要猜测的内容越少，返工也越少。

## 六、CLAUDE.md：把项目背景固化下来

对于 Claude Code 等 Coding Agent，项目根目录下的 CLAUDE.md 可以作为项目交接文档，保存每次执行都需要知道的背景和规则。

适合写入：

- 项目目标和目录结构。
- 技术栈和启动命令。
- 测试、构建和格式化命令。
- 代码风格和文件组织规则。
- 禁止修改的目录。
- 关键业务约束。
- 完成任务前必须执行的验证步骤。

一份有效的 CLAUDE.md 应该短、直接、可判断：

- 优先使用命令式表达。
- 每条规则都能被执行或验证。
- 避免写“尽量”“最好”“代码质量要高”这类无法判断的表述。
- 只放长期稳定的项目规则，不要把临时任务塞进去。

长会话还应该保留关键决策的理由。例如，不只写“接口使用 POST”，还要记录为什么使用 POST。上下文压缩时，决策理由比零散聊天记录更值得保留。

## 七、复杂任务先规划，再执行

### Plan 模式适合复杂改动

涉及多个文件、重构、数据迁移或不熟悉模块时，应该先让 Agent 输出计划：

- 要读取哪些文件。
- 准备修改哪些文件。
- 每个修改的原因是什么。
- 可能影响哪些模块。
- 如何验证结果。

先审方向，再让 Agent 执行，通常比直接让它连续修改更安全。

### Auto 模式需要明确边界

日常操作可以让低风险步骤自动执行，但涉及以下动作时要保留确认：

- 删除文件或数据。
- 修改数据库。
- 发送消息或对外发布内容。
- 访问敏感系统。
- 读取密钥、个人信息或支付信息。

自动化的目标是减少无意义确认，不是取消所有人工判断。

## 八、验证、回滚和排错

### “完成”必须有证据

Agent 说“搞定了”不等于任务完成。至少要检查：

- 命令是否成功退出。
- 构建和测试是否通过。
- 页面是否真的能打开。
- 数据结果是否符合预期。
- 需求中的每条验收标准是否满足。
- 是否产生了额外文件、依赖或未授权改动。

### 大改前创建 Git 检查点

开始复杂修改前，先确认工作区状态并建立检查点：

~~~
查看 git status
  → 确认已有改动
  → 创建可回退检查点
  → 执行本次任务
  → 对比 git diff
  → 验收后再保留改动
~~~

如果结果不对，优先回退到已知状态，而不是在错误改动上继续叠加补丁。

### 排错先定位根因

如果 Agent 连续多轮“改了试试”，通常说明诊断还不充分。应该暂停修改，要求它先说明：

- 哪个文件、哪一行出现问题。
- 错误的直接原因是什么。
- 预期行为和实际行为有什么差异。
- 当前修改会不会影响其他模块。
- 如何用最小改动验证假设。

修复策略应该是：观察 → 定位 → 提出假设 → 最小修改 → 验证，而不是不断叠加补丁。

## 九、适合非技术人的实践场景

### 文档和内容处理

可以让 Agent 把合同、会议记录、网页资料和 PDF 整理成：

- 会议纪要。
- 项目进展简报。
- 一页纸报告。
- 主题化知识库。
- 多版本差异说明。

这类任务的关键不是代码，而是明确输入资料、提取视角、输出格式和引用要求。

### 数据和报表处理

适合把 CSV、Excel 或后台导出的数据交给 Agent 做：

- 清洗字段。
- 分组和统计。
- 生成销售报表。
- 识别异常数据。
- 输出图表或 HTML 页面。

需求中要明确计算口径、字段含义、空值处理和结果校验方式，不能只说“帮我分析一下数据”。

### 原型和个人工具

产品或业务人员可以先用 Agent 做出可讨论的原型，再决定是否进入正式开发：

- 单页工具。
- 内部管理页面。
- 数据看板。
- 表单和计算器。
- 小型自动化脚本。

原型的目标是验证问题、流程和交互，不应一开始就追求完整的工程架构。

### 网页操作自动化

很多运营工作本质上是重复的浏览器流程：查询后台、导出报表、抓取列表、整理舆情、发送固定格式消息。

可以通过 CLI、浏览器自动化原语或 MCP 工具，把网页操作封装成 Agent 可调用的工具。工具化之后，Agent 才能稳定复用流程，而不是每次依赖人工点击和复制。

## 十、Skill：把重复经验变成可复用流程

当一类任务反复出现时，不应该每次重新描述完整步骤，可以将它沉淀成 Skill。

一个好的 Skill 应该：

- 有明确的触发条件。
- 只负责一个相对独立的任务。
- 定义输入、步骤和输出。
- 包含验证和失败处理。
- 不把多个无关流程堆在一起。

例如，可以分别沉淀：

- 生成项目 CLAUDE.md。
- 检查前端页面响应式布局。
- 读取 CSV 并生成销售报表。
- 把会议记录整理成项目周报。
- 对代码改动执行构建和测试。

Skill 的价值不只是少写几句 Prompt，而是把个人经验、检查清单和工具调用方式固化成可重复执行的流程。

## 十一、上下文、会话和记忆管理

### 一个会话只解决一个主要目标

长会话容易出现上下文膨胀、目标漂移和历史决策丢失。更稳的方式是：

- 一个会话围绕一个主要目标。
- 完成一个阶段后清理无关上下文。
- 长任务阶段性写入 HANDOFF.md 或其他状态文件。
- 把关键决策、未完成事项和验证结果持久化。

### 项目规则和个人偏好分开

可以把信息分成两层：

- CLAUDE.md：项目级规则、技术栈、命令和限制。
- Memory：跨项目的个人偏好和协作习惯。

不要把所有聊天历史都当成记忆。真正值得长期保留的是稳定规则、长期偏好和经过验证的工作方法。

## 十二、安全边界

AI Coding 的代码能运行，不代表可以直接上线。以下内容需要额外审查：

- 登录、权限和身份认证。
- 支付、退款和财务操作。
- 个人信息和密钥处理。
- 删除数据和批量写入。
- 对外发布、发信和自动操作生产环境。
- 依赖安装、脚本执行和网络访问。

安全做法包括：

- 不把密钥直接贴进对话或代码。
- 对高风险命令设置人工确认。
- 使用最小权限和隔离环境。
- 让 Agent 解释不熟悉命令的作用。
- 对生成代码做依赖、权限和输入校验审查。

## 十三、推荐落地路径

### 第一步：从低风险、可验收任务开始

先处理 Markdown、CSV、Excel、个人页面和小型脚本，建立“描述—执行—验证”的闭环。

### 第二步：补齐项目上下文

建立简短的 CLAUDE.md，写清项目背景、常用命令、目录边界和验收方式。

### 第三步：把需求写成可执行规格

每个任务都补充背景、目标、范围、约束、异常情况和验收标准。

### 第四步：对复杂改动先规划

先审计划，再执行；大改前建立 Git 检查点；完成后运行验证命令。

### 第五步：沉淀重复流程

把反复出现的设计、排错、数据处理和检查流程封装成 Skill 或命令。

### 第六步：逐步扩大自动化范围

在权限、审计、回滚和测试机制成熟后，再让 Agent 操作更多文件、系统和后台任务。

## 十四、最终沉淀

非技术人用好 AI Coding，不是先学会写完整代码，而是学会把模糊想法转化为可执行、可约束、可验证的小任务。

AI Coding 的长期效率来自一套工程闭环：

~~~
问题背景
  → 目标和范围
  → 项目上下文
  → 任务计划
  → Agent 执行
  → 测试和验收
  → Git 检查点与回滚
  → Skill 和记忆沉淀
~~~

当需求表达、上下文管理、验证习惯、安全边界和流程沉淀都建立起来之后，AI Coding 才会从“偶尔帮忙生成代码”变成稳定的个人生产力系统。
